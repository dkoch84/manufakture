# @manufakture/kernel

The only path by which manufakture touches OpenCASCADE. OCCT (libcascade 3.0.2, single-threaded, [ADR 0002](../../docs/adr/0002-kernel-build-and-loading.md)) runs in a Web Worker behind a thin wrapper of our own ([ADR 0001](../../docs/adr/0001-kernel-wrapper.md)); the main thread talks to it through Comlink with plain data and transferred buffers ([ADR 0007](../../docs/adr/0007-worker-protocol.md)). The UI thread never calls the kernel directly.

```
main thread                         kernel worker
-----------                         -------------
KernelClient  --- Comlink --->  createKernelWorkerApi   (loading, progress, transfer)
 (client.ts)                        KernelService      (batches, generations, errors as data, recycling)
                                    Kernel             (arena, ops, history, topology, mesh)
                                    libcascade (.wasm)
```

| Import                              | Where                 | What                                                                                                                         |

| `@manufakture/kernel/worker`        | worker entry          | `Comlink.expose` of the worker API, with the `.wasm` imported as a Vite `?url` asset                                         |
| `@manufakture/kernel/node`          | Node (tests, goldens) | `createNodeKernel()`, `createNodeService()`, `nodeLoader()`, `wasmPath()`                                                    |
| `@manufakture/kernel/testing`       | Node tests            | `track()`: records every embind object, to prove nothing is left undeleted                                                   |

## Using it from the app

The app talks to the regen worker (`@manufakture/regen/worker`), which hosts this package's worker API and the regen engine in one worker; its `RegenClient` is a `KernelClient`. `KernelClient.worker()` (protected) gives such a subclass the worker proxy typed as its extended API. What follows is the kernel's own worker, used as is by tests and tools.

```ts
import { spawnKernelWorker } from '@manufakture/kernel/client';

// At app start-up, so kernel loading overlaps UI start-up (ADR 0002).
const kernel = spawnKernelWorker({
  onStatus: (s) => {
    if (s.type === 'loading') splash.update(s.progress); // download, compile, instantiate, init, ready
  },
});
await kernel.ready;

const reply = await kernel.submit([
  { op: 'profile', frame, loops, featureId: 'sketch#1', keep: false },
  { op: 'extrude', profile: { result: 0 }, distance: 10, featureId: 'extrude#1' },
  { op: 'tessellate', shape: { result: 1 } },
]);
if (reply !== null) {
  // null: superseded by a newer submit, drop it
  const [, extrude, mesh] = reply.results; // typed per op
}
```

`spawnKernelWorker` creates `new Worker(new URL('./worker.ts', import.meta.url), { type: 'module' })`. Vite emits the `.wasm` as its own content-hashed asset and copies the Emscripten glue verbatim; the `.wasm` is never inlined (checked with a production build: `worker-*.js` 35 KB, `opencascade_single-*.js` 67 KB, `opencascade_single-*.wasm` 42.7 MB). Vite's default worker format builds; the T0.2 spike ran its module worker with `worker: { format: 'es' }`, which is the safer setting when the app wires this in. Hosting must serve the `.wasm` hashed, immutable and brotli-compressed (ADR 0002).

## Operations

A batch is a list of ops and gets one reply (ADR 0007, decision 3). An op can use the shape made by an earlier op of the same batch with `{ result: <index> }`, so a whole chain is one round trip. After a `feature` op, `{ result, body }` takes one of its bodies by id; a bare `{ result }` works only when the feature left exactly one body.

| Op             | Arguments                                                                                                                               | Value                                                                                                                       |
| -------------- | --------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| `box`          | `size`, `at?`                                                                                                                           | `{ shape }`                                                                                                                 |
| `cylinder`     | `radius`, `height`, `at?`, `axis?`                                                                                                      | `{ shape }`                                                                                                                 |
| `profile`      | `frame` (origin, xDir, normal), `loops` of line/arc/circle/bezier, each with `id?`                                                      | `{ shape }`: a planar face                                                                                                  |
| `extrude`      | `profile`, `distance` (along the normal) or a vector, `history?`                                                                        | `ExtrudeResult`: shape, history, `capStart`, `capEnd`, `sides` per loop in entity order, `sideIds`                          |
| `boolean`      | `kind` (`fuse`, `cut`, `common`), `shape`, `tools`, `simplify?`, `history?`                                                             | `OperationResult`: shape, history                                                                                           |
| `fillet`       | `shape`, `edges` (1-based edge indices), `radius`, `history?`                                                                           | `OperationResult`                                                                                                           |
| `tessellate`   | `shape`, `deflection?` (`linear` 0.1 mm, `angular` 0.5 rad)                                                                             | `MeshData`, transferred                                                                                                     |
| `topology`     | `shape`                                                                                                                                 | `Topology`: faces, edges, vertices (ADR 0007)                                                                               |
| `properties`   | `shape`                                                                                                                                 | volume, area, bounding box, validity, counts                                                                                |
| `release`      | `shapes`                                                                                                                                | `{ released, unknown }`                                                                                                     |
| `feature`      | `bodies` (`{ id, shape }` list, or `{ result }`), `feature`                                                                             | `FeatureOutcome`: the bodies after the feature, their names, errors, warnings (see Part features)                           |
| `resolve`      | `shape` (a named body), `refs` (`FaceRef` / `EdgeRef`)                                                                                  | `{ results }`: per reference its `Resolution` plus the face or edge geometry                                                |
| `connector`    | `shape` (a named body), `connectors` (`{ origin, inference }`)                                                                          | `{ results }`: per connector its frame or why there is none (Mate connectors)                                               |
| `pick`         | `shape` (a named body), `kind` (`face`, `edge`, `vertex`), `index`                                                                      | `{ ref }`: the `FaceRef` / `EdgeRef` / `VertexRef` a click there is stored as, or null                                      |
| `measure`      | `shape`, `targets` (`{ kind, name }` or `{ kind, index }`), `body?`                                                                     | `MeasureResult`: per target its exact values, distance and angle of two, body properties (Measure)                          |
| `obb`          | `shape`, `optimal?` (default true)                                                                                                      | `OrientedBox`: centre, unit axes and sizes, longest first, and whether the OBB or the axis-aligned box was used             |
| `exportStep`   | `bodies` (`{ shape, name }`, at least one), `assembly?`                                                                                 | `{ data }`: one AP214 STEP file, transferred; an assembly with `assembly` (STEP exchange)                                   |
| `importStep`   | `data` (the file's bytes, or base64 text of them)                                                                                       | `{ shape }`: a new shape without names, a compound when the file has several roots                                          |
| `interference` | `items` (`{ shapes, transform? }`), `pairs?`, `tolerance?`, `mesh?`, `deflection?`, `prefilterOnly?`                                    | `InterferenceResult`: candidates, booleans run, overlapping pairs with volume (and mesh), failures (Interference)           |
| `project`      | `items` (`{ shape, transform?, key }`), `view` (`direction`, `up`, `origin?`), `hidden?`, `smooth?`, `sewn?`, `deflection?`, `section?` | `ProjectResult`: `keys`, classified 2D edges per item, `bounds`, and with `section` the section faces as loops (Projection) |

Every op takes `featureId?` (echoed in its result and any failure, and stamped on the shapes it makes) and `keep?` (default true; `false` releases the shapes the op makes when the batch ends, for intermediates).

Inside the worker the same operations are methods of the synchronous `Kernel` (`box`, `cylinder`, `profile`, `extrude`, `boolean`, `fillet`, `mesh`, `topology`, `properties`, `measure`, `orientedBox` (the `obb` op), `interference`, `project`, `count`, `solids`, `release`, `checkpoint`, `releaseSince`), which throw `KernelError`. For the part features it also has `revolve` (with caps and the face each entity swept, 0 for an entity on the axis), `thread` (a thread's tools, see Threads), `chamfer` (distance, two distances or distance and angle, on a reference face), `shell` (remove faces, wall inward or outward), `offset`, `draft`, `transform` (translate, rotate, mirror), `compound`, `geometry` (the line, circle, plane or axis of a face or edge), `isValid`, and `setNames` / `named` (a body's names, kept on its arena entry and dropped with it). Every topology-changing one returns kinded history. The regen engine (`packages/regen`, #932) calls `applyFeature` directly from the worker, or sends `feature` ops.

Profile entities are `line` (`start`, `end`), `arc` (`center`, `start`, `end`, `clockwise?`), `circle` (`center`, `radius`, a loop on its own) and `bezier` (`points`: 2 to 4 control points, so a straight segment, a quadratic or a cubic; it starts at the first and ends at the last). A Bezier becomes one edge on a `Geom_BezierCurve` whose poles are the control points placed on the frame (the plane map is affine, so the 3D curve is exactly the planar one), and sweeps one face (`surfaceofextrusion`, or `surfaceofrevolution` in a revolve). A cubic Bezier that ends where it starts may be a loop on its own (a closed quadratic bounds no area and is refused); any other entity must join the next one within the closure tolerance (1e-7 of the loop's size). A Bezier's last pole is then put exactly on the next entity's start (on its own first pole when it closes alone), since OCCT needs its end vertices to within about 1e-7 absolute: a gap the check accepts would otherwise fail to make an edge, or close into an invalid face. Drafting a Bezier's side is not supported: OCCT's draft cannot tilt a `surfaceofextrusion`, so an extrude with a `draft` and a Bezier edge fails with `draft cannot tilt face N`. Orientation is the kernel's: the outer loop is made counter-clockwise and holes clockwise from a signed area over sample points, Beziers sampled like arcs, so loops may come in either direction (glyph outlines and SVG paths, `packages/sketch`'s `outline.ts`, do not have to agree with the sketch's winding).

Profile entities may carry an `id` (a sketch region's edge id, `e2` or `e2#1`; unique within the profile, else `invalid-argument`). The kernel does not interpret it: `extrude` returns `sideIds`, the side face of every tagged entity by id, so the naming layer can name `<feature>:side:<id>` directly. `packages/sketch`'s `regionProfile` produces such loops from a sketch region; `regions.test.ts` builds its fixture profiles (`fixtures/region-profiles.json`) end to end.

## Part features

`applyFeature(kernel, bodies, input)` (`src/features.ts`) is one part feature: the part's bodies before it (`{ id, shape }[]`, in creator order; empty before the first feature) and a plain-data `FeatureInput` in, the bodies after it out, with every face and edge named. It is the API the regen engine (#932) builds on: it translates each core feature into an input (expressions evaluated to millimetres and radians, sketch regions turned into profile loops by `@manufakture/sketch`'s `regionProfile`, references copied as names) and chains the outcomes. The kernel has no runtime dependency on the sketch or core packages; references are resolved here, in the worker, against the names of all the input bodies.

| Kind      | Input                                                                                                                                                                                                                             | Faces it names                                                                                                                       |
| --------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| `extrude` | `profile` (`frame` and `loops`, or `frame` and `regions`; every entity with its sketch edge id), `extent` (`blind`, `symmetric`, `throughAll`, `upToFace` a planar face), `reverse?`, `draft?` (radians, + tapers inward), `mode` | `<id>:cap:start`, `<id>:cap:end`, `<id>:side:<edge id>`; several regions: `<id>:cap:start#k`, `<id>:cap:end#k` (see Several regions) |
| `revolve` | `profile`, `axis` (an `Axis`, a converted sketch line, or `{ edge, flip? }` a straight edge), `angle` (to 2 pi, right-handed about the axis direction), `symmetric?`, `mode`                                                      | the same; a full turn has no caps, an entity on the axis sweeps nothing                                                              |
| `fillet`  | `radius`, `edges` (`{ id, ref: EdgeRef }`)                                                                                                                                                                                        | `<id>:round:<ref id>`; `<id>:round:A&B` along a tangent chain; `<id>:corner:A&B&C`                                                   |
| `chamfer` | `size` (`distance`, `distances`, `distance-angle`), `edges` with an optional reference `face`                                                                                                                                     | `<id>:bevel:<ref id>`, and the same chain and corner names                                                                           |
| `shell`   | `thickness`, `faces` to remove (none: a closed hollow), `outward?`                                                                                                                                                                | `<id>:offset:X` for the wall grown from face X; a removed face's name goes to the rim                                                |
| `hole`    | `frame` (drilled against its normal), `points` (`{ id, at }`), `diameter`, `extent` (`blind` with `tipAngle?`, default 118 degrees, or `throughAll`), `head` (simple, counterbore, countersink)                                   | `<id>:<part>:<point id>`, part `wall`, `tip`, `bottom`, `cbore`, `cbore-floor`, `csink`                                              |
| `pattern` | `source` (`features`: extrude, revolve and hole inputs to rebuild; or `body`), `layout` (`linear`: direction vector or `{ ref, flip? }`, count, spacing; `circular`: axis or `{ ref, flip? }`, count, angle)                      | `<id>:i<k>/<source name>` for instance k (2 and up; 1 is the original)                                                               |
| `mirror`  | `source`, `plane` (a `Plane` or a planar `FaceRef`)                                                                                                                                                                               | `<id>:image/<source name>`                                                                                                           |
| `import`  | `step` (a STEP file's bytes, or base64 text), `mode`                                                                                                                                                                              | `<id>:face:<n>`, n in the file's face order; always fragile                                                                          |
| `derive`  | `sources` (`{ id, shape }`: bodies of another part built in this kernel), `rotation` (radians about x, then y, then z), `translation`, `mode`                                                                                     | `<id>:from/<source name>`, each `&` corner member prefixed too (see Derived bodies)                                                  |
| `thread`  | `ThreadGeometry`: `side`, `axis`, `radius` of the cylinder, `major`, `pitch`, `length`, `hand?`, `clearance?`, `start?` / `end?` (`open`, `chamfer`, `closed`), `phase?`; `scope?`. Or `ThreadFaceInput` (see Threads)            | `<id>:thread:<part>`, per turn `<id>:thread:<part>:<turn>` (see Threads)                                                             |
| `tools`   | `items` (`{ id, body, mode, primitive }`, `mode` `subtract` or `add`; a `box` or a `cylinder` with `step?` and `tip?`, see Tools)                                                                                                 | `<id>:<item id>:<role>`: `xmin` .. `zmax` of a box, `start`, `wall`, `end`, `step`, `shoulder`, `tip` of a cylinder                  |

A body's id is the id of the feature that made it (M2 plan, decision 1): `extrude#3`, or the `body` an extrude, revolve or import input names; pattern and mirror copies that become bodies are `pattern#k:i<n>` and `mirror#k:image`, derived copies `derived#k:from/<source body id>`, followed by `/<source id>` when the pattern copies several bodies or features (`pattern#2:i3/extrude#1`). Face names never include a body id, and they stay unique across the bodies of a part. Every feature is combined with each body on its own:

- `new` makes the tool a body of its own; it may overlap others (two 24,000 mm3 blocks sharing 12,000 are two bodies of 24,000 each, not one compound of 48,000). A `new` whose body id already exists is `invalid`.
- `add` fuses the tool with every body in scope it touches; bodies one tool joins merge into one under the id of the first of them in creator order, and the others are `consumed`. A tool that touches none becomes a body under the feature's id (or `body`), with a `detached` warning. With no body at all, `add` is `no-body`.
- `subtract` and `intersect` act on each body in scope the tool reaches; a cut that leaves a body in pieces keeps one body with several solids (`solids`), and one that leaves nothing of a body is `empty`. An intersect that reaches no body is `empty`; bodies it does not reach stay as they are.
- `scope` (extrude, revolve, import, derive, hole, and a pattern or mirror of bodies) lists the body ids a feature acts on, or copies; absent means every body. A scope entry that is not a body at that point is `lost` with `ref: 'scope'`. References are resolved on any body, scope or not.
- Fillet, chamfer and shell take no scope: they act on each body that owns some of their references (a closed hollow, with no faces, on every body). A reference whose names lie on two bodies (an edge between faces of different bodies) is `invalid`.
- A hole drills every body in scope it reaches; it fails only when a point misses them all.
- A thread cuts every body in scope its tools reach, and fails (`invalid`) when it leaves no thread face in any of them.
- A `tools` feature takes no scope: each item names its own body (see Tools).

A body whose bounding box no tool meets stays out of every boolean and keeps its shape id. An `add` tests each tool against the bodies its box meets (a fuse without history, counting solids) before the one fuse that makes the result; one tool meeting one body costs one boolean, as before. A hole always subtracts. A pattern has 1 to `MAX_PATTERN_COUNT` (1000) instances, the original included; core checks the same limit on a count written as a plain number. A circular pattern over a full turn spaces its instances evenly; over less, the last instance sits at `angle`.

Pattern and mirror copies of features are rebuilt per copy against the body at that point, then moved, so a through-all (or up-to-face) length is measured from where the copy will be: a through cut turned 90 degrees still goes through. A subtracting copy that does not touch any body changes nothing and gives a `missed` warning naming the instances (`pattern#3:i4`, `mirror#2:image`); the feature still succeeds, since a pattern running partly off the body is often meant (a hole, whose every point is placed by hand, errors instead). Added copies follow the `add` rules: copies touching no body (or only each other) become bodies of their own, with a `detached` warning. A pattern or mirror of bodies (`source: { type: 'body', mode? }`) copies the bodies in its scope; its copies are added (`add`, the default: what a one-body part did) or become bodies of their own (`new`). Feature ids are `kind#n`; sketch edge ids must be plain tokens with letter splits (`e2#a`) and at most one final positional piece (`e2#1`, from sketch regions); reference and point ids take no piece. Anything else (`e2#1#a`, a `:`, `|`, `/`, `&`, `?`) is rejected at the boundary, since it would read as a kernel split or break a name.

`FeatureOutcome` has `ok`, `bodies`, `created`, `changed`, `consumed`, `errors`, `warnings` and `resolved`. `bodies` is the body set after the feature, in creator order (a new body last, a merged body in the place of the first body merged into it), each `{ id, shape, names, solids }`; `created` lists the ids of the bodies the feature made, `changed` the existing bodies it gave a new shape, `consumed` the input bodies merged into another. The shapes of created and changed bodies are new, and the caller owns them; every other body keeps its input shape id. When a feature fails, `bodies` are the input bodies unchanged and the three lists are empty, so the features after it still regenerate (except a `tools` feature whose errors are all per item, which keeps what its other items did); a batch only owns (and with `keep: false` releases) the shapes the op made. `applyFeature` throws only `KernelError` `fatal` (a wasm trap).

| Error code      | Meaning                                                                                                                                                                        |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `lost`          | a reference (or a `scope` entry) no longer resolves: `missing` lists the names that are gone (empty: the faces exist but no longer meet)                                       |
| `ambiguous`     | a reference matches several faces or edges: `candidates` lists them, sorted                                                                                                    |
| `invalid`       | a malformed or out-of-range input, a hole that misses the bodies, a tool that misses its body, two references to one edge, a reference spanning two bodies, a repeated body id |
| `no-body`       | the feature needs a body (or the shape has no names)                                                                                                                           |
| `kernel`        | OCCT refused; `occtMessage` when it threw                                                                                                                                      |
| `invalid-shape` | OCCT returned a shape that fails `BRepCheck_Analyzer`, a shell or hollow it silently got wrong, or a closed hollow it could not make (with a hint)                             |
| `empty`         | a cut or intersection left nothing                                                                                                                                             |
| `unnamed`       | a result face no history named: never silently accepted                                                                                                                        |
| `unsupported`   | the feature cannot do this yet (a pattern or mirror of an intersecting feature)                                                                                                |

Every error carries `featureId`, `message`, and for references `ref` (the reference id, or the field: `extent`, `axis`, `plane`, `direction`) and `target` (the reference as a name). `resolved` lists every reference with its `via` and `fragile`.

`warnings` never fail the feature; each has a `code`:

- `reference`: a resolution that is not `exact` and non-fragile (`descendant`, `ancestor`, `ends`, `ordinal`, or any fragile resolution, including an exact match on a positional name), with the `ResolvedRef` fields;
- `missed`: subtracting pattern or mirror copies that do not touch the body, in `instances`;
- `direction`: a direction taken from a reference that no naming rule could orient (see Directions), where its sign matters;
- `detached`: added solids that touch no body in scope, which became bodies of their own, in `bodies`.

For the regen engine (#932), these codes map onto ADR 0007's first-cut `FeatureError` union as follows. The ADR's list was a first cut; the codes without a counterpart are kept as they are, and regen adds its own `expression` and `sketch` errors, which never come from the kernel.

| Kernel code     | ADR 0007 first cut    | Fields                                                               |
| --------------- | --------------------- | -------------------------------------------------------------------- |
| `lost`          | `reference-lost`      | `ref` becomes `referenceId`; `missing`                               |
| `ambiguous`     | `reference-ambiguous` | `ref` becomes `referenceId`; `candidates`                            |
| `unnamed`       | `unnamed-face`        | `message`                                                            |
| `kernel`        | `kernel`              | `message`, `occtMessage` (the ADR's `operation` is in the message)   |
| `invalid-shape` | none (kernel family)  | OCCT returned something wrong without failing; shown like `kernel`   |
| `invalid`       | none                  | a bad or out-of-range input; with `ref` when a reference is at fault |
| `no-body`       | none                  | the feature needs a body                                             |
| `empty`         | none                  | a cut or intersection removed everything                             |
| `unsupported`   | none                  | not implemented yet                                                  |

### Directions

Linear pattern directions, revolve axes and circular pattern axes can come from a reference. Which way such a direction points is chosen by names, never by the order OCCT stores faces and edges in, since an unrelated upstream edit (a sketch started at another corner, a through hole) reorders them. `orientedGeometry` (`src/features.ts`) applies these rules, and the `resolve` op reports geometry oriented the same way:

- a straight edge between two planar faces that are not parallel runs along `nA x nB`, the outward normals of its faces, A being the face whose name sorts first (by code unit): a block's top front edge, `extrude#1:cap:end|extrude#1:side:e1`, runs `+z x -y = +x`;
- any other straight edge (a seam, an edge on a curved face, between tangent faces) runs toward the end vertex of the first end face, by name, that touches only one end (end faces are at a vertex of the edge, not on it);
- a circle edge's normal points toward the first of its faces, by name, whose centroid lies off the circle's plane;
- a cylinder's or cone's axis points toward the first neighbouring face, by name, at one of its ends: every vertex and midpoint of the edges the neighbour shares with the face lies on one side of the plane through the face's centroid square to the axis. A hole wall's axis points toward whichever of its rim faces sorts first; a fillet round's toward the first of the faces at its ends. The faces a round is tangent to run its whole length and never decide, since their centroids move with unrelated edits (a boss on the top face); with no end neighbour, the `direction` warning applies;
- a plane's normal is its outward normal.

`flip: true` on the reference (`{ ref, flip }`, `{ edge, flip }`) turns the result round, so the user can pick the other way. A revolve has no separate `reverse`: it turns right-handed about its axis, so `flip` on an edge axis is how it goes the other way, and a model-space axis (a converted sketch line) is flipped by the caller negating its direction, which is what regen does for core's `sketchLine` `flip`. When no rule decides (every candidate is symmetric about the edge or face), OCCT's direction is used and, where the sign matters (a linear pattern, a partial-angle revolve or circular pattern), a `direction` warning says so.

For the UI and sketch placement: `resolveReferences` (the `resolve` op) gives each stored reference's resolution and geometry, `pickReference` (the `pick` op) the reference to store for a click, and `sketchFrame(kernel, body, faceRef)` the deterministic sketch frame on a planar face (origin: the world origin projected onto the plane; x: world X projected, or world Y when the face faces X).

### Mate connectors

`connectorFrame(kernel, body, origin, inference)` (the `connector` op, `src/features.ts`) is the frame of an assembly's mate connector (M2 plan, T2.3c) on a named body, in the body's coordinates. `origin` is a `FaceRef`, an `EdgeRef` or a `VertexRef` (`{ faces, ordinal? }`: the sorted names of the faces around a vertex, as `vertexName` joins them); `inference` picks the point on it and says which kind `origin` is, so an edge and a vertex, both written as faces, are never told apart by shape. z follows the geometry's direction as the features orient it (see Directions); x is world X projected square to z, or world Y when z runs along X, as for `sketchFrame`; y is z x x.

| Inference  | On                            | Origin                                        | z                                                                                                                                                 |
| ---------- | ----------------------------- | --------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| `centroid` | a face                        | the face's centroid                           | a plane's outward normal; a cylinder's or cone's oriented axis                                                                                    |
| `centre`   | a circular edge               | the circle's centre                           | the outward normal of a planar face of the edge square to the circle (the first by name), so a hole's rim points out of the face it is drilled in |
| `centre`   | a cylindrical or conical face | the axis at the height of the face's centroid | the oriented axis                                                                                                                                 |
| `centre`   | a spherical face              | the sphere's centre                           | world Z (the world axes)                                                                                                                          |
| `midpoint` | an edge                       | the middle of the edge                        | a straight edge's oriented direction; a circular edge's z as for `centre`                                                                         |
| `vertex`   | a vertex                      | the vertex                                    | world Z (the world axes)                                                                                                                          |

A circular edge with no planar face square to it takes the circle's normal as Directions orients it. Anything no rule orients (a spline face's centroid, an ellipse's midpoint, a cylinder no neighbour orients) takes OCCT's direction or the world axes and reports `oriented: false`, which regen turns into a `direction` warning; `flip` on the connector turns it round. A `centre` on something without one (a plane, a straight edge) and an origin of the wrong kind for its inference are `unsuitable`.

The report is `{ ok: true, frame, kind, index, via, fragile, oriented }`, or `{ ok: false, status, message }` with `status` `lost` (with `missing`), `ambiguous` (with `candidates`), `unsuitable` or `no-body`. It never throws for a reference that does not resolve, and the `connector` op answers one report per connector, so one lost connector fails nothing else. Faces and edges resolve like feature references (`exact`, `descendant`, `ancestor`, `ends`, `ordinal`); a vertex (`resolveVertex`) by exact face names, then by faces descending from them, with `ordinal` (by position, always fragile) only choosing among several; one whose faces all exist but no longer meet is `lost` with nothing `missing`. `pickVertex(names, topology, index)` gives the `VertexRef` a click on a vertex is stored as, with an ordinal only when another vertex has the same faces.

### Several regions

A `SketchProfile` is either one region, `{ frame, loops }` (the outer loop, then its holes), or several, `{ frame, regions: [{ loops }, ...] }`, each region with its own holes (`profileRegions(profile)` gives the loops of each). Extrude and revolve take either (text needs many regions, each glyph with its holes; M3 plan, T3.2a). An edge id is unique within a region; two regions may share one, which is the edge between adjacent sketch regions.

- **Building.** Every region is profiled and swept on its own, then joined into one tool, which combines with the bodies by `mode` like any other. Regions whose solids' bounding boxes meet (adjacent regions, glyphs that touch after kerning, a revolve whose regions sweep through each other) are fused in one boolean per group, with `SimplifyResult`, so coplanar faces that run across regions become one face and the walls between adjacent regions disappear; groups that meet nothing stay apart and are gathered in a compound with no boolean. A `new` feature of separate regions is one body of several solids. An extrude's `draft` is applied once per group, after its regions are fused, on every face that is not a cap: drafting each region's prism before the fuse would tilt the wall two adjacent regions share in opposite ways, leaving a V-groove and two solids. So adjacent and overlapping regions taper as the outline of their union, and separate ones each on their own. A draft can grow separate groups into each other: a negative draft leans every side out, and with a `symmetric` extent the half below the sketch plane (the neutral plane) leans out under a positive draft. So with more than one group the drafted groups are grouped by bounding box and fused again, the same way as the undrafted regions: groups that collide become one valid solid with the volume of their union (their sides cut back to where they meet), and groups that stay apart are gathered in a compound as before.
- **Adding.** The joined tool is one shape, so an `add` fuses all of it into the body it meets: regions that do not touch the body are not `detached` bodies of their own but extra solids of the touched body (an `add` of two regions, one on a block and one beside it, is one body of two solids). Use `new` for regions that should be bodies of their own.
- **Naming.** One region is named as before. With several, the regions are numbered from 1 by `sweepRegionOrder`: by the sorted edge ids of each region's outer loop, compared as lists by code unit, then by all of its edge ids, then by input order. Region k's caps are `<id>:cap:start#k` and `<id>:cap:end#k`, whose lineage holds `<id>:cap:start` and `<id>:cap:end`; sides are `<id>:side:<edge id>` as for one region. The numbers come from edge ids, not positions, so moving or resizing a region keeps them, and the order regen passes the regions in changes nothing; adding or removing a region, or rebuilding one from other edges, can renumber the rest, so the `#k` caps are positional and fragile (a reference resolves with a warning). A reference to the plain `<id>:cap:end` finds region k's cap as a descendant while it is the only one, and is ambiguous otherwise. Faces fused across regions merge as `(A+B)` (the full top of a ring and the disk filling its hole is `(extrude#1:cap:end#1+extrude#1:cap:end#2)`); a cap split by an overlap gets `#k` pieces by position, as any split.
- **Cost.** Measured in `test/regions.test.ts` on the Node kernel: 50 small glyph-like regions (a square with a square hole each, 0.6 mm deep) take roughly 0.3 to 0.5 s either way on a desktop machine, whether apart (50 sweeps and a compound, no boolean) or each overlapping its neighbour (one fuse of ten per row); the figures vary with the machine and are logged by the test, not asserted. The sweeps dominate; a paragraph of text costs in proportion to its glyphs, and only touching glyphs pay for a boolean.

### Naming

`src/naming.ts` is the production naming layer of the T0.5 scheme ([report](../../docs/spikes/T0.5-topo-naming.md), naming scheme version 1 in ADR 0004), ported from `spikes/topo-naming`: faces named at birth and carried by kinded history (kept and `Modified` inherit, one input in several faces gives `#k` pieces by centroid, several inputs in one face merge as `(A+B)`), lineage for descendant matching, edges named by their adjacent faces with end faces and a positional ordinal only when needed, references resolved `exact`, then `descendant`, then `ancestor`, with `ends` and `ordinal` only choosing among candidates, and `lost` / `ambiguous` failures. What the features add:

- **Faces generated from a face** (a shell's walls, OCCT's draft) are named by the feature when it has a name for them; otherwise, when the input face was neither kept nor modified, they replace it and inherit its name.
- **Faces generated from edges or vertices**: a referenced edge gives `<id>:round:<ref id>` (`bevel` for chamfers); an edge OCCT added to the blend along a tangent chain gives `<id>:round:A&B`, after the two faces of the edge it replaced; a vertex gives a corner blend `<id>:corner:A&B&C` (exercised by a three-edge fillet).
- **No duplicates.** Faces that still share a name are numbered by position, fragile.
- **Unnamed faces are errors.** A face no history reached gets the placeholder `?faceN`, the feature fails with `unnamed`, and a placeholder can never be picked, stored or resolved (a reference to one is `lost`). `?` is reserved in ids, so any name containing it counts as a placeholder, however a feature wrapped it (`shell#2:offset:?face3`, `hole#2:?face3`); every step of a feature carries its unnamed faces through (a draft, an outward hollow), and the result's names are checked for placeholders as well.
- **Instances.** A pattern instance is `<pattern>:i<k>/<source name>`, a mirror image `<mirror>:image/<source name>`. Their lineage is prefixed too and never contains the source names, so a reference to the source never finds a copy, and a copy can be referenced like any face (`{ faces: [top, 'pattern#3:i2/extrude#2:side:c1'] }`).
- **Nested positional names.** `splitParent` reads a trailing `#<digits>` as a kernel split. In a corner name whose last component is a piece (`fillet#3:corner:A&B&C#2`, where `C#2` is a piece of `C`) that reading is ambiguous: the "parent" `fillet#3:corner:A&B&C` is the same corner round the whole `C`, which is the right face when `C` became whole again, and such a resolution is always `fragile`, so it warns.
- **Sketch region pieces.** Region edge ids `e2#1` are positional: their faces are fragile, and `e2` is their ancestor, so a reference to `side:e2` finds `side:e2#1` as a descendant.
- **Caps of several regions** are `<id>:cap:start#k` and `<id>:cap:end#k`, k from `sweepRegionOrder` (see Several regions): positional pieces of the plain cap names.

### STEP exchange

`Kernel.exportStep(bodies)` (the `exportStep` op, `src/exchange.ts`) writes one AP214 STEP file (`AUTOMOTIVE_DESIGN` schema, lengths in millimetres) with every body a top-level product of its name; `Kernel.importStep(data)` (the `importStep` op) reads one with `STEPControl_Reader` into a new shape. OCCT's translators only work on files, so both go through the instance's in-memory file system (a scratch file in MEMFS, removed on every path, a write that fails part way included).

Names need XCAF. The plain `STEPControl_Writer` names every product `Open CASCADE STEP translator 8.0 <n>`, so export builds an XCAF document (`TDocStd_Document`, `XCAFDoc_ShapeTool.AddShape`, a `TDataStd_Name` per body) and writes it with `STEPCAFControl_Writer`. What libcascade 3.0.2 binds for this, checked:

- `STEPControl_Writer` and `STEPControl_Reader`: bound and working (`Transfer`, `Write`, `ReadFile`, `TransferRoots`, `OneShape`).
- `STEPCAFControl_Writer` and `STEPCAFControl_Reader`, `XCAFApp_Application.GetApplication().InitDocument`, `XCAFDoc_DocumentTool.ShapeTool`, `TDataStd_Name.Set`: bound and working; names round-trip through `STEPCAFControl_Reader` too.
- **Trap:** `STEPCAFControl_Writer.Transfer(doc, mode, multi, progress)` binds `multi` (a `const char*` that must be null for one file) as `std::string`, so it can never be null, and an empty string turns on external references: one file per body plus an assembly file. `Perform(doc, path, progress)` passes null inside OCCT and writes one self-contained file; it is what export uses.
- Reading a name back from a `TDataStd_Name` needs `TCollection_ExtendedString.ToExtString`, which is not usable (unbound type). Product names are read from the file text instead (`@manufakture/io`'s `stepProductNames`).
- AP242 would need `Interface_Static.SetCVal("write.step.schema", ...)`; export stays on OCCT's default, AP214, which is the older and more widely read of the two.

**Assemblies.** With `assembly` (`StepAssemblyLayout`: a `name`, `parts` naming their bodies by index in `bodies`, and `instances` naming a part with a `pose`, a unit quaternion and a translation), `exportStep` writes an assembly (`writeStepAssembly`): every part once, however many instances show it, and every instance a located component of a top-level assembly product. A part of one body is a product of the part's name; a part of several bodies is a sub-assembly of that name whose components are its bodies, unmoved, each a product of the body's name. In the file that is one `PRODUCT` per part (and per body of a multi-body part) and one `NEXT_ASSEMBLY_USAGE_OCCURRENCE`, named after the instance, per instance, with its placement; a CAD program sees one part placed twice, not two copies. What libcascade 3.0.2 binds for this, checked first (the fallback, one transformed product per instance, was not needed): `XCAFDoc_ShapeTool.NewShape`, `AddComponent(assembly, label, TopLoc_Location)` and `UpdateAssemblies`, `gp_Quaternion`, `gp_Trsf.SetRotation` and `SetTranslationPart`, `TopLoc_Location(gp_Trsf)`; and for reading back, `STEPCAFControl_Reader.Transfer`, `GetFreeShapes`, `GetComponents`, `GetReferredShape`, `GetLocation` and `NbComponents`. All work. `stepAssemblyProblem` refuses, as `invalid-argument`, a layout with no parts or instances, a body in no part or in two, a part with no instance, an index out of range, an empty name or a pose that is not finite or not a unit quaternion.

The XCAF document's attributes hold the shapes, so the root label's attributes are forgotten (`ForgetAllAttributes`) before the wrappers are deleted; the reader's work session is cleared (`ClearShapes`, `WS().ClearData(1)`) on every path, failures included. Imported files come from outside, so `importStep` refuses an empty file, one over `MAX_STEP_BYTES` (64 MiB, checked before base64 text is decoded), text that is not STEP and a file with no shapes, each as `invalid-argument`; a truncated file and a header with no data are tested to fail cleanly and leave no embind object behind. `exchange.test.ts` round-trips the demo part (volume, area, face, edge and vertex counts, tight bounding box), checks the schema, unit and product names in the file, runs the `import` feature against a body, and checks with the embind tracker that export and import leave no live embind object behind. They do cost wasm heap: libcascade's empty destructors (ADR 0002) keep some of each cycle, measured at about 400 KB per export and 280 KB per import of the demo part. That growth is bounded by instance recycling, like every other operation's; the test checks it stays far below what a leaked file or model would add.

### Derived bodies

The **`derive` feature** (`applyFeature`, kind `derive`) brings bodies of another part into this one: a derived part's pinned source, which the regen engine builds first in the same kernel (`packages/regen`, "Derived parts"). `sources` are those bodies as `{ id, shape }`, their ids in the source; they are read, never changed, released or made bodies of this part. Each is copied by the placement (rotations about the fixed x, y and z axes through the origin, in that order, then the translation; the translation always runs, so a copy is a new shape even at the origin), and the copies combine with the bodies by `mode` and `scope` like an import's: `new` makes each a body `<id>:from/<source body id>`, `add` fuses them with the bodies they touch (a copy touching none is a detached body under the same id), and `subtract` and `intersect` use them as tools.

Names are carried through the transform's history, then prefixed by `derivedName`, in the form core's `featureIdsInName` reads (M2 plan, decision 6): everything after `<id>:from/` in a merge or corner member is a name in the source document, never a feature of this part. So a source name `A` becomes `derived#1:from/A`; a merged face `(A+B)` is one group and is prefixed once, `derived#1:from/(A+B)`; and a source corner, which has no brackets, has every member prefixed, `derived#1:from/fillet#3:corner:A&derived#1:from/B&derived#1:from/C`, so no member of it can be read as a local face. Lineage is prefixed the same way, so a reference to a source name never finds the copy and a derived face never matches a local face of the same source name. A nested derived name gains one more prefix. Edges are named from the prefixed faces, so a later fillet refers to `derived#1:from/extrude#1:side:e1|derived#1:from/extrude#1:side:e2`, and it resolves `exact` on every version of the source whose edge still exists: names come from the source's features, not from positions, and a source edit such as a thicker plate moves the edge without renaming it. A source that is not a live named shape fails the feature with `no-body` and `ref: 'sources'` (regen reads that as shapes lost to a recycle).

The **`import` feature** (`applyFeature`, kind `import`) reads the file and names every face `<id>:face:<n>` in the order `TopExp.MapShapes` gives for the file's shape. Imported topology has no history to carry names across edits of the file, so the names are positional: `isPositional` counts a name built on `import#k:face:<n>` as positional, every face and edge name is `fragile`, and a reference to one always resolves with a warning. `mode` combines the shape with the bodies like an extrusion's (`new` makes it a body of its own). A file OCCT cannot read fails the feature with `invalid`, passing the body through.

### Measure

`Kernel.measure(shape, targets, { body? })` (the `measure` op, `src/measure.ts`) measures the exact B-rep, never the mesh, in millimetres and radians. A target is a face, edge or vertex of the shape: by its name on a body made by feature operations (faces and edges by the naming layer's name, a vertex by `vertexName`, the sorted names of the faces around it joined by `&`), or by 1-based index (a body with no names, and the viewport's vertices, which have no mesh name slots). A target that is not on the shape, or whose name matches several, is reported in its `items` slot (`not-found`, `ambiguous`) and the others are still measured.

- **Per target**: a vertex's point; an edge's curve type, length, end points, midpoint, direction (lines) and centre, radius, axis and swept angle (circles and arcs); a face's surface type, area, centroid, outward normal (planes), axis and radius (cylinders, spheres, tori; cones get the axis).
- **Two targets**: `distance`, the minimum distance from `BRepExtrema_DistShapeShape` with its witness points `from` and `to` (when several pairs reach it, as between parallel faces, the pair nearest the middle of all of them), and `angle` when both have a direction: between two lines (line edges, cylinder and cone axes), two planes, or a line and a plane, always 0 to 90 degrees, plus for two planar faces the angle between their outward normals (0 to 180).
- **`body: true`**: volume, surface area, centre of mass (`BRepGProp`, uniform density) and a tight bounding box (`BRepBndLib.AddOptimal`, not enlarged by tolerances, unlike `properties`).

`BRepExtrema_DistShapeShape` holds both input shapes, so it is released before delete by loading null shapes into it (`releaseOwned`). `measure.test.ts` checks every value against geometry computed by hand.

### Oriented bounding box

`Kernel.orientedBox(shape, { optimal? })` (the `obb` op, `src/obb.ts`) sizes a body that is not a board for the cut list (M4 plan, T4.3b): the regen worker calls it on request for such bodies (T4.3d), never on every regen. It runs `BRepBndLib.AddOBB` on the exact geometry: no triangulation (a body already meshed is still bounded exactly) and no tolerances, in OCCT's optimal mode unless `optimal: false`. The tight axis-aligned box (`AddOptimal`) is computed as well and used instead, with `source: 'aabb'`, when it is tighter by more than 1e-9 of the volume, or when the OBB throws or comes back empty (an OCCT exception there is decoded and freed, not reported; a wasm trap still is). A shape with nothing to bound is `invalid-argument`.

The result is `{ center, axes, halfSizes, sizes, source }`, normalised so that it does not depend on the order OCCT picks: axes sorted by size, so `sizes` is length >= width >= thickness; the first two axes each signed so their largest component is positive (x, then y, breaks a tie); the third their cross product, so the frame is right-handed. Sizes equal to 1e-9 (a square section) are ordered by their axes, the one nearest world x first. An oriented box is not unique for a symmetric body (a cylinder's cross axes may turn freely about its axis), but its sizes are, and the sizes are what the cut list reads.

The goldens (`test/obb.test.ts`) hold sizes, centres and axes to 1e-6 mm: an axis-aligned box and a square bar, a 100 x 40 x 10 box turned 30 degrees about z (the same without the optimal mode, and after meshing), a box turned 40 degrees about an oblique axis, cylinders on z and on an oblique axis, and a 600 x 300 x 19 board with a dado, which still reports the blank's size, also standing turned in space. Cost: about 1 ms for these bodies. Like `measure`, each call leaves about 200 bytes of wasm heap behind, since libcascade's `delete()` is empty even for `Bnd_OBB`, `Bnd_Box`, `gp_XYZ` and `gp_Pnt`; instance recycling bounds it, and `leaks.test.ts` checks the bound and that no embind object is left.

### Interference

`Kernel.interference(items, options)` (the `interference` op, `src/interference.ts`) tells which items overlap and by how much (M2 plan, T2.3d). An item is one assembly instance: the bodies it shows (`shapes`, live ids in their own coordinates) at one `transform`, a `Placement` (`translation`, and `rotation` a unit quaternion `[x, y, z, w]`, core's `Pose`). Bodies of one item are never checked against each other.

1. **Placement.** Each body is placed as a located handle on the arena's shape (`TopoDS_Shape.Moved`), so nothing is copied, and two instances of one part share one B-rep.
2. **Prefilter.** The bounding box of every placed body (`BRepBndLib.Add`, enlarged by tolerances, so never too small), and per item their union. A pair of items is a candidate only when their boxes share more than `tolerance` of volume, and within it only the pairs of bodies whose boxes do reach a boolean: the common of two bodies can never exceed the box their boxes share. A grid of spaced instances therefore sends no boolean at all, and neither do boxes that only touch.
3. **Booleans.** `BRepAlgoAPI_Common` per candidate pair of bodies, non-destructive (the arena's shapes, shared by every instance, are never retouched) and without history; its volume from `BRepGProp`. A pair of items is reported when its commons add up to more than `tolerance` (default `DEFAULT_INTERFERENCE_TOLERANCE`, 1e-3 mm3), so touching bodies whose boxes do overlap (turned ones, say) are not reported either. With `mesh`, the commons of a reported pair are tessellated together, in world coordinates, name slots `UNNAMED`; the op's reply transfers them.
4. **Failures.** A boolean OCCT cannot compute is listed in `failures` for its pair (neither reported nor ruled out) and the check goes on; a wasm trap ends it as `fatal`.

`pairs` restricts the check to some item pairs, `[i, j]` in that order (default every pair, `i < j`); `prefilterOnly` stops after step 2, listing `candidates` with no boolean run. The regen engine uses both to stream results: the prefilter over every instance first, then one op per candidate pair, each its own batch, so a newer request cancels a check between two pairs. A bad placement (a zero quaternion, a translation that is not finite), a pair that does not name two items and a negative tolerance are `invalid-argument`. Every temporary of a pair (placements, boxes, builders, commons, the compound and its triangulation) is released before the next pair starts, on every path; `leaks.test.ts` checks it with the embind tracker and checks that 30 checks leave the heap where it was.

### Projection

`Kernel.project(items, view, options)` (the `project` op, `src/project.ts`) turns placed bodies and an orthographic view into the 2D geometry a drawing uses (M4 plan, T4.4b; the rules come from the [T4.4a spike](../../docs/spikes/T4.4a-hlr.md)). It makes no shapes.

- **Items** are `{ shape, transform?, key }`: a body, the `Placement` it sits at in the view (an assembly instance's pose, as for interference; absent: as it is) and the caller's name for it, echoed in `keys` in item order. Keys must be unique. Every edge carries `item`, its index.
- **View**: `direction` (from the viewer into the scene), `up` (on paper, not parallel to `direction`) and `origin?` (default the world origin; it only shifts the output). The frame is z = -direction, x = up x z, y = z x x; a point p lands at (dot(p - origin, x), dot(p - origin, y)). `viewFrame(view)` and `projectPoint(frame, p)` compute the same in plain TypeScript, equal to the HLR output within 1e-9 mm, so dimensions are projected without a kernel call. (`HLRAlgo_Projector.Project` on its own ignores the frame's origin; the HLR run does not.)
- **Algorithm**: OCCT's exact hidden-line removal (`HLRBRep_Algo`), with every item in ONE run, read back per item (`CompoundOfEdges(S, ...)`). Projecting items alone and merging loses the occlusion between them, and the poly algorithm draws hidden edges as visible where boards touch, so neither is offered (the plan's `algorithm: 'exact' | 'poly'` option is left out, as the spike recommends).
- **Classes**: `sharp`, `smooth` (tangent edges, `Rg1Line`), `sewn` (seams, `RgNLine`) and `outline` (silhouettes, not model edges), each `visible` or hidden. Options: `hidden` (default true; false does not even read them), `smooth` (default true), `sewn` (default false). A seam on a silhouette is reported once, as sharp; a tangent edge that projects onto a sharp one is dropped. Hidden lines lying exactly under visible ones are returned; the drawing drops them.
- **Curves** (`Curve2`, view coordinates, model mm): `line`; `arc` (centre, radius, `start` in [0, 2 pi) and `end > start`, counter-clockwise); `ellipseArc` (centre, `major >= minor`, `rotation` of the major axis, eccentric-anomaly `start` and `end`, counter-clockwise); `polyline` for anything else, within `deflection` (default 0.05 mm). A circle seen edge on comes back from OCCT as a B-spline: straight curves are tested and returned as lines. `bounds` is the exact 2D box of every returned edge and section loop (null when there are none); `boundsOf` and `endsOf` are exported for the drawing.
- **Sections**: `section: { origin, normal }` cuts every item first (a non-destructive `BRepAlgoAPI_Cut` with a box far larger than the items) and keeps the half space `dot(p - origin, normal) >= 0`: the normal is the direction of sight of the section, the way the arrows on a cutting-plane line point, so for a section seen in the view pass the view's `direction`. `sections` has one entry per item: its faces on the plane, each with its `outer` loop, its `holes` and its true `area`. A loop is a chain of curves, each meeting the next at one of its ends; lines and polylines run along the loop, arcs stay counter-clockwise. Loops are exact arcs and ellipse arcs when the plane faces the viewer, polylines otherwise. An item wholly on the removed side draws nothing and has no faces.
- **Errors**: a zero or non-finite direction, up or section normal, `up` parallel to `direction`, a repeated key, a bad placement or a deflection that is not positive are `invalid-argument`; an unknown shape is `unknown-shape`; a section cut OCCT cannot compute is `kernel`, naming the item.
- **Memory**: `HLRBRep_HLRToShape` keeps a handle on the algorithm and its destructor is empty, so `releaseOwned` removes every loaded shape from `HLRBRep_Algo` (`Remove(i)`) before `delete()`, and points are read with `D0` into one reused `gp_Pnt`. What stays is the small embind values whose `delete()` is empty: 58 KiB a projection of the 40-hole board's isometric view (about 370 edges), 621 KiB without the rule; `leaks.test.ts` bounds it at 150 KiB and checks that no embind object is left.

Time (from the spike, Node): about 1 ms for a box, 15 to 50 ms for a 7-board bookshelf, 42 to 96 ms for 100 boards, per view. Views are computed lazily in the regen worker (M4 plan, decision 8), never on every regen.

### Tools

The `tools` feature (`ToolsInput`, M4 plan T4.2a) cuts named primitives from, or adds them to, chosen bodies: what a joint of `domain-wood` translates to (a dado is one box cut from board A, a tenon boxes cut from B's end and a mortise box cut from A, a dowel a cylinder cut from each board, a pocket screw an angled stepped cylinder), so joints, and later M6's openings, need no kernel feature of their own. Each item is `{ id, body, mode, primitive }`, placed in model space:

- `box`: `frame` (`origin`, `xDir`, `normal`) and `size` `[x, y, z]`: the block from the frame's origin along x, y (`normal x xDir`) and the normal; a corner at the origin, not centred, and `xDir`'s component along the normal is dropped. Faces `xmin`, `xmax`, `ymin`, `ymax`, `zmin`, `zmax`, at the low and high end of each frame axis.
- `cylinder`: `axis` (from its origin along its direction), `radius`, `length`. Faces `start` (at the origin), `wall`, `end`. `step: { radius, length }` makes the first `length` wider (a counterbore, a pocket screw's body): faces `step` (its wall) and `shoulder` (the ring where it meets `wall`). `tip: { angle }` ends it in a drill point of that included angle past `length`, face `tip` instead of `end`.

A face a tool makes is named `<feature id>:<item id>:<role>` (`extension#7:t2:xmax`, `extension#7:t1:wall`), fixed by construction and never fragile, so a reference into a joint survives edits like any other name: the dado's floor still resolves `exact` after the board's width changes or the tool moves. Faces of the body keep their names through the boolean's history, as for an extrusion; faces a tool merges into one are `(A+B)`, like any merge (a tenon's shoulder, cut by four boxes fused first). The plan wrote the box roles `+x`, `-x`, ...: `+` is reserved in names (it joins the members of a merge, and `derivedName` and core's `featureIdsInName` split on it), so the roles are `xmin` .. `zmax`.

Items apply per body, bodies in creator order and each body's items in item order. Consecutive items of one mode form a run: the run's tools are fused where their boxes meet (gathered in a compound otherwise) and combined with the body in one boolean, so a body with only cuts (or only adds) sees one boolean however many tools a joint has. Bodies with no items keep their shape ids. An `add` item is tested against its body first (a fuse without history, counting solids), as `add` features are.

**Coplanar faces.** OCCT booleans are least reliable where a tool face lies in the plane of a body face (a dado flush with the board's top, a through dado's ends at its edges, a dowel hole's mouth). So a subtracting tool's flat face that lies in the plane of a planar body face facing the same way (within 1e-6 mm) is moved out by `TOOL_OVERLAP` (0.01 mm), once, here, rather than in each joint, provided the body has no material in the thin slab the face would sweep moving out (a `common` of the body with that slab is empty). The cut is the same; the moved face never reaches the result. A face that is only in the plane of a body face it does not meet (a blind hole ending at the height of a rabbet's floor, with material above it) stays put, so the hole keeps its depth. Added tools are not moved (an added block flush with a face would grow by the overlap).

**Errors.** Malformed input (no items, a tool id used twice, a bad primitive) is `invalid` for the whole feature, as are out-of-range sizes (`ref` the item id). An item whose body is not there is `lost` (`missing` the body id), and one that does not touch its body is `invalid` (`ref` the item id, `target` the body): those are per item, and the other items still apply, so the outcome has `ok: false` with those errors and the bodies the other items changed. A subtracting tool that only touches its body (its face merged into the body's) does not count as touching. A cut that leaves nothing of a body is `empty`, and an invalid result `invalid-shape`, for the whole feature. Like every boolean, a tools feature leaves part of its B-rep in libcascade's empty destructors: about 270 KiB (measured 269 KiB, the flush checks' slab booleans included) for two boards with a dado, a through dowel, a stepped and tipped hole and an added block (`leaks.test.ts`), which instance recycling bounds.

### Hole sizes

`HOLE_SIZES` (`src/holes.ts`), `holeSize(size)` and `clearanceDiameter(size, fit)` give clearance holes for metric M3 to M12 and inch #6 to 1/2" in close, normal and loose fits, with counterbore and countersink sizes. Metric clearances are ISO 273 (fine, medium, coarse; the same values as ASME B18.2.8's metric table), inch clearances ASME B18.2.8 (the nominal diameter of the drill it names). Both were checked against charts reproducing the standards, not the standard texts. Counterbore and countersink sizes (socket head cap screws, ISO 4762 / ASME B18.3; flat heads 90 degrees ISO 10642, 82 degrees inch) are not verified and are marked so per size (`verified`).

### Threads

`THREAD_SIZES` (`src/threads.ts`) and `threadSize(system, size)` give ISO metric coarse threads M2 to M20 (ISO 261's first choice, plus the second-choice M3.5, M14 and M18) and UNC #4 to 1/2" (ASME B1.1; `1/4` and `1/4-20` name the same size), each with its basic major, pitch and minor diameters and a tap drill (ISO 2306's for metric, D - P rounded to a stock drill; the usual 75% drill for UNC, with its name). Diameters come from the basic profile (ISO 68-1: H = sqrt(3)/2 P, D2 = D - 0.649519 P, D1 = D - 1.082532 P, the same 60 degree profile for UN). They were checked against charts reproducing ISO 724 and ASME B1.1, not the standard texts; the sources are listed in the file, and `threads.test.ts` holds the charts' values.

A modelled thread is a feature on a cylinder (M3 plan, decision 9) whose geometry the caller resolves: the `thread` feature takes a `ThreadGeometry` (the cylinder's axis, from where the thread starts and along it, its `radius` and `side`; the standard's `major` diameter and `pitch`; `length`, `hand`, a radial `clearance`, how each end is finished, and a `phase`). The thread feature of core (M3 plan, T3.2f) uses the other form, `ThreadFaceInput`: a picked cylindrical `face` (and optionally a circular `start` edge), `length` (or `full`), the standard's `major`, `pitch` and `tapDrill`, `hand`, the radial `clearance` and a `representation`. The kernel resolves the rest from the face: the side (a hole gets an internal thread), the radius, the axis and extent; it starts at the `start` edge's end, or at the end `orientedGeometry` points the axis to; it chamfers an end where the cylinder ends freely (its neighbours there are flat faces facing away from it) and closes any other end; and it sets the phase from where the start lies on the axis line, so coaxial threads of one pitch and hand mate wherever each starts. It acts on the body owning the face only (the geometry form cuts every body in scope, a coaxial one too). A radius outside `threadLimits` fails with `invalid` on `face`, naming the range. `cosmetic` builds no thread: the whole face is resized to the tap drill (internal) or the major diameter less twice the clearance (external) by a tube or cylinder cut or added along it, named `<id>:thread:cosmetic`, `cosmetic-start`, `cosmetic-end`. Either way, the outcome's `thread` (`ThreadReport`) says what was built, for display. The kernel-level API is `threadSolid(kernel, id, geometry)`: the tools of the thread with their faces named, which the feature subtracts in one boolean per body and then checks with `BRepCheck_Analyzer`. `threadProblem` says why a geometry cannot be built (the feature fails with `invalid`), and `threadLimits(side, major, pitch, clearance)` gives the cylinder radii a thread can be cut into, for regen's range message.

- **The profile.** A thread is cut as a helical groove: from a shaft (external) or a hole (internal). The groove is the space between the basic profile's teeth: P/4 wide at the root of an external thread, at the minor diameter, P/8 at the root of an internal one, at the major diameter, with 30 degree flanks, and it reaches 0.05 P past the crest. `clearance` moves the whole profile away from the mating part (an external one inward, an internal one outward), so two mating threads with clearance c each are c apart on the flanks in the axial section (2 c sin 30 degrees) and 2 c at crest and root. In space the flank gap is slightly less, since a helical flank leans with the helix: c / sqrt(1 + 3/4 (k / r)^2) with k = P / 2 pi, 0.1498 mm for c = 0.15 on M6 (the fit golden checks it). The crest is the cylinder's own face, kept or modified by the cut, so it keeps its name (`Naming`). When the cylinder lies beyond the crest the standard allows with the clearance (a shaft at the nominal diameter with a clearance, a hole smaller than the minor diameter plus the clearance), a revolved crest trim cuts it to that radius in the same boolean, and the new crest is the thread's `crest` face. A cylinder within 0.01 mm of that radius is left alone (a hole drilled at ISO 724's rounded minor diameter, 4.917 mm for M6, is 0.0003 mm under the exact one), since a thinner trim would only leave a sliver.
- **Ends.** `open`: the groove and tools run one pitch past the end, which must be a free end of the cylinder. `chamfer` (the default start): open, plus a 45 degree cone from the root diameter at the end plane, so the first turn has no feather edge and prints. `closed` (the default end): the groove stops with its whole width inside the length, ending in a flat face, and the cylinder may go on.
- **The helix.** Right-handed about the axis direction (left with `hand: 'left'`). At the start, an external thread's groove is centred at angle `phase` from the reference direction (world X projected square to the axis, world Y when the axis runs along X), an internal thread's half a turn further round, and the centre line rises one pitch per turn. So an external and an internal thread on one axis with the same start and phase mate.
- **Names.** Every face of the tools is named `<id>:thread:<part>`; the groove's parts come per turn and carry the turn, counted from the start (`thread#5:thread:root:3`, turn 0 being the run-in before an open start). Turn numbers are fixed by construction, so the names are not fragile, and lengthening or shortening a thread keeps the name of every turn before the end. A per-turn name descends from its turnless name. Parts: `root`, `flank-a` (the groove's side toward the start), `flank-b`, `opening`, `start` and `end` (a closed groove's ends), `crest` and the crest trim's `crest-start`, `crest-end` (shoulders at closed ends) and `crest-outer`, `chamfer-start`, `chamfer-end` and their tools' `-outer` and `-back` faces. `opening` and the `-outer` and `-back` faces lie outside the material and never reach a result; a face whose name contains `:thread:` is a thread face (T3.1c's rule). Faces the cut splits are numbered like any split (`#k` by position, fragile): the crest trim's cylinder comes back as one piece per turn (OCCT cuts the helical strip at its seam), a chamfer's cone as one or two, and the cylinder's own crest strips likewise (`extrude#1:side:c1#4`). The groove's per-turn faces are whole turns of their own and were never split in the goldens.
- **Which thread faces are cylinders** (T3.1c's thread rule needs one): the `root` of every turn is a cylinder on the thread's axis (and so is `crest`, when a trim made one). The flanks are B-spline surfaces, a chamfer a cone, a closed end a plane. The golden for an internal M5 cut into a hole at the minor diameter records it: `root:0` (the run-in) to `root:10` are the cylindrical thread faces, at the major radius; the crest strips are cylinders at the minor radius named after the hole.

How the groove is built, and what failed first:

- **What works**: the groove is built face by face, one piece per turn. Each piece has a band on the root cylinder and one on the opening cylinder, each a `Geom_CylindricalSurface` of its own whose frame is turned and lifted to the piece's start (so the band's parameters lie within one period), bounded by helices made as `Geom2d_Line`s on the surface (`BRepBuilderAPI_MakeEdge(Geom2d_Curve, Geom_Surface)`, then `BRepLib.BuildCurves3d`); the flanks are ruled faces between the root and opening helices (`BRepFill.Face`), which is the helicoid of the straight flank swept along the helix up to the helix approximation; two planar faces close the ends. `BRepBuilderAPI_Sewing`, `MakeSolid` and `BRepLib.OrientClosedSolid` make the solid. Volumes agree with the profile reference to about 3e-7. A piece shorter than a tenth of a turn at the end is merged with the turn before it (the two then share their span).
- **One band per cylinder over every turn** (the same construction without pieces) gives a valid groove, but a boolean that crosses it with a plane (a shaft's end face, a block's face) returned an empty solid, or left the body uncut, with no error and a result OCCT called valid. The bands' parameters span several periods of the cylinder, which the boolean's face splitting does not handle.
- **`BRepOffsetAPI_MakePipeShell`** along a helical spine with a fixed binormal (the plan's first option) sweeps a valid groove in 20 ms, but it fails the same way: 10 turns cut from a shaft through its end faces came back empty. Its faces are all B-spline surfaces as well, so no thread face would be a cylinder. A `ThruSections` loft would have the same B-spline faces; it was not tried.

Time: an M6 x 20 mm internal thread with chamfered ends in a block takes about 1 s (0.2 s for the tools, the rest the boolean); the golden's budget is 4 s. A sweep of every size in the tables, external and internal, both hands, four pairs of ends (chamfer and closed, open and open, closed and closed, chamfer and chamfer) and clearances 0 and 0.15 mm (800 threads, each 1.5 times the diameter long) built, cut and checked valid, with unique names and a cylindrical thread face every time (run by hand, not part of the suite); the slowest took about 2 s with ten such sweeps running side by side. Like every boolean, a thread leaves part of its B-rep behind in libcascade's empty destructors, about 0.65 MB for an M3 x 4 mm thread in a block (0.2 MB of it the tools, 0.3 MB the cut), which instance recycling bounds; `leaks.test.ts` checks that no embind object is left and measures the heap per thread on fresh instances. Measuring it found that `BRepCheck_Analyzer` kept a result per sub-shape, about 1 MB per check of a threaded body, on every `isValid` and `properties`: it is now re-initialised on an empty compound before delete (`releaseOwned`).

### Known-hard cases

OCCT refuses many fillets and shells, and some it gets wrong without saying so. `features.test.ts` keeps a corpus that must fail cleanly (a per-feature error, the body passed through, nothing left in the arena): a fillet wider than the faces beside its edge, a fillet taller than the block, an oversize chamfer, a fillet on a 0.2 mm step. Two shells OCCT gets wrong silently: a wall thicker than half the part, and removing every face, both come back as the unchanged solid, reported valid. The shell feature rejects removing every face up front, and checks that every kept face grew a wall and that the volume changed, failing with `invalid-shape` otherwise.

Closed hollows of filleted L-brackets are in the corpus too, at 0.5 and 3 mm, inward and outward; they must be exactly right or fail cleanly. Outward, OCCT's offset of such a body came back as a hollow reported ok that was only the enlarged offset (the cut of the body from it left it untouched), or at 3 mm a collapsed sliver of a few mm3. `hollow` therefore checks that the offset grew (inward: shrank) the volume, that its bounding box contains the body's (inward: fits inside it), and that the result's volume is the difference of the two, failing with `invalid-shape` otherwise. With the OCCT build in use all eight of these bracket hollows fail: outward mostly on these checks (one offset throws), inward in OCCT's offset or cut. An offset or cut that throws is reported as `invalid-shape` too, not a bare `kernel` error, with OCCT's message and a hint (another wall thickness, or hollowing before filleting). Closed hollows are only reliable on bodies without fillets for now.

### Topology

`topology(shape)` lists every face, edge and vertex with the facts naming, picking and the print checks need (ADR 0007, decision 9). A face (`FaceInfo`) has its surface type, area and centroid, and:

- a plane: `normal`, the outward normal, corrected for reversed faces and left-handed (mirrored) frames;
- a cylinder: `radius`, `axis` (a unit direction), `axisOrigin` (a point on the axis, the location of the cylinder's frame) and `hole`. The **sign of `axis` carries no meaning**: it is the direction OCCT stores, so two faces of one hole (split by a slot) may point opposite ways, and a mirrored copy may flip it. Compare axes as lines (`|dot|`, and the distance of one `axisOrigin` from the other's line). `hole` is the field to read for the side: true when the face's outward normal points toward the axis (material outside the cylinder, a hole), false when it points away (a pin or boss). It is computed from the surface at the middle of the face's parameter range, its normal `D1U x D1V` flipped for a reversed face and compared with the direction from the axis, which also covers left-handed frames;
- any other surface: `normal`, `axis`, `radius`, `axisOrigin` and `hole` are `null`.

`axisOrigin` and `hole` (T3.1c) are optional in the type so that `FaceInfo` values built by hand before them stay valid; `topology()` always sets both.

### History

Topology-changing ops return a `HistoryEntry` for every face, edge and vertex of every operand (operand 0 is the shape or profile, 1.. the tools), with `kept`, `modified` and `generated` as kinded `{ kind, index }` result references, sorted faces, edges, vertices, then by index (ADR 0007, decision 9). `deleted` is informational: fillet's `IsDeleted` is wrong for untouched edges, so naming must never use it. History is collected by default; `history: false` skips it. All indices are 1-based in `TopExp.MapShapes` order and valid for one shape only.

## Replies

```ts
interface BatchReply {
  generation: number; // echoed
  instance: number; // kernel instance; increases with every recycle
  status: 'done' | 'cancelled';
  results: OpResult[]; // one per op; empty when cancelled
  completedOps: number;
  names: string[]; // name table for the meshes' name slots
  heapBytes: number;
  shapeCount: number;
  ms: number;
  recycle: RecycleReason | null; // a recycle runs right after this reply
}
```

### Errors are data

Nothing an op does throws through the worker boundary (ADR 0007, decision 5). A failed op has `{ ok: false, error: KernelFailure }` and the rest of the batch still runs; ops that depend on it fail with `dependency`.

| `code`             | Meaning                                                                                            |
| ------------------ | -------------------------------------------------------------------------------------------------- |
| `kernel`           | OCCT failed; `occtType` and `occtMessage` carry the decoded OCCT exception when there is one       |
| `invalid-op`       | malformed op: unknown name, wrong types, a `{ result }` that is not an earlier op or made no shape |
| `invalid-argument` | well formed but out of range: zero size, open loop, missing edge, zero-length extrusion            |
| `unknown-shape`    | the id is not live: released, never issued, or from before a recycle                               |
| `dependency`       | an input is the result of an op that failed                                                        |
| `fatal`            | the wasm instance trapped; the rest of the batch fails and the instance is recycled                |

Every failure has `operation` and `message`, and `featureId` when the op had one. Only a malformed envelope (not an object, no integer `generation`, no `ops` array) rejects: that is a programming error.

### Meshes

Per body, fresh typed arrays, all transferred (never copied, the worker keeps nothing):

- `positions`, `normals` (`Float32Array`, xyz per vertex, vertices not shared between faces, normals outward), `indices` (`Uint32Array`, counter-clockwise from outside);
- `faceRanges` (`[firstIndex, indexCount]` per face, three.js group layout) and `triangleFaces` (1-based face index per triangle);
- `edgePositions` (xyz per polyline point) and `edgeRanges` (`[firstPoint, pointCount]` per edge). Edge points are taken from the polygon BRepMesh stored on the triangulation, so they are exactly mesh nodes; degenerate edges have no points;
- `faceNames`, `faceFragile`, `edgeNames`, `edgeFragile`: the name slots of ADR 0007 decision 7.

Face `i` is slot `i - 1` of every per-face array, edge `i` slot `i - 1` of every per-edge array: the same numbering as history and topology. Tessellating a body made by `feature` ops fills every slot from the body's names through the batch's `NameTable` (`applyNames`), and the reply carries `table.names` once; raw shapes keep `UNNAMED` slots. `faceNameOfTriangle` is the picking lookup (decision 8: picking returns a name); for an edge, or to store a reference, send a `pick` op.

## Cancellation

Generation numbers, as ADR 0007 decision 4 decides. Every request carries a `generation` that increases with every edit. A batch is abandoned when a request with a higher generation arrives before it finishes, or when `cancel(g)` covers it; batches with equal generations do not cancel each other and run in submission order. Batches never run concurrently.

An OCCT call cannot be interrupted, so the unit of cancellation is one op: the batch yields to the event loop between ops (a macrotask, not `setTimeout`, which browsers clamp), which is what lets a newer request or a `cancel` message be received at all while a batch runs. A cancelled batch releases every shape it made and replies `status: 'cancelled'` with no results; that includes a newer request that arrives during the last op, which the batch sees at one more yield after it. On the main thread, `KernelClient.submit` resolves to `null` for a reply that a newer submit has superseded. When such a reply had finished (the newer submit came while it travelled back), the client releases the shapes it kept through the worker's `release(shapes)`, which is not a batch: it runs after whatever is queued, is never cancelled and does not count as a newer request, so the next edit (during a drag there always is one) cannot cancel it and leak the shapes. Callers releasing shapes they kept themselves use the same path, `KernelClient.release(shapes)`, and never a `release` batch, which the next edit's cancel could drop. A batch at a stale generation is cancelled even when it is empty. A batch cancelled after its last op has run every op, so its `release` ops have taken effect although the reply carries no results. A `release` op on a lost kernel fails as `fatal`, like every other op.

Terminating the worker is the last resort for a single op that never returns: `KernelClient.restart()` terminates and respawns it, resolves pending submits to `null`, and every shape id is gone; the `onRestarted` option is called once the new worker is ready, so the owner can replay its document. It is not the normal cancellation path because it costs a new instance (0.3 to 0.4 s) plus a replay.

## Shape handles and leaks

Shapes live in an arena in the worker and cross the API as integer `ShapeId`s; no OCCT object leaves the package. Ids are never reused, not even across a recycle. Callers release explicitly (`release` op, `Kernel.release`, `checkpoint` / `releaseSince`).

- Every live shape records the op, `featureId` and `generation` that made it; `leaks()` (client and service) lists them oldest first.
- With `debug: true` (a `KernelServiceConfig` passed to `spawnKernelWorker({ config })` or `init`) shapes also record their creation stack, and a `leak-warning` status is emitted once when more than `maxLiveShapes` (default 10,000) are live.
- Every temporary OCCT object is owned by a scope and released before `delete()` (T0.2's rules: `Nullify`, `Clear`, `Reset`, empty argument lists, `BRepTools.Clean` after meshing, an empty compound for `BRepCheck_Analyzer`), including on every error path. `leaks.test.ts` proves it with the embind tracker, and checks that 30 regens of a small part leave the heap at its initial size.

## Recycling

libcascade's empty destructors leak on every regen, and a `WebAssembly.Memory` never shrinks, so the instance is recycled (ADR 0002, decision 5):

- after a batch, when the heap exceeds `heapThresholdBytes` (default 1 GiB) and no other batch is queued (an idle point);
- after a wasm trap (`WebAssembly.RuntimeError`), always;
- on request (`recycle()`).

A recycle drops the old instance without touching it, creates a new one from the cached `WebAssembly.Module` (no refetch, no recompile), and runs the replay hooks registered with `KernelService.onRecycle(hook)`; the regen engine will register one to replay the document. Status events `recycling`, `loading` (instantiate, init, ready) and `recycled` (with heap before and after, lost shapes and hook errors) go to subscribers. The reply of the batch that triggered it says `recycle: <reason>`, and the recycle runs before the next batch, including batches that were already queued when the trap happened.

## Deviations from the ADRs

- **Op batches here, `regen` in the regen worker.** ADR 0007 decision 3 has one `regen` call per user intent. This worker exposes the plumbing under it: batches of kernel ops with in-batch references, including one `feature` op per part feature. `regen` is added on top of `KernelService` by the regen worker (`packages/regen`, `createRegenWorkerApi`), without changing the protocol rules (generations, errors as data, transfer).
- **API surface.** Implemented from ADR 0001: `release`, `checkpoint`, `releaseSince`, `shapeCount`, `heapBytes`, `box`, `cylinder`, `profile`, `extrude`, `revolve`, `boolean`, `fillet`, `chamfer`, `count`, `mesh`, `exportStep`, plus `shell`, `offset`, `draft`, `transform`, `compound`, `geometry`, `importStep`, `interference`. Not yet: `describe`. `exportStl` is not a kernel call: STL and 3MF are written from `mesh` output by `@manufakture/io`, which welds and checks the mesh. `volume` and `boundingBox` are one `properties()` query; `adjacentFaces` is covered by `topology()`. `profile` takes a `Frame` (origin, xDir, normal) as its plane.
- **The `feature` op reply carries every name.** Each body of `FeatureOutcome.bodies` holds its whole name table: every face with its lineage and every edge, unchanged bodies included. That is more than the UI needs per edit (it needs the mesh name slots, and lineage only to resolve references, which happens in the worker). Slimming it (names of the new body only, lineage on demand) is left to the regen engine (#932), which decides what a `regen` reply carries.
- **Interference items are instances, not bodies.** The M2 plan describes the op's items as `{ shape, transform }`; an item here is `{ shapes, transform }`, every body an instance shows at one placement, so a pair is a pair of instances (its volume summed over their bodies) and the bodies of one instance are not checked against each other. Two bodies of one instance that overlap each other and a third instance count that region twice.
- **Up to face** extrudes to the plane of a planar face (the face's own boundary does not limit it), and only planar faces are accepted.
- **`KernelError`** carries a `code` (the table above), `occtMessage` and `featureId` besides ADR 0001's `operation` and `occtType`.
- **Mesh layout.** ADR 0007 left the edge polyline layout to this task: `edgePositions` plus `edgeRanges`. `triangleFaces` is added next to `faceRanges`. Name slots are `UNNAMED` until the naming layer fills them.
- **History by default.** ADR 0001 has `history?: boolean`; ADR 0007 requires history from every topology-changing op, so it is on unless `history: false`.
- **Topology and mesh extraction go through embind**, not C++ helpers (ADR 0002, decision 3); the API is shaped so that the custom build can replace them.
- **No solver port.** The regen worker runs the sketch solver in-process instead of on a `MessageChannel` port to the solver worker (ADR 0007 decision 2, amended; the reasons are in the regen README). The replay after a recycle is the app's: it regenerates the document when it hears the `recycled` status.
