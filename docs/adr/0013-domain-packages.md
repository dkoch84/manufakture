# 0013: Domain packages: extension features that make bodies, namespaced domain data, a generic takeoff

- Status: accepted, amended 2026-10-08
- Date: 2026-10-02

## Context

M4 makes manufakture useful for woodworking: boards cut from real stock, joinery, cut lists, sheet layouts and drawings ([M4 plan](../plans/m4.md)). M6 (construction) follows the same path with walls, openings, floors, roofs and a lumber takeoff ([M6 plan](../plans/m6.md), decisions 1, 2 and 10). Both are domains: vocabularies and rules that sit on top of the general modeller and must not leak into it. This ADR records how a domain plugs into core and regen, so that every domain milestone does it the same way. It confirms the M4 plan's Part 2 decisions 1 to 6 and 10, with the changes noted below.

The inputs:

- **What the code has today** (format version 10). `packages/core/src/schema.ts` has an `extension` feature kind, reserved since M1 for "printing, CAM, woodworking": `ExtensionFeatureSchema` holds a dotted, namespaced type in `extension` (pattern `^[a-z][a-z0-9-]*(\.[a-z][a-z0-9-]*)+$`, such as `wood.board`), a `schemaVersion` (an integer from 1), `dependsOn` (feature ids), `references` (core's `Reference` wrapper), `expressions` (a record of `StoredExpression`s, which core's `featureExpressions` lists with the kind `any`) and opaque JSON `params`. Core validates the generic parts like any feature's and sorts `expressions` and `params` keys when it serialises. Extensions have no `operation` and no `scope`. In `packages/regen/src/engine.ts` an extension changes no geometry: it is reported `ok` with an `extension` warning ("Regen does not build ... features yet"). Ids are `extension#n`, and `bodyCreator` already reads any `kind#n` prefix, so `extension#3` and `extension#3:layer/a` parse as bodies created by `extension#3`.
- **[ADR 0004](0004-document-format.md)**: the document is the source of truth and nothing derived is stored (decision 1); every change of shape bumps `version` with a migration and a fixture (decision 2); ids are permanent (decision 4); references are names (decision 5); numbers are `StoredExpression`s (decision 7); the cache key covers a feature's inputs, upstream keys and an implementation version (decision 8).
- **The [M2 plan](../plans/m2.md)**, decisions 1 to 4: a body is named after the feature that made it (`extrude#3`, `pattern#2:i3`); an `add` that touches no body makes a new body; features with an operation take an optional `scope` of body ids (absent: every body); only user settings are stored per body.
- **[ADR 0012](0012-3d-printing.md)** (M3, landed). M3 used neither the `extension` kind nor a generic slot. Print setups went into a typed top-level `print` section (decision 1), because they hold `StoredExpression`s and `FaceReference`s that core's validation, variable rename and inline and `diffDocuments` must reach; ADR 0012 rejected M4's `domains` field for that reason, and added that a later ADR moving every domain into `domains` would supersede its decision 1. Text outlines and threads became core kinds (decisions 7 and 9), partly because "regen treats extensions as geometry-free".
- **The [M5 plan](../plans/m5.md)**, decision 2: CAM state is a typed document-level `cam` section, and CAM operations must not be `extension` features, since they do not change bodies.
- **The M6 plan's requests** to M4: accept `<extension id>:<suffix>` body ids for extension creators (M6 decision 7), give the stock catalog a way for other domains to use it, and decide where the takeoff model lives.

The question the M4 plan left open was whether domain data that is not a feature goes into one generic, namespaced document field or into a typed section per domain, as M5 does for `cam`. The project owner chose the generic field (option A).

## Decision

1. **A domain is a package: `packages/domain-<name>`**, pure TypeScript under GPL-3.0-or-later, owning its namespace (`domain-wood` owns `wood`, `domain-construction` owns `construction`); in M4 `domain-wood` also owns `stock` (decision 3). It holds the domain's catalogs, the parameter schemas and migrations of its extension types, their translators (decision 5), the schema and migrations of its domain data (decision 3) and the derived models it computes (the cut list, decision 8).
   - **What it may depend on.** At run time, `packages/core`, `packages/units` and shared domain packages (`packages/takeoff`, decision 8, and later a shared stock package, decision 3). Shared domain packages follow the same rule and import no domain package. A domain package never depends at run time on `packages/kernel`, `packages/regen`, the app or the DOM, so everything in it runs in Node tests with no `.wasm` loaded. Translators produce kernel inputs, so a domain package takes type-only devDependencies: on `packages/regen` for the translator contract, and on `@manufakture/kernel` for the `FeatureInput` types, as `packages/print` does with kernel types. Type imports are erased, so no regen or kernel code loads. Amended 2026-10-08 for M8: a domain's fabrication files live in a `./files` subpath that may also load `packages/io` at run time; the package root is unchanged ([amendment](#amendment-fabrication-files-in-a-files-subpath-t81b)).
   - **No domain package imports another.** Code two domains share moves into a shared package under the same dependency rule (decision 8 names the first: the takeoff model). M6 finds the stock catalog in `domain-wood` and needs it for framing; under this rule it moves the catalog (or the part M6 needs) into a shared package then, rather than importing `domain-wood` (decision 3 says what happens to the `stock` namespace).
   - **Tests with the real kernel.** A domain's own tests run with no kernel. Tests that regenerate its features with the real kernel (for `domain-wood`, a board through regen and kernel) are `domain-wood` tests that take `packages/regen` and `packages/kernel` as devDependencies only; nothing in the run-time dependencies changes.
   - **Who loads it.** Regen does not import domain packages. The regen worker's entry in the app registers the domains the app ships (`domain-wood` in M4) at start-up; regen's tests register fakes.

2. **Domain features are `extension` features, not new core kinds.** A board is `{ kind: 'extension', extension: 'wood.board', schemaVersion: 1, ... }` with id `extension#n`; the tree shows the domain's label ("Board 3", "Dado 1") from the name or the type. Adding a feature type, or a field to one, never bumps the document format and never touches core. The generic fields carry everything core must see:
   - every feature the extension reads goes in `dependsOn`, so dependency order, delete blocking and reorder work unchanged;
   - every body the extension changes goes in `scope` (decision 6), not only in the inputs its translator returns, so regen's per-body dependency graph sees the change;
   - every face or edge reference goes in `references`, so the reference outcomes of ADR 0004 decision 6 (`exact`, `lost`, re-pick) apply;
   - every number a user can type goes in `expressions`, so `variableUses`, rename and inline reach it.

   `params` holds the rest as plain JSON (enums, stock ids, sketch entity ids, flags) and must not hide an expression, a face name or a feature id that core would need to find. The domain validates `params` per type and `schemaVersion`, declares the kind (`length`, `angle`, `number`) of each named expression for regen's evaluation, and owns the migrations.

3. **Document-level domain data is one generic, namespaced field**, `domains`, holding what belongs to a domain but is not a feature. Core stays domain-free: it checks only the envelope, never `data`. For woodworking there are two namespaces:
   - `domains.wood` holds the woodworking settings: kerf, trims, the stage limit and grain rules.
   - `domains.stock` holds the document's stock overrides: a measured thickness, a sheet size, a price. Stock is not wood-only (M6 frames with the same lumber and sheets), so its overrides get their own namespace from the start. In M4 the `stock` namespace's schema, validation and migrations are owned by `domain-wood`, where the stock catalog lives (M4 plan). M6 may move the catalog and the namespace into a shared stock package (decision 1); the namespace name stays `stock`, so that move needs no data migration.

   The shape T4.1a adds (field names may still change in that task; the rules here may not):

   ```ts
   interface ManufaktureDocument {
     // ...as at version 10
     domains?: Record<string, DomainData>; // key: a namespace ('wood'); absent: no domain data
   }

   interface DomainData {
     schemaVersion: number; // the domain's own version of `data`, from 1
     data: JsonValue; // validated and migrated by the domain package, never by core
   }
   ```

   - The key follows the pattern of an extension type's first segment (`^[a-z][a-z0-9-]*$`); it is the namespace of the package that owns the data. A domain reads its own namespaces plus the namespaces owned by shared packages it depends on (`stock`, once it has moved to a shared package). Only the owner writes, validates and migrates a namespace. Since no domain imports another (decision 1), M6 cannot read `stock` while `domain-wood` owns it.
   - **Domain data holds settings, not model.** It holds no face or edge names, no feature or body ids and no variable uses. Lengths in it are `StoredExpression`s, so a change of display units never changes a value (ADR 0005), but the domain's validator refuses any that names a variable: `18.2mm` and `23/32"` are allowed, `#ply - 0.3mm` is not. Core's commands therefore never need to look inside `data`. Anything that needs references, body ids or variable uses goes into a feature (decision 2), `BodyProps`, or a typed section of its own (decision 9).
   - One command, `setDomainData { namespace, schemaVersion, data }`, replaces a namespace's entry, with the old entry (or its absence) as the inverse, so every change is one undo step. `diffDocuments` reports it as `domainChanged` with the namespace and no `firstAffectedIndex`.

4. **Unknown and newer domain content loads, fails visibly and is never rewritten.** ADR 0004 decision 2 refuses a document whose format `version` is newer than the app's. Domain versions are finer grained, so a document from a newer build, or one using a domain this build does not ship, still opens:
   - An extension whose type has no registered domain, or whose `schemaVersion` is newer than its domain's current version, **fails** at regen with an `unsupported` feature error naming the type and both versions. Unlike today's `ok` with an `extension` warning, this applies whether or not the feature has an `operation`, so a missing domain is never silent. The feature makes no body; later features that name its body or faces report `reference-lost` as usual, and features that do not depend on it regenerate.
   - A known type and version whose `params` fail the domain's validation fails with `invalid` and the domain's message.
   - A `domains` entry of an unknown namespace loads and is kept. An entry with a newer `schemaVersion`, or one that fails validation, is reported as an error on that namespace, and every extension of a domain that reads it fails with the same error rather than regenerate from catalog defaults: a board must not silently change thickness because its override cannot be read.
   - **Nothing is rewritten.** The app keeps such features and entries as they are when it saves (core only re-sorts keys). It offers no edit dialog for a feature it cannot read and refuses `setDomainData` for a namespace it cannot read; deleting, renaming, suppressing and reordering stay available, since those touch only generic fields.
   - **Older versions are migrated in memory.** Domain migrations are pure functions from version N to N + 1 per type (and per namespace for domain data), tested against stored fixtures like core's. They run wherever params or data are read (translators, dialogs, the cut list); the stored value is written at the current version only when the user edits that feature or that namespace's data, as part of that undoable edit. Loading and regenerating never change the document. A domain keeps every migration it has ever shipped, for the same reason core does.

5. **Regen builds extensions through a translator registry.** A domain registers, per extension type, a translator: a pure, deterministic function from the feature to one or more kernel `FeatureInput`s carrying the feature's id, or an error value.
   - **Its context** holds the feature's `params` (migrated, validated), its expressions evaluated with the kinds the domain declared, its references resolved with their geometry (planes, lines, circles, through the existing `resolve` op), the domain data of the namespaces it may read (decision 3: its own and `stock`; migrated, validated), and the regen results it names in `dependsOn` that came from extensions of its namespace (for example a board's frame, decision 7).
   - **A two-step form** for translators that need geometry before they can say what to build: a first pure function returns the geometry queries it needs (a joint asks for the faces of the boards it joins), regen answers them with existing kernel ops against the part as it stands before the feature, and the second function builds the inputs from the answers. The answers are part of the translator's input.
   - **Generic kernel inputs only.** No domain code runs in the kernel, and the kernel has no domain feature kinds. A board is an `extrude`; joints use the generic `tools` input (T4.2a). A domain that needs new geometry asks for a new generic kernel input, which is a kernel task under ADR 0001's rules. Face names come from that input's naming rules with the extension's id as the feature id (`extension#7:t2:+x`), so core's name parsing and ADR 0004's reference outcomes apply without change.
   - **Caching.** Translators are cheap and run every time a regen reaches a dirty extension; only the kernel step is cached. The cache key is built from the translator's resulting kernel inputs (which carry every value it read: evaluated expressions, resolved geometry, stock sizes from domain data), the type, its `schemaVersion` and an implementation version the domain declares and bumps with any change that can alter its output (ADR 0004 decision 8). A `domainChanged` for a namespace marks dirty every extension of a domain that may read it (for `stock`, every `wood.*` extension); the cache then sorts out which really changed. A stock thickness override misses for that stock's boards, while a price change, which no translator reads, hits everywhere. This replaces the M4 plan's per-domain "affected features" hook (T4.1b), which is not needed.
   - **Containment.** Every translator call is wrapped: a throw or a malformed result becomes a feature error on that extension, never a failed regen.

6. **Extensions can make and change bodies, through the same `operation` and `scope` as other body features.** T4.1a adds two optional fields to `ExtensionFeatureSchema`:
   - `operation` (`new`, `add`, `cut`, `intersect`): how the extension's solid combines with the part, with the meaning it has for an extrude. An extension with `new` or `add` is a body creator (M2 decisions 1 and 2): its id is a valid body id in `BodyProps` and `scope`, and with `cut` or `intersect` it is not. Absent `operation`: the extension makes no solid of its own to combine. It may still change bodies through inputs that name their bodies (a joint's `tools` items cut each board directly), or change none at all.
   - `scope`: the bodies the extension combines with or changes, as M2 decision 3 defines it (absent: every body at that point), and refused with `new` as today. Every body the extension changes must be listed, including bodies changed through inputs that name them (decision 2). Regen's per-body graph (M2 T2.1c) uses it like any other scope, so a joint scoped to two boards is not redone when a third board changes.
   - **Validation.** Core's `checkScopeOperation` (`packages/core/src/schema.ts`) expects a required `operation`. An extension may have `scope` without `operation` (a joint), so T4.1a adds a variant of that check for extensions: `scope` is refused only when `operation` is `new`.
   - **Amendment (M6 wall layer joins, a T6.1b follow-up).** A `new` extension may also change, through a `tools` input, the bodies it made itself and the bodies made by the features in its `dependsOn`, although `scope` stays refused with `new`. Regen hands those bodies to the `tools` input (any other body is `reference-lost`), and its per-body graph counts every body made by a `dependsOn` feature as changed by the extension, so later features that read them are redone when it changes. This lets a later wall trim and notch an earlier wall's layer bodies at an L or a tee without a scope; `dependsOn` already names what it reads.
   - **Several bodies from one extension** (M6 decision 7) are named `<feature id>:<key>` (`extension#3:layer/sheathing`), the form of M2's `pattern#2:i3`. Core accepts such ids for extension creators; this changes validation, not the document shape, and T4.1a includes it.
   - Changing `ExtensionFeatureSchema` and adding `domains` is one change of shape: **one format bump** (T4.1a), the next free `FORMAT_VERSION` when it lands (11 if nothing lands before it), with a migration that changes only the version (both additions are optional) and a fixture of version 10. It serves every domain for features and plain settings. M4 does not add `expressions` to `DomainData`: that is kept out of T4.1a's bump on purpose, and M6's ADR decides it (Consequences, known conflicts for M6).

7. **Derived results are never stored** (ADR 0004 decision 1). Translator outputs, board frames, the joints' tool lists, cut lists, sheet layouts, oriented boxes and migrated params all live in memory and in the disposable cache. A translator may return metadata next to its kernel inputs (a board's frame: origin, length along the grain, width and thickness axes and extents), which regen reports in the feature's result for the domain's derived models; it is recomputed on every regen of the feature, like face names.

8. **The cut list is one producer of a generic takeoff.** A takeoff is rows of `{ item, stock, size, quantity, unit, extended, sources }`:
   - `item`: what the row is ("Shelf", "2x4 stud", "Dowel 8 mm");
   - `stock`: the stock id, when the row comes from a catalog stock;
   - `size`: the blank size in millimetres (for a board: length along the grain, width, thickness, before joinery);
   - `quantity`: how many pieces;
   - `unit` and `extended`: what the row adds up to and how much of it (board feet, linear length, area, sheets, each);
   - `sources`: the bodies the row counts, with the instance path when it comes from an assembly.

   The model and its grouping and totals live in a shared package, **`packages/takeoff`**, created by T4.3a, with the dependency rule of decision 1. Values are held in millimetre-based internal units and formatted through `packages/units` in the document's display units (ADR 0005). `domain-wood` adds the cut list producer: rows from boards and their frames, from oriented boxes of other bodies (given as input data, since the domain does not call the kernel), from instance counts and from the configuration in force. M6 adds its producers (studs per wall, sheathing area) to the same model without depending on `domain-wood`.

9. **Where domain things go, and how this relates to ADR 0012.** M3's choices stand; this ADR does not supersede ADR 0012 decision 1, and `print` is not moved into `domains`. The rule all domains now follow:
   - **A general modelling capability** that needs core validation and kernel naming, and that any domain could use, is a core kind: text outlines and threads (ADR 0012 decisions 7 and 9). ADR 0012 also gave "regen treats extensions as geometry-free" as a reason for threads; this ADR removes that limit, but threads stay a core kind for the first reason.
   - **Domain geometry** is an `extension` feature with a translator (decisions 2 and 5): boards, joints, walls.
   - **Domain settings** that are plain values are `domains[namespace]` data (decision 3): stock overrides, cut list settings, M6's wall and header rules where they need no variables.
   - **Document-level domain state that holds references, body ids or variable uses**, or that core's commands must reach, is a typed section with its own ADR and its own format bump: `print` (ADR 0012) and M5's `cam`. Those sections exist because their content fails decision 3's "settings, not model" test, not because each domain gets a section by default.

## Alternatives considered

- **A typed section per domain, as M5 does for `cam`** (`wood: { stockOverrides, cutList }`, `construction: { levels, wallTypes }`). Core would validate every field and its commands would reach expressions and references inside. But every domain, and every new field in one, would cost a core schema change and a format bump, serialised against every other milestone's schema tasks; core would learn woodworking and construction vocabulary; and a document from a build with a newer domain field would be refused outright (ADR 0004 decision 2) where a namespaced entry still loads. Rejected for domain settings. It remains the right choice for content that fails decision 3's test, which is why `print` and `cam` stay typed (decision 9).
- **Moving `print` into `domains`.** Print setups hold `FaceReference`s and expressions with variable uses that core must reach, which is ADR 0012's reason for a typed section, and decision 3 forbids exactly that content in `domains`. Moving them would also cost a migration for no gain. Rejected; ADR 0012 decision 1 stands.
- **Woodworking features as first-class core kinds** (`board`, `dado`). Core validation for free, but a core change and a format bump for every feature kind and every new field, and core would no longer be domain-free. Rejected; the generic fields of decision 2 give core what it needs to see.
- **A generic `expressions` record next to `data` in each `domains` entry**, so domain settings could use variables and core could reach them as it reaches an extension's expressions. It would let M6 levels take `#floor_height`. Not adopted now: the owner chose `{ schemaVersion, data }`, and M4's settings need no variables. If a domain needs it, adding an optional `expressions` to `DomainData` is an additive change with its own format bump, recorded as an amendment here.
- **Treating an unknown extension type as a geometry-free warning**, as regen does today. A document opened in a build without its domain would quietly lose its boards. Rejected for a visible `unsupported` error (decision 4).
- **Migrating domain params on load and saving the result.** Opening a document would then change it, and opening it in an older build afterwards would fail. Rejected: migrations run in memory, and only a user's edit writes the new version.
- **Running domain code in the kernel, or adding domain feature kinds to the kernel.** Ties the kernel and its `.wasm` lifecycle to every domain, and loses the Node-only tests of decision 1. Rejected for generic kernel inputs (decision 5).
- **Caching on the extension's own params.** Misses domain data a translator reads (a stock override would serve a stale board). Rejected for a key built from the translator's resulting kernel inputs.
- **A per-domain hook that says which features a domain data change affects** (the M4 plan's T4.1b). Translators are cheap and the cache already tells changed inputs from unchanged ones, so the hook would duplicate that and could disagree with it. Rejected.
- **The takeoff model inside `domain-wood`, or construction importing `domain-wood`.** Couples one domain to another and makes the woodworking package a dependency of building a shed. Rejected for a shared package and the no-cross-import rule (decision 1).

## Consequences

- T4.1a (core), T4.1b (regen), T4.1c (`domain-wood`) and T4.3a (`packages/takeoff` and the cut list) cite this ADR. T4.1a takes one format version for `operation`, `scope`, `<id>:<key>` extension body ids and `domains`; it checks the persistence README for top-level key filters so `domains` is saved and carried in `.mfk` files.
- Regen's behaviour for extensions changes: an unregistered type now fails with `unsupported` instead of `ok` with a warning. No shipped build creates extension features, so no saved document changes outcome; regen's README and the `extension` warning code are updated by T4.1b.
- The stock overrides of T4.1c hold constant expressions only (decision 3): a measured thickness is `18.2mm`, not a variable. A user who wants a variable thickness uses a board's own expressions, not the override.
- A domain bug can store bad `data` or `params` that core accepts; the domain reports it on load as an error on the domain or the feature, never as a broken document, and the user can fix or delete it.
- Every domain keeps its params and data migrations forever, with fixtures, as core does.
- M6 plugs in with no dependency on `domain-wood`; whatever it shares with wood (the stock catalog and the `stock` namespace, the takeoff) lives in shared packages. This ADR does not promise that M6 needs no format bump. Known conflicts between the M6 plan and this ADR, for the M6 owner to settle in M6's ADR:
  - **Variables in domain data.** T6.1a's acceptance wants a level elevation expression using a variable, stored in `domains.construction`, which decision 3's "settings, not model" rule forbids. The way out is an optional `expressions` record on `DomainData` (the alternative above), which is a format bump. M4 does not add it.
  - **Feature ids in params.** M6 decisions 5 and 8 key per-member overrides in a wall's params by ids that embed feature ids (`extension#7:king-l`). M7's id remap must then rewrite ids inside `params`, which decision 2 forbids (`params` must not hide a feature id core would need to find). M6's ADR resolves it.
- ADR 0012 is unchanged; its alternative "Print data under M4's generic `domains` field" is answered by decision 9. The owners of the M3, M5 and M6 plans are asked to review this ADR, since their domains follow it.

## Amendment: fabrication files in a `./files` subpath (T8.1b)

Dated 2026-10-08. Decision 1 lists what a domain package may load at run time: `packages/core`, `packages/units` and shared domain packages. M8's [T8.1b](../plans/agent-surface.md) moves the cut list's and the takeoff's file writers (CSV and PDF) out of `apps/web`, because headless sessions (T8.1c) and the MCP server (T8.4a) must export every fabrication format from Node with no app and no browser (the M8 plan's cross-cutting decision 5). Those writers need `packages/io` (file names, MIME types, the PDF writer), which the domain logic never does. The exception, as built:

- **A `./files` subpath may load `packages/io` at run time.** `@manufakture/domain-wood/files` (`src/files/`: the cut list CSV, the bill of materials CSV and the shop PDF) and `@manufakture/domain-construction/files` (`src/files/`: the takeoff CSV and PDF) may import `@manufakture/io` besides what decision 1 allows. Nothing else in the package may, and it still loads no kernel, regen, `.wasm`, other domain, app or DOM code, so the writers run in Node tests.
- **The package root is unchanged.** Code outside `src/files/` never imports `@manufakture/io` at run time and never imports `src/files/`, by package name or by relative path, so a caller that wants only the domain logic (the regen worker's entry, which registers the domains) loads no file writer. Each package's `src/boundary.test.ts` enforces this as an allowlist.
- **Why a subpath and not `packages/io`.** The writers know the domain's rows (sections, groups, totals, the "not an engineering tool" text of ADR 0015 decision 8); moving them into `packages/io` would make it import the domains, which this ADR forbids of every shared package. A subpath keeps the domain's knowledge in the domain and its `io` dependency out of the root.

ADR 0014 records the same exception for `@manufakture/cam/export`. The rest of decision 1 stands, as do the rules for shared packages (still no domain import) and for type-only imports.
