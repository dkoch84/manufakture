# 0009: Sync model: a server-ordered command log, validated by core, rebased on the client

- Status: proposed
- Date: 2026-09-26

## Context

M7 brings the first server ([product decisions](../decisions/0000-product-decisions.md), decision 1: "no server until M7"). Its first job (T7.1 in [the M7 plan](../plans/m7.md)) is to sync documents: between one user's browsers and machines first, and between several editors of one document later. The epic plan names the command log from T1.12 as the sync unit and asks whether a CRDT (Yjs, Automerge) or a server-ordered operation log fits concurrent edits of a parametric feature list: reorder, delete with dependents, and ids that are never reused.

What M1 and M2 give us, from the code and the plans:

- **The document is a validated JSON feature list** ([ADR 0004](0004-document-format.md)). Validity is global, not per field: a feature comes after everything it depends on, delete refuses while a dependent exists, reorder refuses to cross a dependency (core README, "Dependencies"), variables have no cycles, and every id is permanent and never reused (decision 4). An invalid document is reported, never silently repaired (decision 9).
- **Every change is a command**: a plain, JSON-serializable object, applied by `applyCommand(doc, command)`, which validates it, applies it without mutation, checks the whole result with `checkDocument` and returns the inverse or a `CoreError` (core README, "Commands"). Core is plain TypeScript with no WebAssembly and no geometry, so it runs in Node as it is.
- **Commands carry their ids.** A client asks `previewIds(part.nextIds, 'extrude')` for fresh ids and puts them in the command; `addFeature` and `editFeature` refuse an id below its counter with `id-reused` (core README, "Ids"). Two clients that add an extrude at the same time both pick `extrude#3`.
- **Edits are coarse.** `editFeature` carries the whole new feature, a sketch included; its inverse is `restoreFeature` of the old state. `batch` is all or nothing.
- **The log already exists.** `DocumentStore` reports every `execute`, `undo` and `redo` with its command, and persistence stores them as `{ cause, label, command, at }` in log segments chained by `base` revision, with imported files moved to content-addressed blobs ([persistence README](../../apps/web/src/persistence/README.md)). Saves are guarded per document by a Web Lock, and a tab whose base revision is stale gets a `RevisionConflict`, which today is resolved by picking one version, not by merging ("Not done: merging two tabs' changes").
- **M2 adds history, not merging.** Named versions with stable ids and replay from checkpoints (T2.5a, board #987), a history viewer with restore through a `replaceDocument` command (T2.5b, #988), and branches as separate heads under one document (T2.5c, #989). Merging branches is explicitly left to M7 ([M2 plan](../plans/m2.md), T2.5c) because it "needs the op-log replay that M7's sync brings".
- **Regen is local.** Geometry is derived and rebuilt from the document by every client ([ADR 0004](0004-document-format.md) decision 8). Nothing geometric has to travel.

## Evaluation

Registry facts were read from the npm registry on 2026-09-26 (`registry.npmjs.org/<name>/latest`); they are metadata, and ADR 0006 decision 6 still requires reading the installed package and its license file before adoption. Everything else is research from the cited pages, not built or run here.

### CRDTs

A CRDT merges any two replicas without a coordinator and guarantees they converge.

- **[Yjs](https://github.com/yjs/yjs)** 13.6.33, MIT. A list CRDT at heart with maps, text and arrays ([docs](https://docs.yjs.dev/)). `Y.Array` has insert and delete but no move; a move is a delete plus an insert, so two users moving the same feature concurrently get two copies of it.
- **[Automerge](https://github.com/automerge/automerge)** 3.5.0, MIT. Version 3 cut memory use sharply ([Automerge 3.0](https://automerge.org/blog/automerge-3/)). Lists record insert and delete operations ([merge rules](https://automerge.org/docs/reference/under-the-hood/merge-rules/)); no move operation was found in its documentation, so reorder has the same duplication problem.
- **[Loro](https://github.com/loro-dev/loro)** (`loro-crdt` 1.16.3, MIT) has a movable list and a movable tree with native move ([choosing a CRDT type](https://loro.dev/docs/concepts/choose_crdt_type), [movable tree](https://loro.dev/blog/movable-tree)), which solves concurrent reorder.

All three licenses are GPLv3-compatible. The problem is not the license or the list type but the invariants:

- **Convergence is not validity.** Ink & Switch put it plainly: "The merge replays effects, not intents, and the programmer's invariants [...] were never written down anywhere that Automerge could see" ([Convergence Is Not Enough](https://www.inkandswitch.com/livelymerge/notebook/lm-02/)). For us: user A deletes `sketch#1` (no dependents on A's replica) while user B adds `extrude#4` on it. Both operations are locally valid; the merged document has an extrude whose profile names a sketch that is gone. A CRDT must accept both. The result fails `checkDocument`, and ADR 0004 decision 9 forbids repairing it silently.
- **Ids collide.** Both users add `extrude#3`. In a CRDT both inserts survive, so the part holds two features with one id, which ADR 0004 decision 4 makes impossible. Avoiding it needs replica-unique ids (a client suffix), which changes the id format, the face names that embed feature ids (`extrude#3:cap:end`) and core's name parser.
- **The command log would stop being the unit.** A CRDT document is its own log of low-level operations. Our commands (with labels, inverses and validation) would become a layer that writes into it, and version history (T2.5a) would have two logs to keep in step.

### A server-ordered command log

A server puts every accepted command in one total order per document branch; clients apply their own commands optimistically and reconcile when the server's order arrives.

- **Figma** runs this shape: "Figma isn't using true CRDTs though. CRDTs are designed for decentralized systems where there is no single central authority to decide what the final state should be", and "since Figma is centralized (our server is the central authority), we can simplify our system" ([How Figma's multiplayer technology works](https://www.figma.com/blog/how-figmas-multiplayer-technology-works/)). Clients keep unacknowledged local changes as their best prediction until the server confirms.
- **Onshape**, the parametric CAD closest to our model, records every edit as an immutable, server-ordered microversion in a workspace; versions and microversions are immutable and all writes go to a workspace ([API architecture](https://onshape-public.github.io/docs/api-intro/architecture/)).
- **Replicache** is the packaged form of the same pattern (speculative client mutations rebased on server-authoritative state), but its registry license field is a link to proprietary terms (`https://roci.dev/terms.html`), which [ADR 0006](0006-licensing.md) decision 3 excludes. We take the pattern, not the package.

What it means for us:

- **The server can run core.** Because core is pure TypeScript, the server validates every command with the same `applyCommand` the client ran. A command that is invalid against the current head (an extrude on a sketch someone deleted) is refused with a `CoreError`, exactly as it would be locally. Every document in the log is valid; nothing needs repair.
- **Intent survives.** The unit is the command, which is the user's intent (add this feature, move this one to index 4), with a label a user can read in a "your change could not be applied" notice.
- **Offline still works.** Commands queue locally, as autosave already queues them, and are submitted on reconnect. The cost is that a long offline session can end in refused commands, which must never lose work (decision 6).

## Decision

1. **Server-ordered command log.** Each document branch on the server has one log: a sequence of entries, each at a server revision `n` (1, 2, 3, ...), holding one command in storage form. The server is the only party that assigns revisions. No CRDT library is adopted.

2. **The sync unit is the command.** A sync entry is the persistence `LogEntry` plus what ordering needs: `{ clientId, clientSeq, prevSeq, baseRev, format, cause, label, command, at }`. `clientId` is a random id per installation and document. `clientSeq` increases by one per entry the client sends and is never reused for a different command, a refused one included. `clientSeq` and `prevSeq` are assigned when an entry is sent (moves from unsent to in flight, decision 4) and never change after that. `prevSeq` is the `clientSeq` of the entry the new one was built on, by one rule that holds whatever order verdicts arrive in: **the nearest entry before it in the client's queue that is neither refused nor doomed (decision 4), else the client's latest accepted entry, else absent.** The client sends in queue order and sends nothing while a doomed entry is before it in the queue, so `prevSeq` always names an in-flight entry or the latest accepted one, never an entry the client knows was refused or doomed, and a client is never refused forever for its own past.

   Worked example. A (`clientSeq` 1, adds `extrude#3`, `prevSeq` P), B (2, edits `extrude#3`, `prevSeq` 1) and C (3, `prevSeq` 2) are in flight when another client's `extrude#3` is accepted first. The server refuses A as `id-reused` and B and C as `predecessor-refused`. A was judged by core, so its predecessor P was accepted (or A had none). The client pulls up to the head revision A's refusal carries, then remaps A to A' (adding `extrude#4`) in A's own place in the queue, before B and C, which are doomed and held (decision 4). A' is sent as 4 with `prevSeq` P, or none: the nearest entry before it that is not refused or doomed is P (in flight or already confirmed as the latest accepted), never B or C. When B's and C's verdicts arrive they return, remapped with A's table, after A', and are sent as B' (5, `prevSeq` 4) and C' (6, `prevSeq` 5). If B's and C's verdicts arrive before A's, they wait held for A's verdict, and the result is the same: A' is still 4 naming P, B' 5 and C' 6. Nothing ever shows B applied to the other client's `extrude#3`.

   An undo inverse submitted as an entry (decision 8) follows the same rule, so it names the entry before it in the queue, usually the command it undoes; a doomed command holds the inverse after it, so the inverse is never sent naming an earlier entry instead. `baseRev` is the server revision the client had when it made the command, and `format` the `FORMAT_VERSION` the command was written under (see Consequences).

   The server keeps a de-duplication table per document branch from `(clientId, clientSeq)` to the outcome: the revision the entry was accepted at, or the refusal with its `CoreError`. It checks a submitted entry in this order:

   - a `(clientId, clientSeq)` it has recorded gets the recorded outcome, so a resubmission after a lost reply is never applied twice, and a refusal is final for that `clientSeq`;
   - a `prevSeq` for which it has no outcome gets a retryable `predecessor-unknown` answer that is **not** recorded: the predecessor's request was lost or overtaken, and the entry must not be judged before it;
   - a `prevSeq` that names a refused entry is refused as `predecessor-refused`, recorded like any refusal: the entry was built on the refused one and may name ids it meant to create, and applied on its own it could land on another client's feature that has the same id;
   - anything else is validated by core (decision 3).

   Over HTTP a request can be lost and retried, or overtaken by a later one, so B (`prevSeq` A) can reach the server before A. The `predecessor-unknown` answer covers that without serialising the client: an entry is only judged once its predecessor has an outcome, so B never lands on another client's `extrude#3` before A has been refused. The client keeps the entry in flight, unchanged, and resubmits its in-flight entries in `clientSeq` order, the predecessor first. The alternative, at most one entry in flight per client, is simpler on the server but turns the catch-up after a long offline session into one round trip per entry (a queue of 1000 is 1000 sequential requests), while a retryable answer costs a round trip only when a request was actually lost or reordered.

   The table must not grow forever, and it must not lose a row a client can still name. Each submit therefore carries the client's **retention floor**: the lowest sequence it may still reference, which is the minimum over its in-flight entries of both their `clientSeq` and their `prevSeq`. A refused entry named by a doomed follower's `prevSeq` stays at or above the floor until that follower has its verdict. Per `clientId` the server keeps every row from the highest floor it has been sent, plus the client's latest accepted entry (which a new entry may name as `prevSeq` after its in-flight entries are resolved), and may prune the rest; it never lowers a stored floor, so a submit overtaken by a later one cannot undo a prune. The floor a correct client sends never drops below a row it still needs: a newly sent entry adds its own `clientSeq`, which is the highest yet, and a `prevSeq` that names an entry already in flight (already counted) or the latest accepted entry (kept anyway). A submit that was overtaken still carries an in-flight entry, so the later submit's floor counted it. For example, A (1) and B (2, `prevSeq` 1) are sent and B's submit is lost; A is refused. B is still in flight, so the floor stays 1 and row 1 is kept; B's resubmission then gets `predecessor-refused`, not a protocol error. Only once B has its verdict can the floor rise past 1.

   Imported files stay blobs by SHA-256, uploaded before the entry that names them, and the server refuses an entry that names a blob it does not have (persistence README, save step 2, carried over).

3. **The server validates with core.** On submit the server applies the entry's command to its head with `applyCommand`. If it applies, the entry gets the next revision and is broadcast; if not, the server refuses it with the `CoreError`. The server never regenerates geometry and never needs OCCT. The server runs a core whose `FORMAT_VERSION` and command schema are at least the client's; an older client is refused with an upgrade message (as a newer file is refused today, ADR 0004 decision 2), and a newer client is refused until the server is upgraded.

4. **Clients rebase by replay.** A client keeps the last confirmed document (at server revision `c`) and a queue of its own entries the server has not confirmed, each either **in flight** (sent, so the server may already have ordered them) or **unsent**. The queue keeps its logical order, the order the user made the commands in; entries are sent in that order, so the in-flight entries come first, except that a remapped refused entry (A' in decision 2) takes its old place, ahead of in-flight entries that were sent after it. It shows confirmed plus pending, minus held entries and entries it knows were refused (a refused entry is shown again only once it returns remapped). Entries arrive in revision order, the client's own included. An arriving entry that carries the client's own `clientId` is first matched to the in-flight entry with the same `clientSeq`: that is its acknowledgement, and the entry becomes confirmed exactly as it was sent, with no remap. Every other arriving entry is applied to the confirmed document. Then the client replays its remaining entries on top, one by one, with `applyCommand`:

   - An **in-flight** entry is never edited, because the server may have seen it under its `clientSeq`. If it no longer applies locally, it is held (not shown, not dropped, not remapped) with every entry after it, and nothing further is sent until the server's verdict. If the server accepts it after all, it arrives and is matched. A `predecessor-unknown` answer (decision 2) is not a verdict: the entry stays in flight, unchanged, and is resubmitted under the same `clientSeq` after its predecessor. If the server refuses it with `id-reused`, the refusal carries the server's head revision, and the client first pulls the entries up to that revision, so the remap sees every id taken so far and the entry is not refused again for an id the client had not yet received. The client then remaps it (decision 5) and keeps it, now unsent, in its own place in the queue, before every entry that was sent after it, to be submitted under a new `clientSeq` with the `prevSeq` of decision 2. Any other `CoreError` drops it.
   - A **doomed** entry is an in-flight entry that chains through `prevSeq` (directly or through other in-flight entries) to an entry the client knows was refused, from that entry's own verdict or from a follower's `predecessor-refused`, which says its predecessor was refused. The server will refuse it as `predecessor-refused`, so the client does not wait to be told: it holds it (not shown, not remapped, never named as a `prevSeq`) and holds every unsent entry after it too, sending none of them, until the doomed entry's verdict arrives. It stays in flight meanwhile and is resubmitted unchanged if its request was lost. This is what keeps B of decision 2 off the other client's `extrude#3`: B is held from the moment A stops applying locally (the first rule), and stays held after A's refusal is known and A' has replaced A, instead of being replayed as an edit of whatever now has the id `extrude#3`. If B's and C's verdicts arrive before A's, the client learns from them that A was refused, holds B and C, and waits for (or resubmits A to learn) A's own verdict.
   - A **`predecessor-refused`** entry is never dropped for that reason. It waits until its predecessor is resolved (remapped, or dropped), then returns to the unsent part in its place, after the remapped predecessor, and is replayed and remapped like any unsent entry (with the predecessor's remap table, which could not be applied to it while it was in flight), and submitted under a new `clientSeq` whose `prevSeq` follows decision 2. Only a real `CoreError` in that replay drops it: an edit of a feature the dropped head created fails, while an entry that does not depend on the head lands. The one exception is an undo inverse whose command was dropped, which is removed with it (decision 8).
   - An **unsent** entry whose fresh ids were taken is remapped (decision 5) and replayed again. One that still does not apply, or fails for any other reason, is dropped.

   A dropped entry is removed from the queue, reported to the user by its label and error ("Fillet 2: the edge it names was deleted by another change"), and kept for decision 6. Rebasing never edits a confirmed entry.

   A client that persists its queue across a reload (T7.1d) saves the whole queue state, not only the entries: **the pending remap tables and entry states are part of the saved queue**, together with the entries it knows were refused and its latest accepted `clientSeq`, and they are saved in one step with the confirmed document they belong to. Without them, a reload after A's `id-reused` refusal and before B's verdict (decision 2) would lose A's table and the knowledge that A was refused, and B would be replayed as an edit of the other client's `extrude#3`.

5. **Ids are remapped on rebase.** An entry's ids may be renamed only while the server cannot have applied it under its `clientSeq`: when it is unsent, or after the server refused it (decision 4). When such an entry's fresh ids are no longer fresh (another client's entry took `extrude#3`), the client allocates the next free ids from the rebased counters and rewrites them through one table: in that entry, in every later unsent entry (a later in-flight or doomed entry keeps the table and gets the rewrite when it returns to unsent, decision 4), in the inverses and redo entries of the local undo stack that name them (decision 8), and in app state that points at them (selection, an open dialog). The table is keyed by counter scope, because the same id can exist in several scopes:

   - **part** `nextIds`, one table per part: a counter per feature kind (`extrude#n`, `fillet#n`) and the sub-id counters `e`, `k` and `r` (sketch entities, constraints, references);
   - **document** `nextIds` (M2 plan): `part`, `assembly`, the configuration counters `cp` and `cfg`, and `script` (ADR 0010);
   - **assembly** `nextIds` (M2 plan), one table per assembly: `inst`, `mate` and `mc`;
   - **CAM** `cam.nextIds` (M5 plan): `tool`, `setup`, a counter per operation kind (`profile#n`, `pocket#n`) and `r`. Operation ids share the `kind#n` shape with feature ids and are told apart by scope, never by shape.

   A counter a later milestone adds joins this list in the task that adds it. Ids in command fields are rewritten structurally, each field through the scope it belongs to: feature ids, `dependsOn`, profile and hole sketches, pattern and mirror sources, body ids in `scope` and body properties, instance, mate and connector fields, an instance's `source.part` and `configuration`, configuration parameters' `partId` and `featureId`, CAM tool, setup and `partId` fields. Face names are rewritten by a parser and printer for the naming grammar of `packages/kernel/src/naming.ts`, never by string replacement:

   - a born name `<feature id>:<role>[:<tail>]` maps the feature id through its part's table; a tail that is a sub-id maps through the part's `e`, `k` or `r` table and keeps its split suffix (`extrude#1:side:e7#a` becomes `extrude#1:side:e9#a`, a sketch region edge `e7#1` becomes `e9#1`); a tail that is itself a name (a fillet round `fillet#3:round:A&B`, a shell wall `shell#5:offset:X`) is rewritten recursively; other tails (`cap:end`, the `4` of `import#9:face:4`, hole roles) stay;
   - merges `(A+B)` and corners `A&B&C` rewrite each member, and a positional piece `X#2` keeps its number;
   - instance prefixes `pattern#7:i2/X` and `mirror#8:image/X` map the feature id and rewrite `X`;
   - a derived prefix `derived#1:from/X` maps `derived#1` only: `X` is a name in the carried source document (M2 plan, T2.2a) and is never rewritten, and neither is a derived body id's source part or a derived source's `configuration`;
   - a scripted prefix `scripted#2:boss/X` maps the feature id, keeps the operation id, and rewrites `X` by the same rules, except that tails born inside the script are the script's own ids and stay (ADR 0010 decision 6).

   Edge references store face names, so they are covered by the same rules. Once an entry is accepted its ids are final: confirmed ids are never renamed, so ADR 0004 decision 4 holds on the server and an id is used once, for good. The server refuses `id-reused` as it does today, so a client bug cannot slip a duplicate in.

6. **Nothing typed is lost.** When a rebase drops commands, the client first saves its pre-rebase state (confirmed plus every pending command, as it looked before the others' entries arrived) as a local branch (T2.5c, #989) named after the time it diverged, and says so. The user can compare it (T2.5b, #988) and copy work across. The same rule covers a device that was offline for a long time.

7. **Concurrent edits of one feature: the later arrival wins, whole.** `editFeature` carries the whole feature, so if two clients edit the same fillet, the one the server orders second replaces the first. This is last-writer-wins at feature granularity, like Figma's per-property rule one level coarser. The earlier writer is told ("Fillet 2 was changed by another edit") through the same notice as decision 4. Field-level patches are a later refinement, not part of M7.

8. **Undo stays local and selective.** Each client's undo stack holds its own commands' inverses. Undo applies an inverse only when the object it restores has not been changed by anyone else since the command being undone (compared by canonical JSON of the feature, variable or setting); otherwise it refuses with "changed by another edit" rather than overwrite someone's later work. Undo of a command that is still unsent just removes it from the queue; undo of an in-flight command is submitted as its inverse, like any other command, with the `prevSeq` of decision 2: the entry before it in the queue, which is the command it undoes or an entry after that command (if that command is doomed, the inverse is held behind it and not sent until it returns, so it never skips past it). So the inverse is refused as `predecessor-refused` whenever that command is refused, and is never applied on its own. If the command is then remapped, the inverse is remapped with it and resubmitted; if the command is dropped, the inverse is removed from the queue without a notice, since there is nothing left to undo. When a rebase remaps ids (decision 5), the undo and redo stacks are rewritten with the same table, so an undo acts on the renamed feature and not on another client's feature that took the old id. A held entry (held, doomed, or known refused and not yet remapped) is not on the visible undo stack: it is hidden like the entry itself and comes back, with its remapped inverse, when it returns to unsent or lands, or leaves the stack when it is dropped. Undo acts on the newest shown command; if a held entry comes after that command in the queue, undo waits (disabled, with a "waiting for the server" hint) until the held entries are resolved, rather than put an inverse after commands the user cannot see.

9. **Versions and branches ride on the log.** A named version (T2.5a, #987) records a server revision and is an immutable, append-only record, so syncing it is a plain upload. A branch (T2.5c, #989) is a separate server log that starts from a version. Merging branch B into A is the rebase of decision 4 with B's commands since the fork as the pending queue, and the same notices; this is the M2 follow-up the M2 plan deferred.

10. **The local library stays the first store.** Sync is optional per document. A synced document still lives in the browser (persistence README) and opens offline; the server is one more replica, not the source the app waits for. Snapshots on the server exist so a new device does not replay from revision 1 (every `CHECKPOINT_EVERY` revisions, the constant T2.5a introduces).

11. **Transport and storage**, for T7.1c: HTTP for submit, pull (entries since a revision) and blobs; one WebSocket per open document for push, with pull as the fallback. The server is Node with Fastify (5.12.5, MIT) and a storage interface with a SQLite implementation first (`better-sqlite3` 13.0.3, MIT; SQLite is public domain) and Postgres (`pg` 8.23.0, MIT) as a second implementation if hosting calls for it. All are GPLv3-compatible; licenses to be re-read from the installed packages per ADR 0006.

12. **What stays open for the maintainer.** This ADR stays **proposed** until these are decided: whether a hosted sync service is run at all or the server is self-host only; accounts and authentication (a single-user token for self-hosting is enough for the first tasks); and Postgres versus SQLite for a hosted service. The recommendation is self-hosted and single-user first, SQLite, then multi-user when the rebase notices have been used in practice.

## Alternatives considered

- **Yjs or Automerge as the document store.** Mature, MIT, and offline-first by design, but they merge effects, not intents: concurrent delete-with-dependent and add-dependent produce a document core refuses, concurrent adds produce duplicate ids, and reorder duplicates features without a move operation. Each needs a repair pass that ADR 0004 decision 9 forbids. Rejected.
- **Loro.** Its movable list fixes reorder, but the dependency and id invariants remain. Rejected for the same reason; noted as the CRDT to look at first if a peer-to-peer mode without a server is ever wanted.
- **Operational transformation.** Figma rejected it as "unnecessarily complex for our problem space" (same post). With a server that runs core, transforming commands against each other buys nothing over replaying them, except for concurrent edits of one sketch, which decision 7 accepts as last-writer-wins. Rejected.
- **Server-assigned ids** (the server rewrites ids in each accepted command). Removes the remap from the client but means the client learns its own ids only after a round trip, so offline work, and any command that names an id created by an earlier pending one, needs the same remap anyway. Rejected; the client remaps (decision 5).
- **Replica-unique ids** (`extrude#3~a7f`). Removes collisions but changes the id format, every face name built from an id and core's name parser, with a format and naming-scheme bump, to fix something the client can fix locally. Rejected.
- **Whole-document last-writer-wins** (the current `RevisionConflict`, done over the network). Simple, and it is what two tabs do today; with two devices it loses whole sessions of work. Rejected as the sync model; kept as the local fallback it already is.
- **Replicache.** The right pattern with a license ADR 0006 excludes. Rejected.

## Consequences

- Core becomes shared code between browser and server. Its command semantics are now a wire protocol: a change to what a command means must keep old logs applying the same way (the M2 plan already names this risk for version history). Command fixtures and golden logs replayed in CI are how that is enforced (T7.1a).
- Core needs three new pieces: a way to tell which ids a command creates in every counter scope, a structural id remap over commands, and a parser and printer for face names that the remap and `featureIdsInName` share. All are pure functions with property tests (T7.1a). Every naming form or counter a later task adds must be added to them in that task, with tests.
- Old log entries outlive format bumps. Version replay, branch merges and a pending queue persisted across an app update all apply commands written under an older `FORMAT_VERSION`, and a bump that changes a shape a command carries (a new required field on a feature that `addFeature` holds) would make those commands fail validation. Each entry therefore records its `format`, and core gains command migrations beside the document migrations (`migrations.ts`): an entry is migrated to the current format before it is applied, never rewritten in storage. Golden logs written under each old format are replayed in CI after every bump (T7.1a).
- A long offline session can end with refused commands. Decision 6 keeps the work as a branch, but the user has to reconcile it by hand; the notice text matters as much as the algorithm.
- Two people editing one sketch at the same time lose one side of it (decision 7). Acceptable for single-user sync across devices, which comes first; a real concern for multi-user editing, where finer-grained sketch commands are the fix.
- The server is small: no geometry, no WebAssembly, core plus storage plus transport. It can run on modest hardware, and its tests run in Node like the packages.
- The server is GPL-3.0-or-later like everything else. Under [ADR 0006](0006-licensing.md), GPL (not AGPL) does not oblige a host to publish server changes, but the app served to browsers is distributed, so a hosted instance must offer the app's source.
- Threat model and security review are needed before anything is exposed beyond localhost: authentication, per-document authorisation, entry and blob size limits, rate limits, and validation cost (a large `batch` or `replaceDocument` is core work on the server's thread). The M7 plan flags each task that needs it.
