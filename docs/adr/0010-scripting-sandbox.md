# 0010: Scripting sandbox: QuickJS in WebAssembly, inside the regen worker, with no capabilities

- Status: accepted, amended 2026-10-04
- Date: 2026-09-26

## Context

M7 adds user-facing scripted features (T7.2 in [the M7 plan](../plans/m7.md)): a feature type whose geometry is computed by a user's JavaScript or TypeScript through an API over our modelling operations, in the spirit of Onshape's [FeatureScript](https://cad.onshape.com/FsDoc/). The [product decisions](../decisions/0000-product-decisions.md) (decision 2) put the GUI feature tree first and scripting "later on top of the same document model"; this is that later.

A script is code from whoever wrote the document. Documents are exported as `.mfk` files, will be synced (ADR 0009) and shared by link (T7.3), so opening a document means running code written by someone else. The forces:

- **Security.** A script must not reach the network, storage (OPFS, IndexedDB, other documents), the DOM, other workers or timers. It sees only what we hand it.
- **Availability.** An infinite loop, a runaway recursion or a memory bomb must fail that one feature, not hang or crash the app.
- **Determinism.** Regen results are cached by a hash of their inputs ([ADR 0004](0004-document-format.md) decision 8), documents are shared, and version history replays commands. The same script with the same inputs must give the same geometry in every browser and every session. So: no clock, no unseeded randomness, no host-dependent numerics.
- **Where the geometry is.** Scripts call modelling operations and query their results mid-run (FeatureScript's `opExtrude` followed by a query of what it created). The kernel, its shapes and the naming layer live in the regen worker ([ADR 0007](0007-worker-protocol.md) decision 1, regen README "Where it runs"), and the regen README explains why the engine does not drive the kernel across a worker boundary: every mid-regen query would be a structured-clone round trip.
- **License.** [ADR 0006](0006-licensing.md): permissive or GPLv3-compatible code may be bundled; LGPL only as a separate `.wasm`.
- **Existing extension point.** Core already has an `extension` feature kind with namespaced types, dependencies, references, expressions and opaque `params`; regen reports it as changing no geometry (`packages/regen/src/engine.ts`). A scripted feature changes geometry, so it is a feature kind of its own, not an extension.

## Evaluation

Registry facts were read from the npm registry on 2026-09-26; ADR 0006 decision 6 still requires reading the installed package before adoption. Nothing below was built or run here; the spike T7.0c measures it.

### A plain Web Worker

A dedicated worker has no DOM, and `worker.terminate()` stops any loop. But a worker has `fetch`, `WebSocket`, `importScripts`, `indexedDB`, `navigator.storage` (OPFS) and `postMessage`. Deleting those globals is not a boundary: they are reachable through prototypes and constructors, and new web APIs appear in workers over time. A Content Security Policy on the worker script's response can block network access (`connect-src`), but it depends on hosting headers and does not cover storage. Terminating the worker is the only CPU limit, and there is no memory limit. And the script's `Math.sin` is the host engine's (next section). **Not enough on its own.**

### SES (Hardened JavaScript)

[SES](https://github.com/endojs/endo/tree/master/packages/ses) (`ses` 2.3.0, Apache-2.0, GPLv3-compatible) freezes the realm's intrinsics with `lockdown()` and runs code in `Compartment`s with their own globals, which hold only the capabilities we pass ([guide](https://github.com/endojs/endo/blob/master/packages/ses/docs/guide.md)).

- **Capabilities**: strong confinement within the realm; nothing reachable unless endowed.
- **Availability**: none. The lockdown documentation, section "Availability", says "A compartment cannot protect availability for code running in sibling compartments" ([lockdown.md](https://github.com/endojs/endo/blob/master/packages/ses/docs/lockdown.md#availability)). There is no memory limit. So SES needs its own worker to be killable, and then every kernel call from a script crosses a worker boundary.
- **Determinism**: code runs on the host engine. ECMAScript specifies `Math.sin`, `Math.exp`, `Math.pow` and the rest as implementation-approximated ([ECMA-262, Function Properties of the Math Object](https://tc39.es/ecma262/#sec-function-properties-of-the-math-object)), so V8, SpiderMonkey and JavaScriptCore may return different last bits. A script that computes a spiral with `Math.cos` could produce different geometry, and different cache keys downstream, in Firefox and Chrome. We could replace `Math` with our own functions inside the compartment, but every other engine-dependent path (number formatting, `Array.prototype.sort` with an inconsistent comparator, `Intl`) would need the same scrutiny.
- **Cost**: `lockdown()` changes the whole realm it runs in, so it cannot run in the regen worker without affecting our own code there.

### ShadowRealm

[ShadowRealm](https://github.com/tc39/proposal-shadowrealm) gives a fresh global with its own built-ins and a callable boundary. It is at TC39 Stage 2.7. No browser ships it: a Node pull request to remove its experimental support says "The TC39 ShadowRealm proposal remains unimplemented by browsers" and that WPT dropped its tests ([nodejs/node#65650](https://github.com/nodejs/node/pull/65650), open as of 2026-09-22). Its explainer states that it shares the process and thread with its creator, so "resource exhaustion, or excessive allocation of memory [...] can prevent the incubator realm from proceeding", and that confidentiality "cannot be fully guaranteed" ([explainer](https://github.com/tc39/proposal-shadowrealm/blob/main/explainer.md)). **Not available, and not an availability boundary if it were.**

### QuickJS compiled to WebAssembly

[quickjs-emscripten](https://github.com/justjake/quickjs-emscripten) (0.32.0, published 2026-02-16, MIT) runs the QuickJS interpreter (Bellard's, or the QuickJS-ng fork) as a WebAssembly module.

- **Capabilities**: the interpreter has no host APIs at all. A script sees ECMAScript built-ins plus exactly the functions we install with `context.newFunction`. There is no `fetch` to delete.
- **Isolation**: QuickJS's heap is the module's linear memory. A memory-safety bug in the interpreter corrupts that memory and nothing of ours; what crosses is only what our host functions accept, so the attack surface is our binding layer, which we write and test. The README notes it "has not been audited". On isolation it says that contexts "won't leak into other contexts or runtimes (with one exception, see Asyncify)": a statement about JavaScript values, not a memory-safety boundary, since runtimes created from one module instance share its linear memory. The exception concerns the asyncified build, which decision 2 uses only if T7.0c chooses it; T7.0c reads what the exception covers before that choice.
- **Availability**: `runtime.setInterruptHandler` is called between bytecode operations and can stop a loop at a deadline; `setMemoryLimit` and `setMaxStackSize` bound the heap and recursion ([QuickJSRuntime](https://github.com/justjake/quickjs-emscripten/blob/main/doc/quickjs-emscripten/classes/QuickJSRuntime.md)). A limit hit is an exception inside the script, which we turn into a feature error.
- **Determinism**: every browser runs the same `.wasm`, including the math library compiled into it, so `Math.sin` gives the same bits everywhere. WebAssembly arithmetic is deterministic except for NaN bit patterns, relaxed SIMD, threads and resource exhaustion ([WebAssembly nondeterminism](https://github.com/WebAssembly/design/blob/main/Nondeterminism.md)); none of these reaches geometry if the build uses no relaxed SIMD and no threads and our bindings canonicalise NaN. `Date` and `Math.random` are ours to remove or replace.
- **Size**: the synchronous release variant package (`@jitl/quickjs-wasmfile-release-sync` 0.32.0) is 649,548 bytes unpacked, the QuickJS-ng one 675,582 (registry metadata; the `.wasm` alone is smaller, to be measured). The README gives about 500 KB for the default build and about twice that for the asyncified build, which is needed only if host functions must return promises.
- **Speed**: an interpreter, much slower than the host JIT for heavy arithmetic. A scripted feature's time is dominated by the kernel operations it calls, and a script that tessellates in JavaScript is the wrong script. T7.0c measures the per-call overhead of the binding.
- **License**: MIT, GPLv3-compatible, bundled like any MIT dependency; its `.wasm` is a separate asset anyway.

### Other candidates

- **`isolated-vm`** (7.0.1, ISC) is V8 isolates for Node; it does not run in a browser. Relevant only if scripts are ever evaluated on the server, which nothing plans.
- **A domain-specific language of our own** (FeatureScript is one). Full control over determinism, but a language, parser, error messages, editor support and documentation to own. JavaScript with a small API gives users a language they know. Rejected for M7.
- **An iframe with `sandbox`**. Main-thread, same event loop for CPU, and it cannot be placed in the regen worker. Rejected.

## Decision

1. **Scripts run in QuickJS compiled to WebAssembly** (quickjs-emscripten, synchronous release build, pinned exactly like libcascade in [ADR 0002](0002-kernel-build-and-loading.md) decision 1), loaded as its own `.wasm` asset on the first scripted feature, like planegcs.

   Amended 2026-10-04 after the T7.0c spike: the build is named ([amendment](#amendment-the-t70c-spike-and-the-maintainers-answers-t70d-1082), item 1).

2. **Inside the regen worker.** The script engine runs next to the regen engine, so a script's operations and queries are function calls into the same kernel session, not messages ([ADR 0007](0007-worker-protocol.md) decisions 1 and 3; regen README). It is not a fourth context. How the synchronous interpreter reaches the asynchronous `KernelService` queue (a synchronous in-regen session on the kernel, or the asyncified QuickJS build with promise-returning host functions) is decided by the spike T7.0c on measured cost; the choice does not change anything else here.

   Amended 2026-10-04 after the T7.0c spike: a synchronous kernel session, not the asyncified build ([amendment](#amendment-the-t70c-spike-and-the-maintainers-answers-t70d-1082), item 2).

3. **No ambient capabilities.** The script's global has ECMAScript built-ins minus `Date` (removed) and with `Math.random` replaced by a generator seeded from the script source hash and the feature's `seed`, an integer parameter stored in the feature (default 0) that the user can change like any other. The seed never comes from the feature id: ids are renamed when sync remaps them ([ADR 0009](0009-sync-model.md) decision 5) or a branch is merged, and the geometry must not change when they are. There are no timers, no promises that outlive a run, no module loading, no host objects: only the manufakture API of decision 6, whose functions take and return plain data (numbers, strings, arrays, objects of those) and opaque handles that are indices into a per-run table. Nothing from the kernel or the host crosses as an object.

   Amended 2026-10-04 after the T7.0c spike: how `Date` is removed, and which other globals go ([amendment](#amendment-the-t70c-spike-and-the-maintainers-answers-t70d-1082), item 3).

4. **Limits, all reported as feature errors** (errors as data, ADR 0007 decision 5): a wall-clock budget per run, checked by the interrupt handler (starting value 2 s, tuned in T7.0c), a heap limit (starting value 64 MiB) and a stack limit, a cap on kernel operations per run and on the size of any value crossing the binding. A fresh QuickJS context per feature run, and a fresh runtime per document, so no JavaScript state leaks between features or documents. Each document also gets its own WebAssembly module instance: the `.wasm` is compiled once per worker and instantiated per document whose scripts run, and a source document carried by a derived feature (from another author) counts as a separate document. Runtimes of one instance share its linear memory, so without this an interpreter memory-safety bug in one document's script could read another document's heap. T7.0c measures the cost of an instance. The regen worker's own backstop is unchanged: a stuck kernel operation is handled by the existing recycle path.

   Amended 2026-10-04 after the T7.0c spike: the interrupt handler does not bound loops of builtins, `setMemoryLimit` does not count bytes, an out-of-memory can corrupt the instance, and the stack limit must stay below the browser's; the limits are restated with measured starting values ([amendment](#amendment-the-t70c-spike-and-the-maintainers-answers-t70d-1082), items 4 to 8).

5. **Determinism rules.** A scripted feature's cache key hashes the script source, the evaluated parameters, the `seed`, the script API version, the QuickJS build identity, and the keys of the features it reads, in addition to what ADR 0004 decision 8 lists. The binding canonicalises NaN and refuses non-finite numbers in geometry. A script that returns different results for the same key is a bug in our shims, and a test runs the example scripts in Chromium, Firefox and WebKit and compares results bit for bit.

   Confirmed 2026-10-04 by the T7.0c spike, unchanged ([amendment](#amendment-the-t70c-spike-and-the-maintainers-answers-t70d-1082), item 9).

6. **A FeatureScript-like API, small at first.** A script declares its parameters as data (name, kind `length`, `angle`, `number`, `boolean`, `choice`, `reference`, default and bounds) and exports a `run(ctx, params)` function. Parameters are stored in the feature as `StoredExpression`s and references, so they take variables and units like every other field ([ADR 0005](0005-units.md)). `ctx` offers sketches from data, extrude, revolve, fillet, chamfer, shell, booleans, patterns and transforms, queries of what an operation created (FeatureScript's `qCreatedBy` idea), and measurements. Each call takes an operation id chosen by the script (`'boss'`, `'hole1'`), and result faces are named `<feature id>:<operation id>/<name>`, so references into a scripted feature are names like any other ([ADR 0004](0004-document-format.md) decisions 5 and 6; birth names are required before a feature kind lands, per ADR 0004's consequences). The name after the slash follows the kernel's grammar with one rule: a face born inside the script has no feature id of its own, so it is `<role>` or `<role>:<local id>` (`scripted#2:boss/cap:end`, `scripted#2:boss/side:s1`), where the local id is the script's own sketch id and not one of the part's `e`, `k` or `r` ids. Faces of earlier features that a script operation consumes keep their names, or appear as members of a generated name as they do in a fillet's (`scripted#2:rnd/round:extrude#1:cap:end&extrude#1:side:e2`). Core's name parser (T7.2c) reads `<feature id>:<operation id>/` as a prefix like M2's `<id>:from/`, but unlike it keeps parsing what follows: feature ids in member names there are dependencies of the scripted feature and are remapped by sync ([ADR 0009](0009-sync-model.md) decision 5), while local ids never are.
7. **TypeScript by type erasure.** Scripts may be TypeScript; the app erases types before running (`ts-blank-space` 0.9.0, Apache-2.0, or `sucrase` 3.35.1, MIT, chosen in T7.2b) and keeps the source as typed. Type checking, if any, is an editor feature, never a regen step.

   Amended 2026-10-04 after the T7.0c spike: sucrase, with the constructs it silently drops rejected first ([amendment](#amendment-the-t70c-spike-and-the-maintainers-answers-t70d-1082), item 10).

8. **Scripts are document data.** A document gets a script library (`scripts`, each with a permanent id, name, language, API version and source), and a `scripted` feature names a script and holds its parameter values and its `seed` (decision 3). Both need a format bump with a migration (ADR 0004 decision 2), taken in turn after M2's v4 to v7 and whatever M3 to M6 add.
9. **What stays open for the maintainer.** This ADR stays **proposed** until two product questions are answered: whether a document from someone else runs its scripts on open without asking (the recommendation: yes, because a script has no capabilities to abuse and the limits bound its cost; show which features are scripted and, once documents have several editors with accounts (T7.1h), by whom they were last edited; without accounts there is no author to show), and whether the API is versioned with a promise of old scripts running unchanged forever (the recommendation: yes, per API version, the same promise the file format makes).

   Answered 2026-10-04 by the maintainer: yes to both. Scripts in other people's documents run on open without asking once the human security sign-off (T7.6b) has been recorded; until then the per-document opt-in of T7.2d applies regardless. The script API is versioned, and a script written against an API version runs unchanged forever ([product decision 0001](../decisions/0001-m7-hosting-accounts-and-sharing.md), decisions 9 and 10; [amendment](#amendment-the-t70c-spike-and-the-maintainers-answers-t70d-1082), items 11 and 12). The ADR is accepted.

## Alternatives considered

- **SES in a dedicated script worker.** Strong capability confinement and the host JIT's speed, but no CPU or memory limit without terminating the worker, host-dependent `Math`, and every kernel call a round trip to the regen worker. Rejected; revisit if the interpreter is too slow for real scripts and the determinism of host `Math` can be solved by shimming.
- **A plain worker with globals removed.** Not a boundary. Rejected.
- **ShadowRealm.** Not shipped in any browser; not an availability boundary. Rejected; watch it.
- **Scripts that only emit a plan** (return a list of feature inputs with no mid-run queries). Simplest to sandbox and to cache, but a script could not ask "which edges did this extrude create" and fillet them, which is most of what makes scripted features useful. Rejected as the model; a script may of course be written this way.
- **Our own language.** Rejected for M7 (above).
- **Running scripts on the server.** There is no server before M7 and regen is local by design (ADR 0004). Rejected.

## Consequences

- One more `.wasm` asset, loaded only by documents with scripted features; its license text ships with the app (ADR 0006 decision 5) and its row goes into the license inventory.
- The binding layer is security-critical code: every host function validates its arguments as untrusted input, with tests that feed it hostile values. It needs a security review before scripted features are enabled by default (flagged in the M7 plan).
- Scripts are slower than native JavaScript. Budgets in T7.0c and T7.2 acceptance tell users what to expect; heavy computation belongs in operations we provide, not in the script.
- Naming inside scripts depends on the operation ids scripts choose. A script that renames an operation id breaks references into it, like renaming a sketch entity would; the API documentation must say so.
- The API is a compatibility promise. Every addition is additive under an API version; a breaking change is a new version with the old one kept.
- If the spike T7.0c finds the synchronous kernel session impractical, the asyncified QuickJS build doubles the `.wasm` size and adds a cost per host call; the rest of this decision stands.

## Amendment: the T7.0c spike and the maintainer's answers (T7.0d, #1082)

Amended 2026-10-04 after the T7.0c spike. The [T7.0c spike](../spikes/T7.0c-quickjs.md) ran quickjs-emscripten 0.32.0 in a module worker next to the kernel in Node, Chromium, Firefox and WebKit. It confirmed the choice of QuickJS in WebAssembly, the per-document instance and the determinism rules, settled decision 2's open mechanism, and contradicted three assumptions of decision 4: that the interrupt handler bounds run time, that `setMemoryLimit` bounds the heap, and that a limit hit leaves the interpreter usable. The decisions are restated below where the evidence changes them; everything else stands as written. The ADR is accepted with this amendment; the maintainer's answers to decision 9 are in [product decision 0001](../decisions/0001-m7-hosting-accounts-and-sharing.md).

1. **Decision 1: the build.** The sync release build of Bellard's QuickJS: `@jitl/quickjs-wasmfile-release-sync` 0.32.0 with `quickjs-emscripten-core` 0.32.0, both pinned exactly. Its `.wasm` is 503,134 bytes raw and 199,016 brotli; the first scripted feature in a worker (fetch, compile, instantiate, first run) costs 15 to 27 ms. The QuickJS-ng variant gave the same bits but was 15 to 30 % slower and 13 KB larger; nothing needed its extras.
2. **Decision 2: a synchronous kernel session.** Host functions call the regen worker's synchronous `Kernel` directly; the asyncified build is not used. The synchronous path was never slower: equal for boolean-heavy scripts (24 cuts: 69 to 81 ms against 72 to 92), 42 to 121 µs cheaper per kernel call in the browsers, 5 to 23 times cheaper per plain host call (0.8 to 2.3 µs), and smaller. For anyone revisiting asyncify: the README's exception to context isolation covers **suspension**, not values. All runtimes and contexts of one asyncified module share one suspended stack, so two of them awaiting host calls at once fail with `Already suspended`, as does a host function that re-enters and suspends; in 0.32.0, disposing an asyncified runtime that held a host function also throws. The cost of the synchronous path: a script run holds the worker for its whole duration, so ADR 0007's cancellation by generation cannot stop a script between kernel calls; only the limits can. T7.2c adds a session API on `KernelService` that runs a synchronous function in the service's exclusive slot, owning the shapes it makes.
3. **Decision 3: removing globals.** `Date` is removed through the context's intrinsics when the context is made, not deleted afterwards. `SharedArrayBuffer` (QuickJS's own, with no threads behind it) is removed from the global too; whether `eval` and `Function` stay is T7.2b's call. The Emscripten glue does call the host clock, but with `Date` removed and `Math.random` replaced, no script-visible value depended on it.
4. **Decision 4, time: the interrupt handler is a soft bound.** It stopped every loop of script code within 2 ms of the deadline (5 ms in one WebKit case), but QuickJS polls it on a counter of bytecode steps, not on time, so a loop of builtins overruns: a loop of `sort()` on 20,000 numbers ran 8.4 to 11.9 s past a 100 ms deadline, a loop of JSON round trips 1.7 to 3.2 s, in every browser. The 2 s budget stays, checked by the interrupt handler **and** at the start of every host call. The hard bound is terminating the regen worker: the main thread terminates and recycles it when a regen request has not answered for 10 s (an estimate; T7.2e tests it), the last resort ADR 0007 decision 4 already names.
5. **Decision 4, heap: the `WebAssembly.Memory` maximum is the limit.** In these builds QuickJS reports `malloc_usable_size unavailable`, so `setMemoryLimit` cannot count bytes: with a 64 MiB limit one script grew the instance to the 2 GiB maximum, another to 429 MiB. Each instance therefore gets a `WebAssembly.Memory` whose maximum is 1,280 pages (the 16 MiB the `.wasm` needs plus 64 MiB); every allocation bomb stopped at 79.9 MiB in 36 to 263 ms. `setMemoryLimit(64 MiB)` stays as well, since it refuses single huge allocations at once.
6. **Decision 4: after an out-of-memory, the instance is dropped.** One bomb (many small objects in a `Map`) throws `null` instead of an Error and leaves the whole instance unusable: a new runtime in it failed in Node and all three browsers, a new context in the old runtime trapped, and in an earlier run touching it crashed a Chromium page. So after an out-of-memory, or a thrown `null` or other non-Error where the context says so, the document's instance is discarded, not just its runtime, and the error is mapped to the heap-limit error. A new instance costs about 1 ms. This is the per-document instance of decision 4 paying off: the corruption stays in one document's memory.
7. **Decision 4, stack: 128 KiB, below the browser's stack.** Deep recursion overflowed Chromium's worker stack before QuickJS's own check at a limit of 192 KiB (QuickJS-ng) or 256 KiB (QuickJS); at 128 KiB (about 680 frames of a three-argument function) QuickJS's check fired first everywhere. A host `RangeError` or `too much recursion` escaping the interpreter is treated as the stack-limit error and the instance is dropped.
8. **Decision 4: the other starting limits and instance memory.** 1,000 kernel operations and 100,000 host calls per run; values crossing the binding at most a 1 MiB string or 100,000 array elements (any depth), in both directions. One more instance from the compiled module costs 0.5 to 2 ms and 16 MiB of linear memory, which never shrinks, so a document's instance is dropped at an idle point once its memory passes 32 MiB (an estimate). T7.2b may tune these values; they are starting points.
9. **Decision 5: confirmed.** Of 18,143 values (Math functions, `Math.pow`, number formatting, sorts), QuickJS gave the same bits in Node, Chromium, Firefox and WebKit, and the same as QuickJS-ng; the host engines differed from each other in 646 to 1,234 values, and Node 26 from Chromium 153 (both V8) in 632. The `.wasm` has no SIMD, no relaxed SIMD, no atomics and no shared memory. The binding canonicalises NaN in both directions (QuickJS's NaN differs from the x86 hosts' in its sign bit). The spike's determinism script seeds T7.2e's cross-browser test.
10. **Decision 7: sucrase 3.35.1 (MIT).** 38,384 bytes brotli against 734,865 for ts-blank-space 0.9.0, which bundles the TypeScript compiler; both keep lines and columns of erasable code, and sucrase compiles `enum`, which users write. Sucrase silently drops `namespace` blocks and `import x = require()`, so T7.2b rejects `namespace`, `module` blocks and `import ... = require` before erasing, and documents that `enum` and parameter properties move columns on their own lines.
11. **Decision 9, scripts on open: yes, after the sign-off.** Once T7.6b's security sign-off has been recorded, scripts in a document from someone else run on open without asking, and T7.2d's setting **Run scripts in documents automatically** defaults to on. Until then the per-document opt-in of T7.2d applies, whatever the document's origin. M7 has no accounts (T7.1h skipped), so the app shows which features are scripted, not who last edited them.
12. **Decision 9, API versions: a permanent promise.** Each script records its API version (decision 8), and a script written against an API version runs unchanged, with the same results, forever: the same promise the file format makes (ADR 0004 decision 2). Additions within a version are additive; a breaking change is a new version, with every old one kept. The API version is already part of the cache key (decision 5).

Consequences added by this amendment: a running script cannot be cancelled by generation, only by its limits or by terminating the worker; the session API on `KernelService` is new work in T7.2c; scripts are 30 to 45 times slower than V8 on arithmetic loops (1,000,000 iterations: 84 ms against 2.5 ms in Chromium), which the user docs should say; and T7.2b's tests include the three cases the spike found: a loop of `sort()`, the `Map` bomb, and a stack limit above Chromium's.
