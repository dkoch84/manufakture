# 0015: The construction domain: walls, openings, floors and roofs as extensions, framing members as data

- Status: accepted
- Date: 2026-10-03

## Context

M6 makes manufakture useful to someone framing a small building: levels, walls as layer stacks, doors and windows with headers, floors with joists, gable and hip roofs at a pitch typed as `6/12`, a framing generator, a lumber takeoff, and plan and elevation drawings ([M6 plan](../plans/m6.md)). The milestone is accepted when a 12' x 16' shed is framed and its takeoff matches a hand calculation. The plan's Part 2 lists eleven design decisions written for this ADR to confirm or change (task T6.0a). This ADR records them before the domain's code, so the generators (T6.2a to T6.2c), the domain data (T6.1a), the member sets (T6.5b), the features (T6.1b, T6.1c), the viewport (T6.5c), the takeoff (T6.3a) and the drawings (T6.4a) share one design.

The inputs:

- **The [M6 plan](../plans/m6.md)**: Part 1's research (what thousands of members cost, manifold-3d and web-ifc, framing rules of thumb with their sources, roof pitch math), Part 2's decisions 1 to 11, its open questions, and the T6.0a task section.
- **The [T6.5a spike](../spikes/T6.5a-framing.md)** (done 2026-10-03), which measured three representations on a scripted shed (147 members) and a 2,000 sq ft house (834 members). A B-rep body per member (A) took 5,483 ms cold for the house and left about 42 MiB of kernel heap per regen, so the 1 GiB recycle came after 22 regens. Member data with meshes computed in TypeScript (B) took 12.9 ms cold and 0.66 ms after moving one opening; Manifold for the cut members (C) added 39 ms cold and nothing warm. Manifold's `delete()` frees memory. Instancing cut the house's draw calls from 996 to 137, per-instance picking agreed with raycasting on 200 of 200 picks, LOD was not needed at house scale, and member B-reps on demand took 4,072 ms for the whole house. It recommends B with Manifold for cut members, refines the member shape, and revises the budgets.
- **[ADR 0013](0013-domain-packages.md)** and what M4 built on it. A domain is a package `packages/domain-<name>` that depends at run time only on `core`, `units` and shared domain packages, and never imports another domain (decision 1). Domain geometry is an `extension` feature with a translator (decisions 2 and 5); plain settings go into the namespaced `domains` field, which holds "settings, not model": no feature or body ids, no face names, no variable uses (decision 3). One extension may make several bodies named `<feature id>:<key>` (decision 6). Derived results are never stored; a translator may return `metadata` that later extensions of its namespace read through `dependsOn` (decisions 5 and 7). The takeoff is a shared package, `packages/takeoff`, with rows of `{ item, stock, size, quantity, unit, extended, sources }` (decision 8). As landed: `packages/domain-wood` holds the stock catalog (`STOCK`, `findStock`, `resolveStock`) and owns the `stock` namespace; `packages/takeoff` holds the row model; `packages/nesting` holds the 1D and 2D layouts and has no dependencies; regen's extension contract (`packages/regen/src/extensions.ts`) has translators that return kernel inputs and metadata, and domains that declare which namespaces they read. ADR 0013's consequences leave two conflicts with the M6 plan for this ADR: variables in domain data (a level elevation using a variable) and feature ids in params (per-member overrides keyed by ids that embed an opening's feature id).
- **[ADR 0004](0004-document-format.md)**: nothing derived is stored (decision 1); every change of shape bumps `version` (decision 2); ids are permanent (decision 4); references are names with the outcomes `exact` to `lost` (decisions 5 and 6); numbers are `StoredExpression`s (decision 7); cache keys cover inputs and an implementation version (decision 8).
- **[ADR 0005](0005-units.md)** and its amendment (T6.0b): `rise:run` is a pitch in any expression, `6/12` is a pitch in slope fields only (`EvaluateOptions.slope`), and percent slopes (`25%`) are accepted in slope fields only.
- **[ADR 0006](0006-licensing.md)**: the dependency allowlist (Apache-2.0 and MPL-2.0 allowed, MPL files not marked "Incompatible With Secondary Licenses"), and licenses read from the installed package (decision 6). Its inventory lists manifold and web-ifc as "none yet, unverified".
- **The drawing model as M4 landed it** (`packages/core/src/schema.ts`, format version 12): a view's source is a part (all bodies or listed ones) or an assembly; dimensions are linear, radius, diameter or angle, with model references only. The generic domain view source, domain reference kind and `chain` dimension kind that the M6 plan asked of T4.4c were not added.
- **The [M4 plan](../plans/m4.md)**: the catalog, the `tools` input (T4.2a), the takeoff and nesting (T4.3a, T4.3c), the cut list panel (T4.3d) and the drawing tasks (T4.4b to T4.4g) M6 builds on.
- **The project owner's decisions for M6**: new documents ship no header rules (the plan's open question, option A); the disclaimer text is drafted in T6.0c and reworded by the owner in a follow-up; the takeoff shows the as-framed count only, with no estimating rule-of-thumb row; percent slopes are accepted in slope fields (landed in ADR 0005's amendment); IFC export (T6.6a) is built in this epic as a stretch, with web-ifc.

## Decision

1. **A domain package, `packages/domain-construction`**, pure TypeScript under GPL-3.0-or-later, owning the `construction` namespace, under ADR 0013 decision 1 unchanged.
   - **Run-time dependencies**: `@manufakture/core`, `@manufakture/units`, and the shared packages `@manufakture/takeoff` (the row model, ADR 0013 decision 8), `@manufakture/nesting` (1D lengths and 2D sheet layouts for the takeoff) and `@manufakture/stock` (below). `@manufakture/regen` and `@manufakture/kernel` are type-only devDependencies, as in `domain-wood`. It never imports `domain-wood`, and nothing in it loads a `.wasm`, so the generators and the takeoff run in Node tests. Manifold is not a dependency of the domain package: meshing is regen's (decision 5).
   - **The stock catalog moves into a shared package, `packages/stock`**, as ADR 0013 decisions 1 and 3 require once a second domain needs it. It takes `domain-wood`'s catalog (`STOCK`, `findStock`, `stockByRegion`, `defaultRegion`), the `stock` namespace's schema, migrations, reader and writer, and `resolveStock`. It depends on `core` and `units` only. `domain-wood` imports from it and keeps re-exporting what its users import today, so no caller breaks. The namespace name stays `stock`, so no document changes. Because a namespace's reader is registered with regen through a domain (`ExtensionDomain.data`), `packages/stock` exports a data-only registration (namespace `stock`, no extension types) that the regen worker's entry registers next to wood and construction; `domain-wood` then declares `reads: ['stock']` and stops owning it. T6.1a does the move, since it is the first task that needs the catalog.
   - **Construction stock is added to the shared catalog itself**, not through a per-domain extension point: precut studs (92-5/8", 104-5/8"), 7/16" OSB sheathing, and 1/2" and 5/8" gypsum board in 4' x 8' and 4' x 12', each with its `source` and `verified` flags (Part 1 marks the precut and gypsum sizes unverified). Gypsum needs a catalog category and a core material it does not have yet; T6.1a adds the category and maps gypsum to the nearest existing material until a material is added, as the catalog already does for OSB.
   - **Takeoff**: construction's producers emit `TakeoffRow`s into `packages/takeoff`'s model (decision 10). No second takeoff mechanism.

2. **Four extension types, and one namespace of domain data.**
   - `construction.wall`, `construction.opening`, `construction.floor` and `construction.roof` are `extension` features (ADR 0013 decision 2), each with its own `schemaVersion` and params migrations, ids `extension#n`, labels from the domain ("Wall 3", "Window 1"). Every feature an extension reads is in `dependsOn` (an opening names its host wall, a roof the walls it bears on, a floor the walls or the sketch it follows), every typed number is in `expressions`, and `params` holds no feature id, face name or expression (decision 6 says where the opening's wall and the members' ids go).
   - **`domains.construction`** (version 1, T6.1a) holds the document-level construction settings: levels, wall types (the layer stack and the stud layer's stock, spacing and plate counts), floor and roof types, framing settings (document defaults a wall may override) and the header rules (decision 7). Stock ids in it are catalog ids, which are data, not model ids.
   - **Levels are constant settings in M6** (this resolves ADR 0013's first conflict). A level is `{ id, name, elevation, height }`, with `elevation` and `height` as `StoredExpression`s that must be constants (`8'`, `2.4m`); one that names a variable is refused, as `domains.stock` refuses one. A level is not a part studio: a building is one part studio (M2 multi-body), so every layer body, member and opening shares one regen and one reference namespace. Variables reach construction geometry through the features' own expressions: a wall's `height`, an opening's position and size, a roof's pitch and overhangs. So a configuration row (T2.4a) can still vary a shed's length or wall height. T6.1a's acceptance case "a level elevation expression using a variable" becomes "a variable in a level's elevation is refused with the domain's message". If levels need variables later, ADR 0013's alternative (an optional `expressions` record on `DomainData`) is the way, with its own format bump, recorded as an amendment there.
   - **One part studio is enough for M6.** T6.5a framed the whole house in 52 ms cold with Manifold; nothing measured asks for one part studio per level. The plan's open question is closed for M6 and reopens if T6.5d's multi-storey numbers miss their budgets.

3. **Wall layers are bodies.** Sheathing, drywall and optional siding are B-rep bodies made by the wall's translator: one extruded rectangle per layer and wall segment, mitred or butted at corners. They are few and large, so they get names, references and hidden-line drawings like any body. One wall makes several bodies, named `<feature id>:layer/<layer id>` (`extension#3:layer/sheathing`), the form ADR 0013 decision 6 allows and T4.1a's validation accepts. An opening cuts them through the generic `tools` input (T4.2a), with the host wall's layer bodies in its `scope` (ADR 0013 decision 6: every body it changes is listed).

4. **Framing members are data, not bodies** (T6.5a, recommendation 1; the plan's decision 4, confirmed with the spike's refinements). The shape, as T6.5a measured it:

   ```ts
   interface Member {
     id: string; // local to its owner: 's12', 'top1:2', 'king-l' (decision 6)
     owner: string; // the feature that owns it: a wall, an opening, a floor or a roof
     role: Role; // stud, plate, king, jack, header, sill, cripple, blocking, joist, rim, rafter, hip, ...
     stock: StockRef; // catalog entry (with overrides): nominal name, dressed width and depth
     length: number; // the blank along local x, mm: what is cut from stock
     placement: { origin: Vec3; x: Vec3; y: Vec3 }; // rotation and translation only, right-handed
     cuts: Cut[]; // in the member's own frame
   }
   type Cut =
     | { kind: 'plane'; n: Vec3; k: number } // removes dot(n, p) >= k: plumb, seat, bevel, side cuts
     | { kind: 'notch'; a: Plane; b: Plane }; // removes the intersection of two half-spaces: a birdsmouth
   ```

   - **Cuts are in the member's local frame**, so two members of one stock, length and cuts are one shape wherever they are placed. **No mirroring**: a mirrored member is a different shape with its own key, since a negative-determinant instance matrix flips the triangles' winding. **`length` is the blank**; a cut length is derived where a takeoff or a drawing wants it. **A birdsmouth is one `notch`**, as a framer marks it. A generator drops a cut that removes nothing and never emits two members in the same space; T6.2a's property tests check every member, cut or not (the spike checked only uncut ones, and its overlapping tee studs showed up as disagreeing picks).
   - Members have **no B-rep, no face names and cannot be referenced by features** in M6. A member is picked as a whole, identified by its full id (decision 6), and the info panel shows its stock, length and cuts from the data. The measure tool works on layer bodies only.
   - **B-reps of members are built on demand only**: STEP export of framing, and drawing views that need hidden lines through members. They are built in batches per owner, used and released at once, with cancellation between batches, and go through the kernel's normal recycle check; member B-reps are never kept between requests (T6.5a memory rule 4). The whole house took 4,072 ms to build and 825 ms more for one STEP file, and left about 40 MiB behind: acceptable for an export with progress.
   - **STL and 3MF export** of a building include the members as their shared meshes under their transforms: one object per member in 3MF (named by its full id), appended to the triangle soup in STL. That is why cut members need closed shells (decision 5).

5. **Members are produced by the domain from its features' metadata, and meshed and shared in the regen worker.** This changes how the plan's decision 4 and T6.5b get members out of regen, because the plan's own pieces do not fit together otherwise: the wall frames its openings (kings, jacks, cripples on the wall's layout, plates stopped at doors), but an opening is a later feature that depends on its wall, and a translator can only read the extensions it names in `dependsOn`, which come before it.
   - **Translators build bodies and report framing inputs.** Each construction translator returns its kernel inputs (layer bodies, opening cuts) as ADR 0013 decision 5 says, plus its framing input as `metadata` (decision 7 of ADR 0013): a wall its segments, joins, resolved settings and stud stock; an opening its position, rough opening, sill and resolved header; a floor and a roof theirs. Metadata is recomputed on every regen and never stored.
   - **A member stage after the part's features.** The domain's registration (`ExtensionDomain`) gains one optional entry, a pure member producer, which regen calls after a part's features have regenerated, with the metadata of that part's construction features. It frames by **group**: a wall with every opening that names it and is not suppressed, a floor, a roof (with the walls it bears on). Each group runs the pure generators (T6.2a to T6.2c) and returns members. It is the same registry and the same purity and containment rules as translators (a throw becomes an error on the group's features, never a failed regen), not a second extension mechanism; it replaces the plan's "optional `members` output" on the translator result.
   - **Caching per group**, keyed by the group's metadata, the domain data it reads, the stock sizes it uses and the domain's implementation version (ADR 0004 decision 8). Moving an opening misses only its wall's group. T6.5a measured that case at 0.63 ms for the house.
   - **Meshing and sharing** (T6.5a recommendation 3). Members with no cuts are 12-triangle boxes computed in TypeScript; members with cuts are meshed by Manifold (decision 9) as closed shells. The shape key is the stock, the blank length rounded to 0.001 mm and the sorted local cuts (normals to 1e-5, offsets to 0.001 mm); placement is never part of it. There is one mesh cache per regen worker, shared by all groups and kept across regens: a regen meshes only keys it lacks and prunes keys no member uses. A mesh crosses to the main thread once, when its key is new; a group's regen sends its instance lists (full ids, roles, one transferred `Float32Array` of matrices). T6.5a measured 147 members to 33 shapes for the shed and 834 to 108 for the house.
   - **Memory rules for T6.5b** (T6.5a recommendation 5): members never enter the kernel's arena in a regen; member sets are plain data (64 bytes of matrix a member); Manifold is one module per regen worker, loaded on the first member with a cut, with every Manifold object, intermediates included, deleted in a `finally` right after `getMesh`; on-demand member B-reps follow decision 4; T6.5d measures memory with `heapInUse` from `@manufakture/kernel/testing`.
   - **Drawing them** (T6.5c): an `InstancedMesh` per role and shape, picked through a per-instance id in the existing pick pass (a reserved id range so instance ids never collide with face ids), edges as one `LineSegments` per group. No LOD at first: hiding blocking and cripples saved 0.3 ms of 20 in the spike; turning edges off beyond a distance (a quarter of the SwiftShader frame) is the first LOD rule to add if a GPU measurement asks for it. `BatchedMesh` is the fallback if draw calls turn out to matter on a GPU.

6. **Member and layer ids: stable by role and layout, and fragile.**
   - **A member's full id is `<owner feature id>:<local id>`.** Layout members belong to their wall: a stud by its layout slot (`extension#3:s12`, the 12th slot from the wall's start), plates by course and piece (`extension#3:top1:2`), corners and blocking by the forms T6.2a defines. Opening members belong to the **opening**, not the wall: `extension#7:king-l`, `extension#7:jack-r`, `extension#7:header`, `extension#7:cripple-a2`. Floors and roofs name theirs the same way (`extension#9:j7`). This drops the plan's double form `extension#3:extension#7:king-l`: an id names exactly one feature, always at its front, where M7's remap already looks for the `<feature id>:<suffix>` form. A local id may itself contain a colon (`top1:2`), so parsers split at the first colon only.
   - **Per-member overrides are domain params of the owner, keyed by local id** (the plan's decision 8): delete a member, change its stock, nudge a stud. A wall's overrides name `s12` or `top1:2`; an opening's name `king-l` or `header`. No params hold a feature id, which resolves ADR 0013's second conflict, and M7's id remap needs nothing inside `params`. Anything more than an override (a hand-framed detail) is ordinary bodies in the same part studio, which the takeoff counts through the cut list.
   - **What keeps an id, and what loses it.** Lengthening a wall adds slots at the end and keeps the others. An opening hides the layout members in its way; moving it brings them back under their old ids, and its own members keep theirs. Changing a wall's spacing, layout origin or direction renumbers its slots. An override whose member no longer exists reports `lost`, like any reference, and is shown on its feature; nothing else in the document refers to a member.
   - **Layer body ids** are `<feature id>:layer/<layer id>`, with the layer id from the wall type. They follow body rules: references to layer faces resolve with ADR 0004's outcomes, and removing a layer from a wall type loses them.
   - **Naming forms for M7** (M7 T7.1a): the layer body form and the `<feature id>:<local id>` member form, each documented in core's README by the task that defines it (T6.1b and T6.2a, as the plan's "Schema versions" section assigns), and added to core's name parser and remap with their tests if T7.1a has landed by then.

7. **The user chooses every structural size; new documents ship no header rules.**
   - Wall types name the stud stock, plate counts and spacing; floor and roof types name joist, rafter, ridge and hip stock and spacing. Every default is a layout default from common practice (16" on centre, one bottom and two top plates, top plate splices at least 24" apart), documented with its source; none is a sizing.
   - **Header rules** (`opening width up to X: header Y, jack studs N`) are a user-edited table in `domains.construction`. **A new document has none**, and the editor offers no template rows, no code values and nothing that reads as a sizing table (the project owner's decision, the plan's option A). **A new wall type asks for one default header** (stock, plies, jack count) when it is created. An opening's header is, in order: its own explicit header, else the first header rule covering its width, else its wall type's default. **Every opening shows which one it used** (the header rule for widths up to 48", the wall type's default, or set on this opening). When rules exist and an opening is wider than all of them, it uses the default and shows a layout warning.
   - **No load tables ship, in any form**: not in the app, the catalog, the defaults or the user docs. Load-based tables are copyrighted, depend on loads the app does not know, and their use is an engineering judgement (Part 1).
   - **Warnings are layout warnings, labelled rules of thumb**, with the code `rule-of-thumb` that `domain-wood`'s joints already use: an opening wider than any header rule; a roof below 3/12 without ceiling joists or ties (a ridge beam may be needed); a birdsmouth deeper than a third of the rafter. None says a structure is adequate or inadequate.

8. **manufakture is not an engineering tool, and says so.** It lays out framing by rules the user chooses and does no structural calculation: no loads, spans, member sizing, bracing assessment or code compliance check, and nothing it produces says a structure is safe or legal. T6.0c writes the disclaimer, a short form and a long form; the long form opens `docs/user/construction.md`, and the short form is one constant exported by `packages/domain-construction` (`src/disclaimer.ts`), shown in the construction tools (once per document and in their help), every drawing title block (T6.4a), every takeoff export (T6.3b), the IFC header (T6.6a) and the user docs. T6.0c's agent drafts the text and the project owner rewords it in a follow-up, so this ADR fixes where the text appears and what it must cover (the list in the plan's T6.0c), not its wording. The UI never labels anything "safe", "compliant", "OK" or "passes" for a structural property, and reviewers of every M6 task check that.

9. **Code references are cited by section, never copied.**
   - The app and its docs name the International Residential Code by edition and section (R602.3(5) for stud spacing, R602.3.2 for top plates, R602.7 for headers, R802.4.1 for rafter spans, R802.3 for the ridge, R602.10 for bracing) as places for the reader to look. No table, value or text of the code is shipped, quoted in the UI, or used as data.
   - **The Part 1 figures stay unverified.** The plan read them through a summarising fetch of a state adoption on UpCodes, and ICC's own site refused the fetch. This ADR could not re-read them against a primary source: no fetch of ICC's or UpCodes' text was possible in this task. They remain marked unverified in the plan, none is used as data (decision 7), and user documentation cites section numbers only; a task that wants to quote a figure re-reads it from the code's text first and cites the edition and the adopting jurisdiction.
   - Part 1's own layout sources (Fine Homebuilding on stud layout) back the generator's layout defaults, cited in `packages/domain-construction/README.md` next to each default.

10. **The takeoff is producers on M4's model, as framed.** Construction's producers (T6.3a) add rows to `packages/takeoff`: framing members grouped by stock and cut length, then assigned to lengths sold through the 1D layout (`packages/nesting`, with kerf) or to precut studs where they match; plates, blocking and fascia also in linear feet; sheathing, subfloor, roof sheathing and drywall as sheets from a per-face layout with offcuts reused through the 2D packer; per-level and per-feature subtotals; cost from the stock overrides' prices, with rows lacking a price flagged. **Only the as-framed count is shown**: no "one stud per foot" estimating row (the project owner's decision; the plan's open question is closed). Each row's `sources` name the members' full ids or the layer bodies. Hardware (nails, hangers, anchors) is out of scope. Every export carries the short disclaimer (decision 8).

11. **Construction drawings are mostly analytic.**
    - A **framing elevation** is a wall's members projected onto its plane: rectangles and cut lines computed from member data, with no hidden-line removal. A **floor plan** is a horizontal section at the level's cut height (default 4'): layer bodies cut by M4's section path (T4.4b) plus member sections computed from member data. **Building elevations** use hidden-line removal on layer bodies, which are few and large. A **roof framing plan** is members projected from above. All of it feeds `packages/drawing`'s input types, with door swings and window symbols in plans and a **pitch symbol** (a right triangle marked `12` and `p`, formatted by `packages/units` as ADR 0005's amendment describes).
    - **Dimension strings are derived, never stored.** M4's dimensions (T4.4c, as landed) have model references only and no `chain` kind, so by the plan's own fallback rule, T6.4a computes chained strings (overall, openings by centreline or rough opening, stud layout) from wall, opening and member data at every drawing regen; a view's settings select which strings it shows; and a "convert to dimensions" action turns one into ordinary dimensions on layer faces for a user who wants to edit it.
    - **View sources.** A plan maps onto an existing part view (`top`, with a section at the cut height), and building elevations onto standard views. A framing elevation of one wall and a roof framing plan need a source the landed `ViewSource` cannot express (one wall's or one roof's members). If T6.4a finds no way to express them with the existing sources, it adds a namespaced domain view source with one format bump, serialised with every other schema task as the plan's "Schema versions" section says. That is the only format bump M6 may take.

12. **What M6 does not do.** Load, span, bracing and code checks of any kind; member sizing, engineered lumber sizing; trusses (perhaps placeholder members later); stairs and floor openings; dormers, valleys, unequal pitches and irregular roof footprints; foundations beyond skids and a slab outline; insulation, MEP and finishes; face references to members; hardware takeoff; buildings spread over several part studios.

13. **Third-party libraries.**
    - **Manifold is adopted** (T6.5a recommendation 7): manifold-3d, Apache-2.0, read from the installed 3.5.4 package by the spike. It is loaded lazily in the regen worker as its own `.wasm` asset, so a document with no cut members never downloads it. T6.5b pins it exactly, updates ADR 0006's inventory row from "none yet, unverified", adds its notice, and decides whether the package's install footprint (tooling dependencies that `manifold.js` never imports) is acceptable or whether to vendor its two files with their license.
    - **IFC export (T6.6a) is built in this epic as a stretch, with web-ifc** (MPL-2.0, per Part 1), loaded lazily in the regen worker on export only, single-threaded, pinned exactly. Re-checking its license and its bundled C++ libraries against ADR 0006, and updating the inventory, is that task's job. GlobalIds are derived deterministically from document and element ids. An own IFC-SPF writer, with web-ifc kept as a development-only reader, remains the fallback the plan describes.

## Alternatives considered

- **A B-rep body per member** (T6.5a representation A). Members would be ordinary bodies with names and references for free. Measured: 5.5 s cold for the house before any layer or opening, 4.8 MiB transferred per regen, a kernel recycle every 22 regens, and 996 draw calls. Rejected for decision 4.
- **Our own convex planar clip instead of Manifold for cut members.** 27 times faster per shape, but a notched member comes out as two convex pieces sharing an inner face, which is not a closed shell and so cannot go into STL or 3MF without welding, and every new kind of cut would need more geometry code. Manifold's extra cost is paid once per new shape (0.2 ms) and is cached. Rejected.
- **Members as the output of each feature's translator**, the plan's T6.5b design, with openings either reaching into their wall's set or listing the wall members they hide and replace. A wall cannot read its openings (they come after it), and an opening that edits its wall's set from outside breaks down at the first plate stopped by two doors and at cripples that must stay on the wall's layout. Rejected for the member stage of decision 5, which frames a wall and its openings together.
- **Openings as entries in the wall's params instead of features.** One translator would see everything, and opening member ids would carry no feature id. But openings would lose what features give them (their own row in the tree, suppression, `dependsOn`, their own `schemaVersion`), their expressions would be crowded into the wall's, and the plan's four types would become three. Rejected; the member stage gives the same framing with four types.
- **Opening member ids under their wall** (`extension#3:extension#7:king-l`, the plan's form). It embeds a second feature id that M7's remap would have to find, and puts overrides of opening members into the wall's params, which ADR 0013 decision 2 forbids. Rejected for owner-based ids (decision 6).
- **Variables in levels now**, through an optional `expressions` record on `DomainData`. It would let a level's elevation follow `#floor_height`, at the cost of a format bump and of core reaching into domain data. Not adopted in M6: the features' own expressions already take variables, and the change stays additive for later (decision 2).
- **Shipping header rules, or a template of empty rows citing the IRC.** Either makes the app look like it sizes headers, and a template invites copying code tables into a document. Rejected by the project owner's decision (decision 7).
- **An estimating row (one stud per foot of wall) next to the as-framed count.** Lumber yards quote that way, but it is a second number for the same thing, and a rule of thumb shown as a quantity. Rejected by the project owner's decision (decision 10).
- **Construction stock through an extension point in `domain-wood`'s catalog.** It would make construction depend on `domain-wood`, which ADR 0013 decision 1 forbids. Rejected for the shared `packages/stock` (decision 1).
- **A separate construction workspace.** Walls, openings, floors and roofs are features in a part studio's feature list, so T6.1d builds a **Construction** toolbar group and panels (levels, wall types, takeoff) in the part studio, not a workspace of its own as CAM and drawings have.
- **Stored dimension strings** through a `chain` kind and domain references. Would need the core additions T4.4c did not make, and a format bump for each. Rejected for derived strings (decision 11).

## Consequences

- T6.1a to T6.6a cite this ADR. The plan's Part 2 decisions hold as recorded here, with these changes: members come from a domain member stage, not from the translator result (decision 5, which changes T6.5b's scope); opening members belong to the opening and every member id has one feature id at its front (decision 6, which changes T6.2a's id forms and T6.1b's override keys); levels are constants (decision 2, which changes one T6.1a acceptance case); header rules ship empty (decision 7); the takeoff shows the as-framed count only (decision 10); and dimension strings are derived (decision 11).
- **T6.1a moves the stock catalog and the `stock` namespace into `packages/stock`**, keeps `domain-wood`'s exports working, and changes `domain-wood`'s registration to read `stock` instead of owning it. The `domain-wood` tests must pass unchanged. The M4 plan's owner is asked to review that move and every part of this ADR that leans on T4.0a to T4.4g.
- **Regen gains the member stage** (T6.5b): an optional member producer on `ExtensionDomain`, a `MemberSetResult` next to `BodyResult` in `PartResult`, the worker-wide mesh cache, and on-demand member B-reps through the kernel at the client's latest generation. Regen's README documents it.
- **Wall type edits must keep openings' scopes right.** An opening lists its wall's layer bodies in `scope`, so adding or removing a layer in a wall type updates the scopes of the openings it hosts in the same command (T6.1d).
- **The format.** M6's features and settings need no bump (ADR 0013's T4.1a covered `extension` bodies and `domains`). The one possible bump is T6.4a's domain view source (decision 11).
- **ADR 0006** gains verified rows for manifold-3d (T6.5b) and, if T6.6a lands, web-ifc and its bundled libraries. **ADR 0013** is unchanged: this ADR settles the two conflicts its consequences left for M6, and its decisions 1 and 3 are the reason for `packages/stock`. **ADR 0005** is unchanged; its amendment already covers pitch and percent slopes.
- The Part 1 IRC figures remain secondary and unverified (decision 9). Anyone who wants one in user documentation re-reads it from the code's text first.
- Defaults follow North American practice because the acceptance case is imperial. Metric framing (400 and 600 mm centres, CLS lumber) is covered only as far as spacing and stock are settings and the catalog has metric entries.
