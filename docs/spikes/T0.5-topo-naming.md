# T0.5 spike: topological naming via OCCT history

- Status: done
- Date: 2026-09-26
- Code: [`spikes/topo-naming/`](../../spikes/topo-naming/)
- Builds on: [T0.3](T0.3-wrapper.md) and [ADR 0001](../adr/0001-kernel-wrapper.md) (own thin wrapper on libcascade 3.0.2), [T0.2](T0.2-occt.md) (memory conventions)

## Summary

References to faces and edges can survive upstream edits with names built from OCCT history, as long as edges are named by their faces and every resolution that is not exact, or that rests on a positional name, is reported rather than hidden.

- **Faces are named at birth and carried by history.** An extrusion names its caps and the face swept by each sketch entity (`extrude#1:cap:end`, `extrude#1:side:e2`). Booleans and fillets pass each name on through OCCT's kept / `Modified` / `Generated` history, and a fillet names the face it makes after its own reference (`fillet#3:round:r1`). No result face was left without a name in any scenario.
- **Edges are named by their two adjacent faces** (`extrude#1:side:e1|extrude#1:side:e2`), not by edge history. Edge history (`Modified` for edges, now collected) misses every edge an operation creates: the 4 boundary edges of a fillet face, and every boolean section edge, which only appears as `Generated` of a face. Where edge history does reach, it agrees with the face-pair name in every case tested. When two faces meet more than once, the other faces at the edge's end vertices tell the edges apart (`...|...[cut#4:side:s2,extrude#1:side:e2]`); only when those tie too does a positional ordinal come in, flagged fragile.
- **The scenario passes.** The fillet lands on the same corner, with the same two side faces and both caps as neighbours, after the rectangle is resized, after a vertex splits an edge (away from the corner and at the corner), after the hole and the slot are reordered, and after all three at once. Reordering the two cuts gives identical face and edge name sets. Deleting the sketch edge behind the filleted edge gives a clean `lost` error naming the missing face, while a sharp edge still sits exactly where the fillet was; a proximity match would have filleted it silently.
- **Index references look safe and are not.** The corner edge keeps its MapShapes index through a resize, a reorder and a far split, then silently becomes a different edge when e1 is split or the sketcher emits the same rectangle starting from another corner. The name resolves correctly in both. (The index was 2 in the exploratory probe; the test checks where the index lands, not its value.)
- **Positional names are never silent.** A kernel-split piece (`cut#4:side:s3#2`) is numbered by position, so after an edit the same name can pick a different piece. Every resolution that rests on such a name, or on an edge ordinal, comes back with `fragile: true`, including an exact match on an unchanged model, and the regen engine records it per reference.
- **OCCT quirk**: `BRepFilletAPI_MakeFillet::IsDeleted` returns true for edges the fillet did not touch (all 10 untouched edges of the exploratory probe model; the tests assert only that there are some). Naming must use kept / `Modified` / `Generated` and never `IsDeleted` alone.
- All 23 scenario tests pass (`pnpm --filter @manufakture/spike-topo-naming test`, about 1.3 s). A full regen of the four-feature part takes about 17 ms, of which about 7 ms is the embind-based `topology()` query that naming needs (`pnpm --filter @manufakture/spike-topo-naming bench`, median of 20 runs after 5 warm-up; two runs gave 16.6 / 6.7 ms and 17.5 / 6.9 ms on Node 26.10.0). The figures in the first draft of this report (16.4 ms and 6.7 ms) came from a throwaway script that was deleted and cannot be reproduced from the spike; the bench script replaces it and agrees.

Recommendation: adopt this scheme for `packages/kernel` and the regen engine. The kernel returns kinded history (faces, edges and vertices, in and out) and a topology query; the naming layer is pure TypeScript next to the regen engine in the worker; meshes carry face and edge names. Details in [Recommendations](#recommendations).

### Changes to the T0.3 wrapper

T0.3 left edge-level history open. What changed:

- `HistoryEntry` outputs carry a kind: `modified` and `generated` are lists of `{ kind, index }` in the result, and `kept` is the index of the same sub-shape (same kind) when it passed through untouched. T0.3 mapped everything to result faces.
- History is collected for every face, edge and vertex of every operand, including entries with no face output, so `Modified` for edges is recorded (for cut as well as fillet).
- `extrude(frame, loop, from, to)` builds the profile face from sketch loop edges with shared vertices and returns the result face each profile edge generated (`BRepPrimAPI_MakePrism::Generated(edge)`) plus both caps (`FirstShape()`, `LastShape()`).
- `boolean('cut' | 'fuse', a, b, { simplify })`: `simplify` runs `SimplifyResult`, whose history OCCT merges into the builder's, so merged faces show up in `Modified`.
- `topology(shape)`: faces (surface type, centroid, area, outward normal for planes, axis and radius for cylinders), edges (adjacent faces, seam flag, curve type, midpoint, length, vertices) and vertices (point, adjacent faces). This is what edge names and ambiguity checks need.

The T0.2 conventions carry over unchanged: every temporary is owned by a `Scope` and released before `delete()`, and heap growth in tests is expected.

## The ID scheme

### Features and sketch entities

Every name starts with the id of the feature that created the geometry: `extrude#1`, `cut#2`, `fillet#3`. Feature ids are assigned once, when the feature is created, and never change. They are not positions in the tree, which is why reordering renames nothing. Sketch entities carry the sketcher's own stable ids (`e1`, `c1`), and a fillet's edge references carry ids too (`r1`), so the faces they produce can be named after them.

### Faces

| Name                    | Face                                                                                       |
| ----------------------- | ------------------------------------------------------------------------------------------ |
| `extrude#1:cap:start`   | the extrusion's cap at the sketch plane (at `from`)                                        |
| `extrude#1:cap:end`     | the cap at the far end (at `to`)                                                           |
| `extrude#1:side:e2`     | the face swept by sketch entity `e2`                                                       |
| `fillet#3:round:r1`     | the face fillet#3 made from its edge reference `r1`                                        |
| `fillet#3:corner:A&B&C` | a corner blend a fillet makes from a vertex, named by the faces around it (not exercised)  |
| `extrude#1:side:e2#a`   | the side from sketch entity `e2#a`: a piece of `e2` split in the sketcher                  |
| `cut#4:side:s3#1`, `#2` | face `cut#4:side:s3` split into pieces by a later operation, ordered by position (fragile) |
| `fillet#3:round:r1#1`   | one of several faces generated from one input, ordered by position (fragile)               |
| `(A+B)`                 | faces `A` and `B` merged into one (`SimplifyResult`), sorted                               |

Cut tools and fused bodies are named like any extrusion, under the cut's own id, so the hole wall is `cut#2:side:c1` and a pocket floor is `cut#4:cap:end`. A tool face that ends up outside the part (`cut#4:side:s1`, both caps of a through hole) is simply deleted.

Propagation, per result face: collect every input face that is kept as, or `Modified` into, this face. One source: the face takes its name. One source split into several faces: each piece gets `#k`, ordered by centroid (x, then y, then z). Several sources: a merge. No source but `Generated` from an input edge or vertex: the operation names it (fillet round or corner); when one input generates several faces, they get `#k` by centroid like split pieces, and are fragile. Nothing at all: `?faceN`, reported as unnamed; no scenario produced one, and the product should treat it as a regen error.

Every face also carries its **lineage**: its own name and every name it descends from. `extrude#1:side:e2#a` has lineage `[...e2#a, ...e2]`; `cut#4:side:s3#1` has `[...s3#1, ...s3]`; `(A+B)` has both. Lineage is what lets a reference to `e2` still find `e2#a` when that is the only candidate.

### Edges

An edge is named by the sorted names of its adjacent faces:

| Name          | When                                                                                 |
| ------------- | ------------------------------------------------------------------------------------ |
| `A\|B`        | the only edge between faces `A` and `B`                                              |
| `A\|A`        | the seam of periodic face `A` (a hole wall's seam is `cut#2:side:c1\|cut#2:side:c1`) |
| `A\|B[C,D]`   | several `A\|B` edges: add the sorted names of the other faces at its end vertices    |
| `A\|B[C,D]#k` | still not unique: order by midpoint (x, then y, then z); flagged fragile             |

In the test part, the slot cuts the top front edge in two, giving `extrude#1:cap:end|extrude#1:side:e1[cut#4:side:s2,extrude#1:side:e2]` and `...[cut#4:side:s4,extrude#1:side:e4]`. A blind horizontal trough, whose round wall meets the top twice between the same two end walls, is the only case in the spike that needed an ordinal.

Why faces and not edge history: face-pair names cover every edge, including the ones an operation creates (fillet boundaries, boolean section edges), with no extra rules; they mean what a user means ("the edge between the top and the front"); and they come for free once faces are named. The `what edge history alone would give` tests show the alternative falls short (4 of the fillet result's edges have no input edge) and agrees with face pairs wherever it does reach. Edge history is still collected, since it is cheap and useful for validating naming, but naming does not depend on it.

Vertices are named only where a name is needed (corner blends): the sorted names of the faces around them, joined by `&`.

### Splits and merges

- **Sketch splits** are the sketcher's business: splitting `e2` with a vertex yields `e2#a` and `e2#b`, in order along the original edge. The naming layer reads `e2` as the ancestor of both. This is deterministic.
- **Kernel splits** (one input face, several result faces) get `#1`, `#2` by centroid order. This is deterministic for a given geometry, but the order can change when the geometry does, so these names are flagged fragile. Several faces generated from one input edge or vertex are numbered the same way, never in the kernel's index order.
- Both kinds of split use the `#` separator; what follows tells them apart. A letter (`e2#a`) is a sketch split, deterministic and not fragile; digits (`s3#1`) are a positional piece and fragile (`isPositional` in `src/naming.ts`). Feature ids (`cut#4`) are never confused with either, since a `:` always follows their digits.
- **Merges** get `(A+B)`, with the union of the sources' lineage.

### References and resolution

References store names, never indices:

```ts
interface FaceRef {
  face: string;
}
interface EdgeRef {
  faces: string[];
  ends?: string[];
  ordinal?: number;
}
```

A click is stored with only what is needed to be unique at the time: `pickEdge` gives `{ faces }` for the corner edge, adds `ends` for one of the split top edges, and `ordinal` only for the trough lines. Resolution, in order, stopping at the first level that yields candidates:

1. `exact`: faces (and for a face reference, the name) match exactly.
2. `descendant`: a face's lineage contains the referenced name (a sketch or kernel split, or a merge).
3. `ancestor`: the reference names a kernel-split piece `X#k`, the split is gone, and `X` exists (the piece became whole again).

Then, only to choose among several candidates, never to find one: `ends` keeps the candidates whose end faces match the most referenced end faces (by lineage), and `ordinal` picks by position. When the chosen edge's end faces still match the reference by name exactly, `via` stays as it was (so a reference that needed `ends` at pick time is `exact` on an unchanged model); a partial or lineage-only match gives `via: 'ends'`. The result is exactly one index, how it was found (`via`) and whether the choice rested on position (`fragile`), or an error:

- `lost`, with the referenced names that no longer exist anywhere (`missing`), or empty when the faces all exist but no longer share an edge (`describeFailure` spells this case out);
- `ambiguous`, with the candidate names, sorted.

`fragile` is independent of `via`. It is true when a positional face name (`X#k`) is in the reference's faces, or in its ends when they were used to choose, or when the ordinal picked the edge. An exact match on a fragile name is still fragile.

The regen engine never picks by index or by proximity. A feature with an unresolved reference is skipped with a `FeatureError`, and the features after it still regenerate.

## Failure cases and what does not work

- **Kernel-split ordinals are positional.** `cut#4:side:s3#1` is "the piece with the smallest centroid (x, then y, then z)". If an edit changes the number of pieces or their order, `#1` can name a different piece and still resolve by exact name: the `split reoriented` test shows `s3#2` moving from the right piece to the top piece. This scheme cannot prevent that. What it guarantees is that it is never silent: every resolution through a positional name returns `fragile: true`, so the regen reports it. The `ancestor` fallback covers the split disappearing, not the split changing.
- **Several faces generated from one input are positional too.** They are numbered like split pieces, by centroid, and flagged fragile. Only the synthetic test exercises this; no kernel scenario in the spike generated more than one face from one input.
- **Edge ordinals are positional too**, with the same risk, and they only arise when faces and end faces tie (the trough). They are rare but real.
- **End faces change with neighbouring edits.** The corner fillet replaced `side:e2` with `fillet#3:round:r1` at the end of the top front edge, so the edge's display name changed and exact matching of `ends` would have failed. Scored matching handles it; when candidates score equally, the result is `ambiguous`, not a guess.
- **Descendant matching trusts the sketcher's split convention.** If the sketcher gives the pieces unrelated ids, or the user deletes an entity and redraws it, the reference is `lost`. That is the intended behaviour (a re-pick prompt), but it means sketch entity ids must be stable and never reused.
- **A reference can resolve to something whose meaning drifted.** "The edge between e1 and e2" is by definition the same semantic edge as long as it is unique, but in a non-convex profile two faces can stop meeting at one place and start meeting at another. The name cannot tell. No scenario hit this; it is inherent to any semantic scheme.
- **Sketch placement on a face is only half-solved.** The sketch frame on a face is derived from the face's outward normal and the world axes (x is world X projected onto the plane), so it is deterministic, but it does not rotate with the face. Revisit when sketches attach to faces that can tilt.
- **Not exercised**: revolve, sweep, loft, shell, chamfer, draft, patterns and mirrors (several instances of one feature need an instance index in the name), multi-body parts, corner blends (the naming rule exists, no test has three filleted edges at a vertex), non-manifold edges, faces generated by vertices in booleans, and imported geometry (no feature history at all: names would have to come from something else).
- **Cost.** `topology()` goes through embind per face, edge and vertex: about 7 of 17 ms per regen of the test part (`bench`, see the summary). It belongs in the C++ helper layer that ADR 0001 already plans.

## Recommendations

### For T1.3: kernel worker protocol (meshes carry face and edge IDs)

1. Topology-changing operations return this spike's `HistoryEntry`: per operand, per input face, edge and vertex, `kept` (same-kind index), `modified` and `generated` as kinded result references, and `deleted`. Naming uses kept, modified and generated only; `deleted` is informational (fillet's is wrong).
2. `extrude` (and later revolve, sweep) returns the profile-to-face map and the caps, keyed by the order of the loop's entities, so the regen engine can apply sketch ids.
3. Add a `topology(shape)` query with the fields in `src/kernel.ts`, implemented in C++ with the other helpers.
4. Run the naming layer in the worker, next to the regen engine: it is pure TypeScript over plain data (`src/naming.ts`).
5. Meshes carry names as a string table sent once per regen, plus per-face and per-edge indices into it, aligned with `faceRanges` and with the edge polylines. Also send a `fragile` flag per face and edge so the UI can warn at pick time.
6. Picking returns a name, not an index: the main thread sends back the face or edge name (or the whole `EdgeRef` from `pickEdge`), and the worker resolves it.

### For T1.8: part features

1. Feature ids are `kind#n`, assigned at creation, unique in the part, never reused; they are never tree positions.
2. Each feature defines its birth names on this pattern: `cap:start`, `cap:end`, `side:<sketch id>` for extrude and cut; `round:<ref id>` and `corner:<vertex name>` for fillet (and chamfer); references inside a feature have their own ids.
3. Every reference a feature holds is a `FaceRef` or `EdgeRef`, resolved on every regen. Record `via` and `fragile` per reference. A resolution warns at regen when `via` is `descendant`, `ancestor`, `ends` or `ordinal`, or when `fragile` is true, whatever `via` says: an `exact` match on a positional name (`X#2`) is fragile and always warns. Only an `exact`, non-fragile resolution is silent. Positional split naming can still pick a different piece after an edit; the warning is what makes that visible, never a silent re-attachment. `lost` and `ambiguous` fail the feature with a re-pick prompt listing the missing names or the candidates (or, for `lost` with no missing names, saying the faces no longer meet), and later features keep regenerating.
4. Treat an unnamed result face (`?faceN`) as a regen error.
5. The sketcher (T1.5) names split pieces `<id>#a`, `<id>#b` in order along the original entity, and never reuses an id.
6. Port this spike's scenarios as regression tests for the real feature set.

### For the document format ADR (T0.6)

- References are persisted as names (`FaceRef`, `EdgeRef` with `ends` and `ordinal` only when they were needed at pick time), never as sub-shape indices or shape hashes.
- Feature ids, sketch entity ids and reference ids are persistent, unique within a part, and never reused after deletion: a reused id would silently re-attach a lost reference.
- Face and edge names are derived data, recomputed on every regen; only references store them.
- The file records a naming scheme version, so a later scheme can migrate stored references.
- Optionally keep, next to each reference, the geometry of its last successful resolution (a point and a normal or tangent), for the re-pick UI to highlight what was lost. It must never be used to resolve.
