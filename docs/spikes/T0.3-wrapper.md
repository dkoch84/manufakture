# T0.3 spike: kernel wrapper (brepjs vs replicad vs a thin wrapper of our own)

- Status: done
- Date: 2026-09-26
- Code: [`spikes/kernel-wrapper/`](../../spikes/kernel-wrapper/)
- Raw results: [`spikes/kernel-wrapper/results/`](../../spikes/kernel-wrapper/results/) (every number below comes from these files unless marked "computed")
- Decision: [ADR 0001](../adr/0001-kernel-wrapper.md)

## Summary

The same modelling scenario (T0.2's filleted box, plus a sketch wire extruded and drilled) was built with brepjs, with replicad, and with a minimal wrapper of our own over the raw libcascade 3.0.2 bindings. All of them produce identical geometry (same volumes to 1e-6, same face counts, same triangle counts), so the choice is decided by history access, memory, the OCCT build each one ties us to, and maintenance.

- **History (what T0.5 needs).** Only raw OCCT calls reach it. Our wrapper traces all 26 faces of the filleted box back to the input faces, edges and vertices that produced them, and all 9 faces of the drilled part back to input faces. It records history to result faces only; result edges and `Modified` for input edges are not collected yet (see [History](#history)). replicad has no history API at all; its raw escape hatch works, but on replicad's own trimmed build `NCollection_IndexedMap` cannot even be constructed. brepjs (and occt-wasm under it) track faces only, by hash, so the 12 fillet faces and 8 corner blends, which OCCT reports as generated by edges and vertices, are lost: 6 of 26 traced. And brepjs's `*WithEvolution` functions silently return **empty** history unless an input already carries metadata.
- **Memory.** Everything built on libcascade or replicad's own build leaks, because both builds register empty destructors (libcascade 2102 of 5298 classes, as in T0.2; replicad's build **171 of 454**, including `TopoDS_Shape` and every builder). Per scenario run: our wrapper 143.4 KiB with T0.2's release-before-delete mitigations, replicad 359.7 to 361.0 KiB (forcing GC changes nothing, since the finalizers call the same empty destructors). occt-wasm, which keeps shapes in a C++ arena and hands JS only integer ids, leaks **nothing measurable** (0 KiB for occt-wasm, 1.3 KiB, one probe step, for brepjs).
- **Build compatibility.** brepjs cannot use libcascade: its only OCCT adapters target occt-wasm or the old suffixed opencascade.js API. replicad runs its modelling on libcascade 3.0.2 unchanged, but `mesh()` fails there because it calls four C++ helper classes that only replicad's own build contains.
- **Performance.** Wrapper overhead on identical wasm is small for replicad (per call 74.09 against 73.25 microseconds for our own thin wrapper, both on libcascade; bare libcascade calls were not measured separately) and noticeable for brepjs (121.88 against 68.70 microseconds for occt-wasm alone; 17.19 against 14.37 ms for the whole scenario). The real speed differences come from the builds: a C++ mesh extractor copies a fine mesh 2.6 to 2.8 times faster than per-node embind calls, and occt-wasm initialises in 32 ms against 482 ms for libcascade in Node.
- **The claim that brepjs's author hit performance walls with replicad**: not reproducible with replicad 1.1.0, which is faster than brepjs on this scenario. It was plausible for replicad before 1.0.0 (August 2026), which extracted meshes node by node through embind, and replicad's memory leak is real today. Details in [the claim](#the-claim-replicad-hit-performance-and-api-walls).

Recommendation (see the [ADR](../adr/0001-kernel-wrapper.md)): write our own thin wrapper in `packages/kernel`. Shapes live in an arena and cross the API as integer ids (occt-wasm's design), every topology-changing operation can return OCCT history by sub-shape index (to result faces today; T0.5 settles edge-level history), and no OCCT object ever leaves the package. It runs on libcascade 3.0.2 now; the implementation moves into C++ helpers in a custom build without changing the API.

## What the spike does

```
spikes/kernel-wrapper/
  src/scenario.ts            the scenario, its exact expected volumes and face counts
  src/loaders.ts             loads each OCCT build through instantiateWasm (timed phases, heap access)
  src/own/kernel.ts          the own-wrapper sketch: arena of shape ids, scopes, history, mesh
  src/candidates/*.ts        the scenario implemented once per candidate
  src/candidates.test.ts     the proof: geometry, meshes, history and memory per candidate (26 tests)
  scripts/measure.ts         driver; sections: sizes, audit, node, memory, maintenance
  scripts/node-child.ts      one measurement per fresh process (init, timing, calls, leak, replicadBoxes)
  scripts/destructor-audit.ts  T0.2's empty-destructor audit, generalised to any of the three builds
  scripts/import-time.ts     import cost of a wrapper library's JS
  results/                   raw JSON
```

The scenario (`src/scenario.ts`), run by every candidate:

1. **Part A** (T0.2's box): a 40 x 30 x 20 mm box, all 12 edges filleted at 2 mm. Expected: 26 faces, volume 23,701.687 mm³ (exact formula in the source).
2. **Part B**: a closed L-shaped polyline (6 points) in the XY plane made into a face and extruded 25 mm: 8 faces, 22,500 mm³. Then a 4 mm radius cylinder along Y is cut through the 10 mm base leg: 9 faces, 21,997.345 mm³.
3. **Mesh** both parts (0.1 mm linear, 0.5 rad angular deflection, as T0.2; "fine" is 0.01 mm and 0.1 rad) and copy positions, normals and indices into typed arrays.
4. **Query** volume and face count of each part.
5. With `history: true`, fillet and cut use each candidate's history mechanism, and the result is summarised as "which result faces can be traced back to an input".

To reproduce: `pnpm --filter @manufakture/spike-kernel-wrapper measure` (all sections, about 3 minutes; `maintenance` needs network), or name sections: `measure sizes audit node memory maintenance`. `pnpm --filter @manufakture/spike-kernel-wrapper test` runs the tests (about 2 s). The spike is kept outside the pnpm workspace; add it back to run these (see [spikes/README.md](../../spikes/README.md)).

## Method

- **Timing**: per candidate and configuration, a fresh process loads the build, does one first run (reported separately; it includes V8's lazy compilation), then 20 runs; medians. Configurations: `model` (no mesh), `scenario` (with mesh), `history` (no mesh, history on), `fine` (fine mesh).
- **Per-call overhead** (`calls`): 500 iterations of "make a 10 mm cube, query its volume, release it" through each API, after a warm-up; median of 5 repeats, in microseconds per iteration. This is almost pure call overhead, since OCCT's own work is tiny.
- **Init**: 5 fresh processes per build; phases timed inside Emscripten's `instantiateWasm` hook as in T0.2.
- **Memory**: T0.2's method. Bytes in use after N scenario runs = memory size minus what the allocator can still hand out in 64 KiB blocks before the memory must grow; leak per run = (in use after 60 runs minus after 10) / 50, in fresh processes, resolution about 1.3 KiB per run. Two modes: `sync` (no yield between runs, as in a tight regen loop in a worker, so FinalizationRegistry callbacks cannot run) and `gc` (after every run, `gc()` and three event-loop turns so that finalizers do run).
- **Destructor audit**: T0.2's `destructor-audit.ts` (intercepts embind's class registration and reads each destructor's wasm body), made build-independent.
- **Sizes**: Node `zlib`, gzip level 9 and brotli quality 11 (24-bit window), on the shipped files.
- **Maintenance**: npm registry and GitHub REST API, fetched 2026-09-26 (`results/maintenance.json`).

## Results

### Geometry: all candidates agree

Every candidate passes the same checks (`candidates.test.ts`, 26 tests): 26 faces and the exact filleted-box volume, 8 faces and 22,500 mm³ for the extrusion, 9 faces and 21,997.345 mm³ after the cut, all within a relative 1e-6. Every candidate that can mesh produces the same triangulation: 628 and 128 triangles at the normal setting, 9,460 and 528 at the fine one. That is expected, since all three builds are OCCT 8.0.1 with the same `BRepMesh`, and it means the timings below compare equal work.

replicad-libcascade does the modelling but not the mesh: replicad 1.x calls `ReplicadMeshExtractor`, `ReplicadEdgeMeshExtractor`, `ReplicadShapeCaster` and `ReplicadShapeHasher`, C++ classes compiled into its own build only, and `mesh()` fails with `Cannot read properties of undefined (reading 'extract')` (tested). Everything else replicad references exists in libcascade, because replicad 1.x was ported to the same OCCT 8 binding generator (taucad's opencascade.js toolchain, per `replicad-opencascadejs`'s build scripts and replicad [PR #263](https://github.com/sgenoud/replicad/pull/263)). A custom libcascade build could add those four classes.

### History

What each candidate can tell about where the result faces came from (`history` configuration; `candidates.test.ts` pins every number):

| Candidate           | How                                                                       | Fillet: result faces traced  | Cut: result faces traced    | Input kinds reported   |
| ------------------- | ------------------------------------------------------------------------- | ---------------------------- | --------------------------- | ---------------------- |
| own-libcascade      | `Modified` / `Generated` / `IsDeleted` on the builder, by sub-shape index | 26 of 26                     | 9 of 9                      | faces, edges, vertices |
| replicad            | no API; escape hatch (`getOC()`, `.wrapped`, raw builders, `cast()`)      | 26 of 26                     | 9 of 9                      | faces, edges, vertices |
| replicad-libcascade | same escape hatch                                                         | 26 of 26                     | 9 of 9                      | faces, edges, vertices |
| occt-wasm           | `filletWithHistory` / `cutWithHistory`, keyed by face hash                | 6 of 26                      | 9 of 9                      | faces only             |
| brepjs              | `filletWithEvolution` / `cutWithEvolution`, keyed by face hash            | 6 of 26 (0 without metadata) | 9 of 9 (0 without metadata) | faces only             |

The full picture from OCCT for the fillet: each of the 6 box faces is modified into one trimmed face, each of the 12 edges generates one fillet face, each of the 8 vertices one corner blend (6 + 12 + 8 = 26). For the cut: the two prism faces the drill passes through and the drill's side face are modified, the drill's two caps are deleted and the other six prism faces pass through unchanged (3 + 6 = 9). Filleting a single edge (also tested) modifies four faces, not two: the two faces meeting at the edge and the two end faces, which gain the fillet's arc.

Findings:

- **occt-wasm and brepjs only ask about input faces.** Fillet surfaces come from edges and vertices, so their provenance is lost. That is the case topological naming cares most about ("the fillet on the edge between face A and face B"). Fixing it means changing occt-wasm's C++ facade.
- **brepjs's evolution is empty by default.** `collectInputFaceHashes()` returns `[]` unless an input has face origins, tags or colours, so `filletWithEvolution(box, …)` on a plain box returns empty maps, with no error (tested). `setShapeOrigin(shape, n)` on the inputs opts in.
- **Hashes are not names.** occt-wasm's hashes come from OCCT's shape hashing, bounded to 2³¹ - 1: unique only within one kernel instance, and collisions are possible. Index-based history (our wrapper) is exact for a given result shape; either way, persistent naming is T0.5's job on top.
- **replicad's escape hatch works but fights the trimmed build**: `NCollection_IndexedMap_TopoDS_Shape_TopTools_ShapeMapHasher` is bound but throws `unbound types: 19NCollection_BaseMap` when constructed, so the spike numbers sub-shapes with `TopExp_Explorer` plus `IsSame` there (`explorerIndexer`, quadratic). And history needs raw builders, so replicad's own `fillet()` and `cut()` cannot be used for any operation whose history matters.
- **What our wrapper's history does not cover yet.** `collectHistory` maps inputs to result faces only: `HistoryEntry` holds result face indices, so result edges are never named and `Modified` is never recorded for input edges. The fillet collects faces, edges and vertices, but skips any input edge or vertex that generated no face; the cut collects input faces only. That is enough for the tables above, not proof of what naming needs. T0.5 (topological naming, the next task) must establish which edge-level history it needs and extend the entry.
- **Cost of history**: our wrapper 9.07 against 8.49 ms for the modelling part (+0.58 ms, computed), occt-wasm 11.53 against 11.17 ms, brepjs 14.24 against 13.81 ms.

### Memory

**Destructor audit** (`results/destructor-audit.json`):

| Build                        | Bound classes | Empty destructor (delete() frees nothing) | Among them                                                                                                                                               |
| ---------------------------- | ------------- | ----------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| libcascade 3.0.2             | 5298          | 2102                                      | as in T0.2: `TopoDS_Shape`, `gp_Pnt`, `TopLoc_Location`, every builder                                                                                   |
| replicad-opencascadejs 1.1.0 | 454           | 171                                       | `TopoDS_Shape`, `TopoDS_Face`, `TopoDS_Edge`, `gp_Pnt`, `BRepAlgoAPI_Cut`, `BRepFilletAPI_MakeFillet`, `TopExp_Explorer`, `GProp_GProps`, all primitives |
| occt-wasm 5.3.5              | 9             | 0                                         | shapes never cross into JS as embind objects                                                                                                             |

So replicad's own build, made with the same toolchain family as libcascade, has the same bug. It is almost certainly the cause of the open replicad issue [#282](https://github.com/sgenoud/replicad/issues/282) ("~200 KB per BRepAlgoAPI_Fuse is never freed, even after delete()"), and of heaps passing 2 GiB in [#269](https://github.com/sgenoud/replicad/issues/269).

**Leak per scenario run** (`results/memory.json`; `model` is without meshing, `scenario` with):

| Candidate           | Memory handling                                                      | model, sync | model, gc | scenario, sync | scenario, gc  | In use after 60 scenario runs |
| ------------------- | -------------------------------------------------------------------- | ----------- | --------- | -------------- | ------------- | ----------------------------- |
| own-libcascade      | arena of ids; scopes; release before delete (T0.2)                   | 110.1 KiB   | 110.1 KiB | 143.4 KiB      | 143.4 KiB     | 48.62 MiB                     |
| replicad            | FinalizationRegistry on every wrapper and builder, optional delete() | 273.9 KiB   | 279.0 KiB | 361.0 KiB      | 359.7 KiB     | 58.25 to 58.44 MiB            |
| replicad-libcascade | same                                                                 | 249.6 KiB   | 249.6 KiB | (cannot mesh)  | (cannot mesh) | 54.50 MiB (model)             |
| occt-wasm           | C++ arena, u32 ids, `release` / `checkpoint` / `releaseSince`        | 0           | 0         | 0              | 0             | 11.00 MiB                     |
| brepjs              | handles with delete() and Symbol.dispose, FinalizationRegistry net   | 0           | 0         | 1.3 KiB        | 1.3 KiB       | 11.06 MiB                     |

- **GC timing does not matter**: `sync` and `gc` agree within one probe step for every candidate. replicad's finalizers run in `gc` mode, but they call the same empty destructors. So the leak comes from the builds, not from the wrapper's memory strategy.
- **Our wrapper is the best of the libcascade-based options** (143.4 against 249.6 to 361.0 KiB per run) because it applies T0.2's release-before-delete rules, which replicad does not.
- **A C++ arena solves the problem outright.** occt-wasm's facade keeps every `TopoDS_Shape` in C++, where destructors run normally, and JS only holds integers. It also has far less in use: 11 MiB after 10 runs, against about 41 MiB for the embind-heavy builds. This is exactly the custom-build-with-C++-helpers direction T0.2 recommended, and the numbers here are the target for it.
- Handle tracking: our arena and occt-wasm's are empty after every run (`liveHandles` 0), and brepjs's disposal stats return to their starting value (tested). replicad keeps no count.

What the numbers say (differences computed from the tables):

- **replicad's wrapper overhead is about 1 %** more than our own thin wrapper on the same libcascade wasm (74.09 against 73.25 microseconds per call; fillet 4.61 against 4.34 ms). This compares two wrappers; neither was measured against bare libcascade calls. Its slower modelling (11.56 against 8.49 ms) is extra OCCT work by design: every replicad boolean runs `SimplifyResult` (`ShapeUpgrade_UnifySameDomain`), and its sketches build 2D curves before the 3D face. The escape-hatch cut, which skips `SimplifyResult`, takes 3.33 ms against 5.06 ms for replicad's own `cut()`, even though it also collects history.
- **brepjs's overhead over its own kernel is 77 % per call** (121.88 against 68.70 microseconds) and 2.82 ms (20 %) on the scenario (17.19 against 14.37 ms). Its queries cost twice as much (3.21 against 1.53 ms): runtime validity checks and per-shape sub-shape caches.
- **Mesh extraction is where a wrapper's design costs real time.** Copying a mesh out node by node through embind (our wrapper on the stock bindings, T0.2's method) takes 76.89 ms for the fine mesh; the C++ extractors of replicad and occt-wasm take 27.65 to 29.59 ms for the same 9,988 triangles, 2.6 to 2.8 times faster. The fix is a C++ helper in the build, not a different JS wrapper.
- **An idiom trap in replicad**: `makeBaseBox`, the box used throughout replicad's examples, sketches a rectangle and extrudes it. It costs 351.5 microseconds per box against 71.7 for `makeBox` (which calls `BRepPrimAPI_MakeBox`), and filleting its 12 edges takes 12.47 ms against 3.82 ms (`results/node.json`, `replicadBoxes`). The scenario uses `makeBox` for replicad so that all candidates do the same OCCT work.

### API ergonomics and typing

| Aspect          | own wrapper (sketch)                                | replicad 1.1.0                                                             | brepjs 20.0.0 (+ occt-wasm)                                                          |
| --------------- | --------------------------------------------------- | -------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| Style           | coarse operations on integer shape ids              | fluent classes (`shape.fillet(2).cut(tool)`), `draw()` / `Sketcher` for 2D | functional (`fillet(s, edges, r)`), plus a fluent view                               |
| Public surface  | what we define (about 12 operations in the sketch)  | 172 named exports                                                          | 626 named exports; occt-wasm's kernel class alone has 207 methods                    |
| Typing          | branded `ShapeId`; libcascade's full typings inside | generated `.d.ts`; shape classes typed, validity not                       | branded kinds and validity (`ValidSolid`, `ClosedWire`, `PlanarFace`), `Result<T,E>` |
| Errors          | `KernelError` with decoded OCCT exception           | throws                                                                     | `Result` with error codes; occt-wasm throws `OcctError` with a code                  |
| Kernel instance | one per `OwnKernel`                                 | one global (`setOC`)                                                       | one global registry (`registerKernel`)                                               |
| Memory          | explicit arena; nothing escapes                     | GC plus optional `delete()`; builders only via GC                          | `delete()` / `using`, GC safety net                                                  |
| Selection       | sub-shape indices (T0.5 adds names)                 | finders (`EdgeFinder().inDirection('Z')`)                                  | finders (`edgeFinder()`), face tags                                                  |

Both libraries are built for code-first modelling: a script composes shapes, and the library's value is a pleasant, large modelling vocabulary. manufakture is GUI and feature-tree first (product decision 2): the kernel is driven by a regen engine that replays features, needs history for naming, and must survive long sessions in one worker. Neither library's vocabulary is what that engine calls, and both hide or drop the history it needs. brepjs's type discipline is the strongest here and worth copying in spirit (branded ids, structured errors), and replicad's and occt-wasm's C++ mesh extractors are the design to copy for meshing.

### The claim: replicad hit performance and API walls

brepjs's README says its author "kept hitting performance walls and fighting the API" with replicad. brepjs's own documentation ([why brepjs](https://brepjs.dev/introduction/why-brepjs), [migrating from replicad](https://brepjs.dev/migration/replicad)) only argues the API and type-safety side and links no measurements; its published benchmarks compare brepjs's own kernels, not replicad. Checked against the measurements:

- **Wrapper speed: refuted for replicad 1.1.0.** On the same wasm, replicad costs about 1 % per call more than our own thin wrapper, and on its own build it runs the scenario in 14.30 ms against brepjs's 17.19 ms.
- **Meshing: confirmed for the replicad brepjs started from.** brepjs began in February 2026, when replicad (0.20 to 0.23) copied meshes out node by node through embind; the C++ extractors arrived with replicad 1.0.0 in August 2026 (replicad [PR #263](https://github.com/sgenoud/replicad/pull/263), [issue #269](https://github.com/sgenoud/replicad/issues/269)). That method, measured here on our wrapper, is 2.6 to 2.8 times slower on a fine mesh than a C++ extractor.
- **Memory: confirmed, and still present.** replicad leaks 249.6 to 361.0 KiB per scenario run whatever the GC does, because of the empty destructors in its build (open [issue #282](https://github.com/sgenoud/replicad/issues/282)). brepjs on occt-wasm does not leak.
- **Idioms**: replicad's documented `makeBaseBox` is 4.9 times more expensive than `makeBox` and makes the following fillet 3.3 times slower (computed from `replicadBoxes`), an easy trap.
- **API**: a real design difference rather than a measurable wall. brepjs encodes shape kinds and validity in types and returns `Result`; replicad types shape classes but not validity, and throws.

Verdict: partly confirmed. The walls were real, but they sit in the OCCT build (per-node extraction, empty destructors), not in replicad's JS layer, and the meshing one has since been fixed.

## Gotchas

- **brepjs's `*WithEvolution` returns empty maps** unless an input carries metadata; set a shape origin first.
- **occt-wasm's `EvolutionData` is flat** `[inputHash, count, output...]` vectors, although its type comments describe plain hash lists.
- **replicad keeps one global OCCT module.** Two replicad instances (for example on two builds) in one realm must call `setOC` before every use.
- **replicad's trimmed build** has classes that are declared but not constructible (`NCollection_IndexedMap_…`, missing its bound base class), and some classes appear with `_2` to `_7` suffixes next to the suffix-free ones.
- **`TopoDS_Shape` has no bound copy constructor** in libcascade; a builder's `Shape()` already returns a fresh copy, so an arena takes ownership of that.
- **occt-wasm's glue is minified** and keeps `malloc` and `free` private; the spike reads their export names from the glue to probe the heap.
- **`p += leb()` is a bug when `leb()` advances `p`**: JavaScript reads `p` first. The first version of the generalised audit reported 0 empty destructors because of it; the T0.2 audit gave the correct 2102.

## Recommendation

Write our own thin wrapper, as specified in [ADR 0001](../adr/0001-kernel-wrapper.md):

1. `packages/kernel` exposes shapes as integer ids in an arena and coarse operations that return OCCT history by sub-shape index: input faces, edges and vertices to result faces, as proven here, with edge-level history left to T0.5. No OCCT object crosses its API.
2. First backend: libcascade 3.0.2 through the raw bindings, with T0.2's release-before-delete rules and instance recycling. At 143.4 KiB per scenario run that is about 7 regens per MiB of growth, roughly 7,000 between recycles at T0.2's example 1 GiB threshold (computed); each recycle costs a new instance (481.74 ms init in Node) plus replaying the feature tree.
3. The next step is T0.2's custom build: move the operations, history collection and mesh extraction into C++ helpers, so that shapes stay in C++ as in occt-wasm. Target numbers from this spike: no measurable leak, mesh copy at C++ extractor speed (27.66 ms for the fine case), and init well under libcascade's 482 ms. occt-wasm (MIT OR Apache-2.0 tooling) is a fallback: its facade could be forked and given edge and vertex history. The ADR switches to it if the custom libcascade build misses these targets by the end of M1, or if real M1 models leak more than 1 MiB per regen.
4. Do not adopt brepjs or replicad. Borrow: occt-wasm's arena, checkpoint and structured errors; brepjs's branded ids and error codes; replicad's and occt-wasm's C++ mesh extractor contract (packed buffers plus per-face groups).
