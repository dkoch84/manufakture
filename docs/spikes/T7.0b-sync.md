## Summary

- **ADR 0009 holds on real commands, with five additions.** Over 180 seeded runs of 9 scenarios (2 to 5 clients, 48,800 random commands, random delivery orders, 15 % message loss, a 20-second offline stretch, restores), every client converged to the server's document (180/180), every one of the 42,560 server heads passed `checkDocument`, no counter ever went below its high-water mark, and 34,138 id-free intent checks found no reference bound to the wrong item. No command was dropped for an id collision: the remap renamed 973,098 ids in 25,462 entries, and no replayed command was ever refused for one of its own fresh ids.
- **The five additions**, each found as a failure of an earlier version of the harness and fixed in it:
  1. **One simultaneous rename table over the whole queue**, in the client's current naming. Per-entry tables applied one after another collide.
  2. **An in-flight entry whose fresh ids are below the confirmed counters is renamed in the client's naming at once** (its sent copy untouched): it can never be accepted, and the user must not be able to make a command that names the confirmed item with the same id.
  3. **A dropped entry's ids become tombstones**, so a held entry naming them fails instead of binding to whatever later gets the number.
  4. **The entry carries the ids it creates, and the server checks them.** The server cannot compute them: two concurrent sketch edits that each add `e10` are both accepted by core, the second taking over the first one's entity. The guard caught 176 such takeovers; without it, 17 misbindings in 20 runs of one scenario.
  5. **`replaceDocument` is rebased as its intent** (the past document, re-derived on the head), and the server refuses any counter regression. Without both: 11,966 heads with a counter below its high-water mark in 20 runs.
- **Dropped commands: 0 % to 26 % by scenario, none for ids.** Two devices editing calmly: 0 of 4,000. Five clients editing faster than the round trip: 19.0 %; of that, the shared rollback bar causes more than half (8.3 % without `setRollback`). The rest are real conflicts (a delete against an add that depends on it, an edit of a deleted feature). Without the remap the same scenario drops 52.7 %.
- **Rebase cost is replay, not remap.** 1,000 pending commands on the 200-feature part rebase in 548 ms when a remote entry takes the first command's ids (the remap is 10 ms of it) and 528 ms when it takes none; 100 in 25 ms; 10 in 2.4 ms. On the M1 bracket: 342, 5.8 and 0.3 ms.
- **The remap is structural everywhere, with three places that need more than the command:** mate connectors, CAM operations and instance bodies name faces of another part, found through the document (instance to part, setup to part). Opaque data stays opaque: derived and pinned sources, extension `params` (ADR 0013 decision 2 keeps feature ids out of them), free text.
- **One case the remap cannot make meaning-preserving:** face names are compared by code unit, so a rename that adds a digit (`e9` to `e10`) can reverse which of an edge's faces sorts first, and that order picks a chamfer's reference face and the direction of an edge (kernel README, "Directions"). 81 such reversals in 48,800 commands. Numeric-aware comparison of names would make every remap order-preserving (a naming-scheme bump).
- **Nothing pushes ADR 0009 toward server-assigned ids.** The created-ids guard needs the client to say what it creates, which works the same either way, and every case above is solved on the client. Details in [Implications](#implications-for-adr-0009-and-t71a).

## What the spike does

**Server** (`server.ts`). One log per document. A submitted entry is checked in ADR 0009 decision 2
order: a recorded `(clientId, clientSeq)` gets its recorded outcome; an unknown `prevSeq` gets
`predecessor-unknown` (not recorded); a refused `prevSeq` gets `predecessor-refused`; then the
created-ids guard (addition 4), core's `applyCommand`, and the counter guard (addition 5). An
accepted entry gets the next revision and is broadcast to every client. After every accepted entry
the server runs `checkDocument` on the head and compares every counter with its high-water mark.

**Client** (`client.ts`). A confirmed document and a queue. Broadcasts are applied in revision order
(buffered when they arrive out of order); the client's own entry is matched by `clientSeq` and
confirmed exactly as sent. Rebase, after every change:

1. Refusals are acted on once the pull has reached their head revision: `id-reused` returns the
   entry to unsent in its place, `predecessor-refused` waits for the predecessor to be resolved,
   anything else drops it.
2. In-flight entries are replayed unchanged. One that chains through `prevSeq` to a refused entry is
   doomed (held); one whose fresh ids collide with the confirmed counters is certain to be refused
   and held (addition 2); one that fails otherwise is held and blocks everything after it.
3. One pass over the queue: each entry that may still be renamed gets the next free numbers for its
   own fresh ids, from the counters of the document replayed so far, and is rewritten through one
   table holding the renames of every earlier entry plus its own (addition 1). It is then replayed
   for display unless it or an entry before it is held; an unsent entry that fails is dropped and
   its ids tombstoned (addition 3). A restore is re-derived as `restoredDocument(head, past)`.
4. The visible document gets counters past every held entry's ids, so a new command never takes an
   id a held entry holds. Unsent entries are sent in queue order up to the first held one, each with
   `prevSeq` by the decision 2 rule and its created ids.

**Remap** (`remap.ts`, `names.ts`). A walker over the command JSON carries a context (part,
assembly, drawing, and which scope `r` ids belong to) and classifies each id by its shape in that
context: `part#`, `assembly#`, `cp#`, `cfg#`, `font#`, `drawing#` in the document scope; `inst#`,
`mate#`, `mc#`, `explode#`, `step#` in the current assembly; `tool#`, `setup#` and the operation kinds
in CAM; `print#`, `item#` in print; `sheet#`, `view#`, `dim#`, `note#` in the current drawing; any other
`kind#n` a feature of the current part; `e`, `k` the current part; `r` the current `r` scope. Names
go through a recursive-descent rewriter: born names with sub-id tails (split and positional suffixes
kept), nested names, corner lists, merges, instance prefixes; a derived prefix maps only its own
id. Record keys are ids in configuration row values and `setPoses`. Whole documents
(`replaceDocument`, `restorePart`) are walked the same way.

**Generator** (`generator.ts`). Every M1 feature kind (sketch, extrude, fillet, chamfer with and
without a second distance, shell, hole, linear pattern, mirror), edits (extrude extent, a sketch
entity and constraint added, fillet radius), delete, reorder, suppress, rollback, variables (set,
delete), batches (a sketch with its extrude; two simple commands), `replaceDocument` (a restore of an
earlier confirmed document through `restoredDocument`), and the other scopes: `addPart`,
`duplicatePart`, `addAssembly`, `addInstance`, `addMate` (connectors on side faces of the instance's
part), configuration parameters and rows, CAM tools, setups, pocket and profile operations. Each
command is made on the client's visible document and kept only if it applies there.

**Intent check** (`intent.ts`). Convergence and `checkDocument` cannot see a reference that the remap
bound to the wrong item of the right kind: core never reads mate connector names, CAM face names or
sub-ids inside face names. So every generated item carries in its name an id-free signature of what
it references: the permanent tags of the features it depends on (from core's `featureDependencies`
for features) and a unique coordinate of each sketch entity its face names point at. At the end
the signature is computed again on the server's document. A difference is a misbinding, unless the
target is gone (deleted where core does not protect it, or lost to a whole-feature edit), which is
counted apart as lost.

command's ids in those counters move. "No collision": the remote entry sets a variable. Median of 5:

## Where the remap is ambiguous or impossible

1. **Per-entry tables collide; one simultaneous table does not.** Entry A creates `extrude#4`,
   entry B (after it, unsent) creates `extrude#5` and edits A's `extrude#4`. A remote `extrude#4`
   arrives. A's table `{#4 to #5}` applied to B makes B hold two different `extrude#5`s, and B's own
   table `{#5 to #6}` then renames both. The spike keeps every queued command in the client's current
   naming and rewrites each entry once with one table (the renames of all earlier entries plus its
   own shift), keyed by scope and current id. Keys from different entries never clash because the
   client's naming never gives one id to two items, which additions 2 and 3 keep true.
2. **An in-flight collision makes a name ambiguous until it is renamed.** In flight, A holds
   `extrude#4`; a remote `extrude#4` arrives. A cannot be edited (the server may know it by its
   `clientSeq`) and is held, so the user sees the remote `extrude#4` and may edit it. If A is renamed
   only when its refusal arrives (ADR 0009 decision 5 as written), the rename `{#4 to #6}` also hits
   that new edit, which meant the remote feature. Since counters only grow, an in-flight entry whose
   fresh ids are below the confirmed counters can never be accepted, whatever error the server will
   give, so the spike renames it in the client's naming at once and keeps its sent copy as it is.
   This needs no change to the wire: the entry is still refused and resubmitted as decision 4 says.
3. **Dropped ids must never be handed out again in the client's naming.** If a dropped entry's
   `extrude#13` is simply forgotten, a held entry that names it binds later to whichever entry the
   next shift moves to `#13`, or to a remote `#13`. The spike renames a dropped entry's ids to
   tombstones: `kind#0` / `e0` where an id is a plain field (the schema refuses it, so it is never
   allocated either), and a valid but unreachable `kind#999999999999999` inside a face name (core
   accepts any face name text, but its dependency check refuses the missing feature). A sub-id
   inside a face name of a surviving feature is not checked by core at all, so a reference to a
   dropped entity survives as a `reference-lost` for regen to report.
4. **The server cannot tell which ids an edit creates.** `editFeature` carries the whole feature,
   and core's id rule counts an id as introduced only if the feature on the head lacks it. Clients
   A and B both add entity `e10` to `sketch#1`. A's edit lands; B's, built on the old sketch, carries
   its own `e10`, which the head's sketch already has, so core takes it as an edit of A's entity and
   accepts it (176 takeovers caught over the non-ablation scenarios). A's references to `e10` then
   point at B's line. The fix needs the client: each entry carries the ids it created, computed
   against the document it was made on, and the server refuses `id-reused` when one is below its
   counter. Without the guard (five-busy-nocreated): 17 misbindings, 28 entries the client knew
   were refused but the server accepted, and 29.3 % drops against 19.0 %.
5. **A duplicated part's ids are aliases.** `duplicatePart` copies features with their ids and the
   source's counters. A scope created by the queue (`addPart`, `addAssembly`) is local and its ids keep
   their numbers, but a duplicated part is not: its copied ids follow the source part's renames up to
   the duplicate, and ids added after it take numbers from the copied counters, which grew when the
   source took remote features. The spike copies the source's rename table into the new part's at
   the duplicate.
6. **Some names belong to another part, found through the document.** A mate connector names faces
   of its instance's part, a CAM operation sketches, holes and faces of its setup's part, and an
   instance's `bodies` body ids of its source part. The command does not say which part: the spike
   resolves instance to part and setup to part from the visible document and the queued commands.
   One case stayed unresolved in 180 runs (a mate inside a restored document whose instance the
   visible document does not have). An `editInstance` that changes the source while a queued mate
   names the old part's faces is ambiguous and not handled.
7. **Renames can reverse the order of names, and that order has meaning.** An edge reference stores
   its faces sorted by code unit; the kernel picks a chamfer's reference face as the one that sorts
   first and orients an edge's direction from the faces' order (kernel README, "Directions"). Under
   code-unit order `extrude#10:...` sorts before `extrude#1:...` and `e10` before `e9`, so a rename
   that adds a digit can swap them: 81 times in 48,800 commands. Flipping `flip` or swapping chamfer
   distances is not a structural fix, since some direction rules depend on geometry. Numeric-aware
   comparison fixes it: renamed ids of a counter stay above every confirmed id and keep their
   relative order, so every comparison a command can make is unchanged.
8. **A restore carries counters.** `replaceDocument` holds a whole document, counters included. Replayed
   as sent after other clients' entries, it moves counters back on the server, and ids are later
   handed out twice (restores-naive: 11,966 heads below the high-water mark, in all 20 runs). The
   spike stores the restore's intent (the past document) and re-derives `restoredDocument(head, past)`
   at every replay, and the server refuses any counter regression. One core gap remains:
   `restoredDocument` takes a part's counters from the past version when the part has been deleted
   since, which is below that part's high-water mark (12 refusals as `counter-regression` in restores).
9. **A whole-feature edit can be refused for an id no remap can fix (stale edit, 0.1 % to 0.9 %).**
   Client A adds `e10` to a sketch and then edits it again (carrying `e10`); B's edit of the old sketch
   lands between them and removes `e10`. A's second edit now re-introduces an id below the counter.
   It is not A's fresh id, so remapping does not apply, and decision 7 ("the later arrival wins,
   whole") cannot hold for it.
10. **A verdict belongs to one `clientSeq`.** A late answer to a resubmission, kept on the queue entry
    after the entry was resolved and resent, was read as the new `clientSeq`'s verdict. The server
    never saw the new entry, the next entries got `predecessor-unknown` for ever, and 2 of 20 lossy
    runs livelocked until the client cleared the verdict when an entry left flight.
11. **Opaque data cannot be remapped and must stay id-free.** Derived and pinned sources (another
    document), extension `params` (opaque JSON; ADR 0013 decision 2 already keeps feature ids out of
    them), `domains` data (`setDomainData` replaces a namespace whole), names and labels. A user who
    names a feature `extrude#3` is safe only because the walker skips free-text fields by key.

Not covered: undo and redo stacks (the remap is the same function over inverses, but the generator
makes no undos), retention floors and pruning, a queue persisted across a reload, derived features,
`editInstance` and `setPoses`, drawings, print setups, fonts and exploded views, and regen (geometry
is never built, so intent is checked through names only).

## Implications for ADR 0009 and T7.1a

For ADR 0009 (T7.0d):

1. **Keep client-chosen ids and the client remap.** Every collision in 48,800 commands was resolved
   on the client; the remap is about 0.01 ms per command (2 to 3 % of a 1,000-command rebase, at most 14 % of the smaller ones). Server-assigned
   ids would still need the same queue rewrite for offline work and for commands naming ids of
   earlier pending ones (as the ADR's alternatives already say), and would not help with any of the
   cases above. Replica-unique ids would avoid renames, and with them case 7, at the cost the ADR
   already rejected; numeric-aware comparison solves case 7 more cheaply.
2. **Decision 2: add `created` to the sync entry.** The ids the command allocates, per scope and
   counter, computed by the client against the document it made the command on and rewritten with
   the command. The server refuses `id-reused` when a created id is below its counter, before
   applying (case 4). `created` is part of the entry's storage form and of `SyncEntrySchema`.
3. **Decision 3: the server also refuses counter regressions** (any counter below its high-water
   mark, including a part scope that comes back), as an invariant check after `applyCommand`.
4. **Decision 4: an in-flight entry whose created ids are below the confirmed counters is known
   refused** and renamed in the client's naming at once (case 2), without editing what was sent.
   Verdict state is per `clientSeq` and cleared when an entry leaves flight (case 10).
5. **Decision 5: one simultaneous table, in the client's current naming, over the whole queue**
   (case 1), rather than a table per entry applied to later entries; a dropped entry's ids become
   tombstones (case 3); a duplicated part inherits its source's renames (case 5); names that belong
   to another part are resolved through the document (case 6).
6. **Decision 7 needs a sentence on stale edits** (case 9): either core lets an `editFeature`
   re-introduce sub-ids that the same feature held before (restore semantics for its own ids), or
   the remap treats such sub-ids as fresh and renames them with their references. Until then they
   are dropped and reported like any conflict.
7. **Restores are rebased as intent**: a `replaceDocument` entry records which version it restores,
   and the client re-derives the document on the head at every replay (case 8). Decision 9's branch
   merge is the same rule.
8. **Positional state causes most drops.** The rollback bar is shared document state, and adds,
   `setRollback`, reorder and restore indexes are positions. Either make the bar per-client view
   state (not synced) and let adds name an anchor ("after feature X", or the end), or accept that
   moving the bar refuses other clients' adds. This is the largest single lever on the drop rate
   (five clients: 19.0 % with the shared bar, 8.3 % without `setRollback`).
9. **Decision 11: prefer an ordered channel for submits.** With every request delayed independently,
   `predecessor-unknown` answers ran at 10 to 24 per accepted entry in every busy scenario; with one ordered channel per
   client (the WebSocket the ADR already opens, or HTTP requests sent in order on one connection)
   they were 0. Keep `predecessor-unknown` as the backstop.

For T7.1a:

1. **`createdIds` is computed on the client's document, not the server's head**, and travels in the
   entry (decision 2 above). The spike gets it from counter diffs (`scopes.ts`), which is simple and
   covers every scope; diffs must ignore scopes the command creates (an empty `addPart`, or the copied
   counters of a `duplicatePart`).
2. **`remapIds(commands, table)` needs a resolver argument** (instance to part, setup to part, from a
   document plus the queue) and position-aware tombstones; its scope list is the walker's in
   `remap.ts`. Walk per schema rather than by shape where the spike guessed (free-text keys, record
   keys); the spike's shape rules found no false positive in these runs, but they are a list to keep
   in step by hand.
3. **The name parser and printer**: every form of the ADR's decision 5 list is in `names.test.ts`.
   Add a comparison helper for names, and decide whether the kernel moves to numeric-aware order
   (a naming-scheme bump) or the remap reports a reversal as a warning (case 7).
4. **Fix `restoredDocument`** for parts deleted since the version (case 8), so a restore never sets
   a counter below its high-water mark; the document may need to remember deleted parts' counters.
5. **Property tests can use the intent signature as their oracle**: tag items, run random concurrent
   streams, and check that every reference still points at its tag. It found every bug above that
   convergence and `checkDocument` missed.
6. **Golden logs** should include the cases above as fixed sequences: two concurrent sketch edits
   adding one entity id, an in-flight collision followed by an edit of the remote feature, a dropped
   head with a held follower, a duplicate of a part that takes remote features, a stale restore.
