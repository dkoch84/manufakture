# T0.4 spike: planegcs sketch solver

- Status: done
- Date: 2026-09-26
- Code: [`spikes/planegcs/`](../../spikes/planegcs/)
- Raw results: [`spikes/planegcs/results/`](../../spikes/planegcs/results/) (every number below comes from these files)

## Summary

`@salusoft89/planegcs` (FreeCAD's PlaneGCS compiled to WebAssembly) is usable as the 2D constraint solver, with a small, well-understood list of things to fix before sketches get large.

- **Correctness.** DOF counting, a tangent arc with a radius, and redundant/conflicting constraint detection all work, and the Vitest suite pins every case down (19 tests). The rectangle goes 16, 8, 4, 2, 0 DOF as constraints are added; the rounded rectangle goes 21, 11, 7, 5, 2, 0.
- **Conflict reporting is good enough for a first sketcher UI**, with caveats: it lists every constraint that takes part in a conflict as one flat list (no per-group structure, no "remove this one" suggestion), and the diagnosis is only refreshed when a constraint is added or removed, not when a value changes.
- **Latency.** At 50 entities every configuration is well under the 16 ms target: DogLeg re-solves in 1.7 to 2.9 ms per move, a FreeCAD-style drag in 3.1 ms. At 200 entities nothing robust is: 56 ms (DogLeg, drag held by driving constraints), 131 ms (FreeCAD-style drag) and 135 ms (dimension change on a fully constrained sketch). The cost is dense linear algebra over one coupled system.
- **DogLeg is the right default.** LM converges too but is 1.8 to 3 times slower at 50 and 200 entities. BFGS is fast but failed to converge on every move of the 50 and 200-entity dimension change (60 of 60), leaving 2.7 mm of error at 200.
- **Worker vs main thread: the worker costs nothing measurable.** Round-trip overhead of `postMessage` there and back is a median of 0.02 to 0.12 ms on top of the solve. Solve in a worker.
- **The published binary has a fixed 16 MiB heap** and aborts with `Aborted(OOM)` from 130 entities in the spike's sketches; 200 entities needs 40 MiB. It also needs `'unsafe-eval'` under a Content Security Policy. Both are build flags, so the product should build its own planegcs wasm.

Recommendation for T1.5: planegcs 1.2.0 (pinned) in a solver worker, behind the project's own thin wrapper over `GcsSystem` with stable constraint tags, DogLeg by default, FreeCAD's tangency model, and a project-built wasm with memory growth before sketches pass about 100 entities. Details in [Recommendation for T1.5](#recommendation-for-t15).

## What the spike does

```
spikes/planegcs/
  src/sketch.ts        sketch builders: rectangle, rounded rectangle (tangent arc), N-entity chain
  src/solver.ts        loading (optionally with a larger memory), analyze(): solve + DOF + conflict lists
  src/wasm-memory.ts   reads and rewrites the wasm memory limits (spike-only, see Memory)
  src/bench.ts         DragSession: the drag benchmark shared by Node, the page and the worker
  src/worker.ts        solver worker (plain postMessage, parameters returned as a transferred Float64Array)
  src/main.ts          window.spike for the measurement script
  src/solver.test.ts   the proof for steps 2 to 4, plus the behaviours this document relies on
  scripts/measure.ts   measurement driver (sections: sizes, limits, node, browser)
  results/             raw JSON
```

Sketches follow FreeCAD's model: every line owns its two endpoints and connectivity is a `p2p_coincident`; an arc is a centre, start and end point plus `arc_rules` (4 equations tying the endpoints to centre, radius and angles).

- **Rectangle** (step 2): 4 lines, 8 points. Coincident corners, 2 `horizontal_l`, 2 `vertical_l`, width and height as `p2p_distance`, and the bottom-left corner made coincident with a fixed origin point.
- **Rounded rectangle** (step 3): the top-right corner is a tangent arc: 4 lines + 1 arc, 11 points and 3 arc parameters (25 unknowns). Tangent joints, `arc_radius` 6, width 40, height 25.
- **Chain** (step 5): N/5 rounded rectangles in a row, each bottom-left corner horizontally aligned with the previous bottom-right corner. planegcs solves decoupled parts of a sketch as separate subsystems, so coupling the units is what makes this one N-entity solve and not N/5 small ones. It is a demanding case on purpose. `full` mode adds every dimension plus a gap distance per link (DOF 0); `free` mode has no dimensions, as a sketch has while being drawn.

Benchmark scenarios, each a sequence of moves where one move is what a `pointermove` handler would do (update a target, solve, read every parameter back):

| Scenario | Sketch        | What moves                                                                                                                                                                                                                                                                         |
| -------- | ------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `drag`   | chain, `free` | A corner of the middle unit, held by two **temporary** `coordinate_x`/`coordinate_y` constraints: how FreeCAD's Sketcher drags. Temporary constraints do not count as DOF and make planegcs solve that part with its SQP routine whatever algorithm is requested, so it runs once. |
| `pin`    | chain, `free` | The same point and path, held by two **driving** coordinate constraints, so each move uses the requested algorithm. Adding them costs one re-diagnosis at drag start, and it only works while the point still has DOF.                                                             |
| `scrub`  | chain, `full` | The first unit's width, a sketch parameter, swings 30 to 50 mm (as when dragging or typing a dimension). The whole chain shifts, so every unit is re-solved.                                                                                                                       |

The drag target moves around a 10 mm circle in 60 steps (about 1 mm per move). To reproduce: `pnpm --filter @manufakture/spike-planegcs measure` (about 3 minutes; set `SPIKE_BROWSER_LD_LIBRARY_PATH` if Chromium's system libraries are missing, as in the T0.2 spike), or name sections: `measure sizes`, `measure limits`, `measure node`, `measure browser`. `pnpm --filter @manufakture/spike-planegcs test` runs the tests. The spike is kept outside the pnpm workspace; add it back to run these (see [spikes/README.md](../../spikes/README.md)).

## Method

- **Latency**: per configuration, a fresh wasm instance, `setup()` (load the sketch, first solve, drag start), then 5 warm-up moves and 60 measured moves; median and p95 (nearest rank). "Main thread" is the time for one move on the page's main thread. "Worker round trip" is measured on the page from `postMessage` to the reply, so it includes the solve in the worker, reading the parameters back, the copy and transfer of the `Float64Array`, and both message hops. "Node" is the same move in Node.
- Each move's result is checked: `errorMm` is the dragged point's distance from the pointer (drag, pin), or the error of the last unit's position against the exact answer (scrub). All figures are in `node.json` and `browser.json` (`maxErrorMm`, `failed`).
- All latency runs use the published wasm with its memory raised to 64 MiB, because the stock 16 MiB cannot hold the 200-entity sketch (see [Memory](#memory-the-fixed-16-mib-heap)). A control run shows the larger memory does not change speed: scrub, 50 entities, DogLeg, median 2.829 ms stock against 2.847 ms at 64 MiB (`node.json`, `memoryControl`).

## Results

### DOF, tangent arc and radius (steps 2 and 3)

Proved by `src/solver.test.ts`. Every case solves from a perturbed start (points offset by up to 2 mm) to the exact geometry with each algorithm.

| Rectangle, cumulative                       | DOF |
| ------------------------------------------- | --- |
| 4 lines (8 points)                          | 16  |
| + 4 coincident                              | 8   |
| + 2 horizontal, 2 vertical                  | 4   |
| + width, height                             | 2   |
| + corner coincident with fixed origin point | 0   |

| Rounded rectangle, cumulative    | DOF |
| -------------------------------- | --- |
| 4 lines + arc (with `arc_rules`) | 21  |
| + 5 coincident                   | 11  |
| + 2 horizontal, 2 vertical       | 7   |
| + 2 tangencies                   | 5   |
| + width, height, `arc_radius`    | 2   |
| + anchor                         | 0   |

The solved arc has centre (34, 19), radius 6, start angle 0 and end angle pi/2, and its endpoints land on (40, 19) and (34, 25).

**How tangency is modelled matters.** The spike first joined line and arc with `p2p_coincident` plus `tangent_la` (distance from the arc centre to the line equals the radius). At the exact solution that pair is degenerate: the line touches the circle at the shared point, and the tangency equation's gradient becomes dependent on the coincident's. Diagnosed from the exact geometry, the sketch reports both tangencies as redundant and DOF 2 instead of 0; from a perturbed start it reports DOF 0. The same degeneracy made the Jacobian singular at the solution, so DogLeg converged only linearly (15 iterations for one 50-entity move, seen with `DebugMode.IterationLevel`) and the early benchmarks were about twice as slow. FreeCAD models an endpoint-to-endpoint tangency as the coincident plus `angle_via_point` (the angle between the two curves' tangent directions at the shared point, here 0), which stays regular: DOF 0 and nothing redundant from exact geometry too. Both behaviours are tests; all numbers below use the FreeCAD model.

### Redundant and conflicting constraints (step 4)

The API, all on `GcsWrapper` (`w`):

| Call                                                   | Returns                                                                                           |
| ------------------------------------------------------ | ------------------------------------------------------------------------------------------------- |
| `w.solve(Algorithm.DogLeg)`                            | `SolveStatus`: `Success` 0, `Converged` 1, `Failed` 2, `SuccessfulSolutionInvalid` 3              |
| `w.gcs.dof()`                                          | DOF from the last diagnosis; -1 before the first solve and -1 whenever there are conflicts        |
| `w.get_gcs_conflicting_constraints()`                  | ids of the constraints in all conflict groups, one flat list in push order                        |
| `w.get_gcs_redundant_constraints()`                    | ids of the constraints the solver chose to drop as redundant (their equations are all consistent) |
| `w.get_gcs_partially_redundant_constraints()`          | ids of multi-equation constraints of which only some equations were dropped                       |
| `w.has_gcs_conflicting_constraints()` (and the others) | booleans                                                                                          |

The diagnosis runs inside `solve()` (FreeCAD's `System::initSolution`: a QR decomposition of the Jacobian), so read DOF and the lists after solving. What it reported, starting from the DOF 0 rectangle:

| Added constraint                                 | Status (DogLeg) | DOF | Conflicting                                                             | Redundant   |
| ------------------------------------------------ | --------------- | --- | ----------------------------------------------------------------------- | ----------- |
| second width, same value (40)                    | Converged       | 0   | none                                                                    | the new one |
| `horizontal_pp` on the already horizontal bottom | Converged       | 0   | none                                                                    | the new one |
| diagonal at its true length                      | Converged       | 0   | none                                                                    | the new one |
| second width, different value (50)               | Failed          | -1  | `r:width`, the new one                                                  | none        |
| `vertical_l` on the horizontal bottom line       | Failed          | -1  | `r:h-bottom`, `r:width`, the new one                                    | none        |
| diagonal of 10 mm                                | Failed          | -1  | `r:co-b`, `r:h-bottom`, `r:v-right`, `r:width`, `r:height`, the new one | none        |

What that means for the sketcher's conflict explanation:

- **Conflicting**: the solver lists every constraint that takes part in the conflict, not only the one just added, so the UI can highlight the whole loop. The list is flat and sorted by push order: with two independent conflicts in one sketch, the groups are merged (FreeCAD computes `conflictGroups` internally; exporting them is open issue #1). There is no "suggested culprit" for a conflict; the UI has to supply one, and "the constraint the user just added" is the obvious choice.
- **Redundant**: the solver picks which constraint to drop (the one in the most dependent groups, then the one with the fewest equations, then the newest). A test shows that pushing the duplicate first makes `r:width` the redundant one, so push constraints in creation order and the most recent one is blamed.
- **Status is not a conflict signal.** DogLeg and LM return `Failed` on the conflicts above, but BFGS returns `Converged` for the same conflicting sketch, and every redundant case returns `Converged`. A sketch can also fail without any conflict (a negative width, probed during the spike). Read the lists, not the status.
- **The diagnosis is cached until a constraint is added or removed.** Changing a value through a sketch param (a dimension edit) does not re-run it. A test makes a redundant diagonal contradict the rectangle by editing its value: `solve()` still says `Converged`, the conflicting list stays empty and the diagonal stays "redundant", because redundant constraints are left out of the solve. Rebuilding the system (clear and push again) then reports the six-constraint conflict. So after a dimension edit, either rebuild or check the redundant constraints' residuals.
- **Temporary constraints never appear** in these lists and do not reduce DOF (tag -1 is excluded from the diagnosis). Tag 0 would also be excluded ("high priority"); the wrapper never assigns it.
- **Partially redundant**: the call exists, but the spike did not construct a case that triggers it (duplicates of coincident and horizontal constraints were all reported fully redundant).

Largest error per configuration (`maxErrorMm`, main thread): under 1e-9 mm everywhere except BFGS on `scrub`, which reached 3e-8 mm at 50 entities and 2.7 mm at 200. The system sizes: 10, 50 and 200 entities are 58, 274 and 1,084 solver parameters in `free` mode and 63, 311 and 1,241 in `full` mode.

Reading the table:

- **50 entities meets the target with a wide margin** in every scenario: the worst robust configuration is LM at 4.6 ms p95.
- **200 entities misses it** except `pin` with BFGS (9.5 ms p95). Every call re-partitions the system (`solve_system` always runs `initSolution`); an unchanged re-solve (`idleSolveMs` in the results) costs 2.4 ms for `pin` with DogLeg at 200 but 34 ms for the SQP drag, whose per-call work is dense in the size of the whole coupled system. The chain is one coupled system on purpose; sketches made of several unconnected profiles are split into subsystems by planegcs and cost less.
- **DogLeg** converged on every move of every scenario and was fastest on the fully constrained `scrub`. **LM** also always converged, at 1.8 to 3 times DogLeg's cost at 50 and 200 entities. **BFGS** was the fastest `pin` solver at 50 and 200 entities but did not converge on the fully constrained `scrub` at 50 and 200 (status `Failed` on all 60 moves, with visible error at 200), so it is not usable as the general solver.
- Main thread, worker and Node agree to within 8 per cent at 50 and 200 entities: V8 runs the same wasm in all three.

### Main thread vs Web Worker (step 6)

- **Messaging overhead**: an empty ping round trip is 0.01 ms median, 0.02 ms p95 (200 samples). Over the solve itself, the worker round trip adds a median of 0.02 to 0.12 ms and a p95 of 0.035 to 0.325 ms (`roundTripOverheadMs`), including copying and transferring up to 1,241 parameters (about 10 KB).
- **Start-up**: loading planegcs takes 4.3 to 10.2 ms on the main thread; starting a worker and loading it there takes 11.0 to 14.0 ms (5 runs, `init` in `browser.json`).
- There is therefore no latency argument for main-thread solving. The worker's real benefit shows at 200 entities: a 130 ms solve on the main thread is 8 dropped frames of pointer handling and rendering; in a worker the viewport keeps drawing and the next target can replace a queued one.

### Memory: the fixed 16 MiB heap

From `limits.json` (one solve with diagnosis, fresh instance per attempt):

- With the published binary, chains of 125 entities solve and 130 abort with `Aborted(OOM)`, in both `full` and `free` mode (so it is the parameter count, roughly 650 here, not the constraint count). The abort poisons the instance: it must be thrown away.
- 200 entities (`full`) still aborts at 32 MiB and solves at 40 MiB.
- 300 rebuilds of the 50-entity sketch in one instance (`clear_data()` and push again) completed without growth problems.

To measure beyond the limit without a rebuild toolchain, `src/wasm-memory.ts` rewrites the min/max limits in the binary's memory section (same encoded width, so no offsets move) and the module is instantiated through Emscripten's `instantiateWasm` hook. That is a spike device only; the product should build planegcs with `-sALLOW_MEMORY_GROWTH`.

## Gotchas

- `dof()` is -1 until the first `solve()`, and -1 again whenever there are conflicts.
- The default debug mode (`Minimal`) prints a line from inside the wasm (`console.log`) on diagnoses; set `wrapper.debug_mode = DebugMode.NoDebug`. `IterationLevel` is useful: it prints subsystem sizes and every iteration.
- `GcsWrapper` gives each constraint the tag "position in push order" and maps tags back through that position. It has no way to remove a primitive (the code is commented out), so the only supported edit is a full rebuild.
- `get_p_params()` returns an embind vector that must be `.delete()`d; reading it element by element costs about 0.1 ms at 1,084 to 1,241 parameters (median `moveMs` minus median `solveMs`).
- In Vite the glue's Node branch (`await import("module")`) produces "externalized for browser compatibility" warnings at build time; harmless. Load the wasm through a `?url` import and `locateFile` (or fetch the bytes and use `instantiateWasm`).
- The typings only declare `locateFile` for `init_planegcs_module`; `instantiateWasm` works but needs a cast.
- Under a Content Security Policy without `'unsafe-eval'`, initialisation throws `EvalError`: embind generates invokers with `new Function` (reported in open PR #12, which adds `-sDYNAMIC_EXECUTION=0`). Not tested here; the spike page sets no CSP.

## Ansatz (research only, not measured)

[Ansatz](https://github.com/LAU-MARS/Ansatz) (`ansatz-wasm` on npm) is a Rust constraint solver for 2D sketches and 3D assemblies, with a wasm build and JSON in/out. Read on 2026-09-26; **nothing here was measured.**

- **Status**: created 2026-09-09, last push 2026-09-11, 7 commits by one author, 1 star, npm `ansatz-wasm` 0.3.0 (823 downloads in the month to 2026-09-24). MIT license, GPLv3-compatible.
- **2D sketches are not implemented yet.** Its README says general 2D sketch constraints are still `unsupported_constraint`; the only 2D path is a closed-form point-distance case. So it cannot be a fallback for the sketcher today.
- **3D is where it is interesting**: rigid-body mates (planar contact, coaxial, distance, angle, fixed), joints (revolute, cylindrical, prismatic, spherical) with per-joint diagnostics, solved by Levenberg-Marquardt over an exponential-map pose parameterisation with analytic Jacobians and SVD rank analysis (nalgebra, dense).
- **Diagnostics-first design** is what we want for conflict explanation: it reports DOF, redundant and conflicting constraint groups, per-constraint residuals and a human-readable message per entry, which is exactly what planegcs flattens away.
- It runs single-threaded, no SharedArrayBuffer needed, and aims for bit-identical results across platforms.

Verdict: too young to depend on (days old, single author). Worth re-checking when the product reaches assemblies and mates; its diagnostic report shape is a good reference for our own solver wrapper's API either way. [SolveSpace](https://github.com/solvespace/solvespace)'s `libslvs` (GPLv3, also has 2D and 3D) is the other candidate to look at then.

## Recommendation for T1.5

1. **Solver**: `@salusoft89/planegcs` 1.2.0, pinned, loaded in a **dedicated solver worker**. The worker round trip costs about 0.1 ms, and large solves then never block the viewport. Coalesce pointer moves in the worker (latest target wins) so a slow solve never queues stale drags.
2. **Own wrapper, not `GcsWrapper`**: a thin project class over `GcsSystem` (the embind API: `push_p_param`, `add_constraint_*`, `solve_system`, `get_conflicting`, ...) that uses the sketch data model's stable constraint ids as numeric tags, so the conflict and redundancy lists map straight back to model ids and constraints can be removed with `clear_by_id`. `GcsWrapper`'s positional tags and lack of removal make it a rebuild-only API. Keep the solver behind a small interface (load sketch, solve, drag, diagnose) so it can be swapped.
3. **Data model follows FreeCAD**: lines own their endpoints; coincident for connectivity; **endpoint tangency as coincident plus `angle_via_point`**, never `tangent_la` at a shared endpoint; arcs with `arc_rules`. Dimension values as sketch params, so a dimension edit is a value change, not a rebuild.
4. **Algorithms**: DogLeg by default; LM as a retry on failure; not BFGS.
5. **Dragging**: FreeCAD's way, temporary coordinate constraints on the dragged point (no DOF consumed, never conflicts): 3.1 ms per move at 50 entities. Keep driving-constraint drag (`pin`) in mind for big sketches.
6. **Diagnosis**: run after every topology change, and after value edits that touch redundant constraints (or check their residuals), since the cached diagnosis does not see value changes. Explain conflicts by highlighting the whole list and blaming the most recently added constraint; do not rely on the solve status.
7. **Before sketches pass about 100 entities** (a follow-up task, not T1.5 itself): build planegcs in this repo with `-sALLOW_MEMORY_GROWTH` and `-sDYNAMIC_EXECUTION=0`, export conflict groups, and expose `initSolution` separately so a drag does not re-partition the system on every move; then re-run this spike's benchmark against it.
