## Summary

- **OpenCAMLib builds with a current Emscripten, as an ES module plus a separate `.wasm`, with three small changes and no edits to its C++.** The recipe (`spikes/opencamlib/build/build-ocl.sh`) pins emsdk (checkout `e566f7b`, SDK 6.0.10), cmake 4.4.3 and ninja 1.13.2 from PyPI, Boost 1.89.0 headers and OCL commit `95b036f` (master, 2025-02-12), and builds in 8 to 14 seconds. It is a root-free local script, run on a workstation; it has not been run in a container or CI yet (moving it into CI is part of adopting OCL, below). The result is a 329,046-byte `.wasm` (119 KB gzipped) and a 103 KB glue module. Four builds gave the same `.wasm` SHA-256. It loads in Node, in a Node worker thread and in a browser module worker (headless Chromium 153), where the `.wasm` arrives as its own request.
- **Our TypeScript drop-cutter gives the same answers as OCL for flat and ball cutters**: on 892,104 points (2 meshes, 3 flat and ball tools; 44,814 points per tool on the bracket, 252,554 on the 99,200-triangle part) the largest Z difference is 2.3e-12 mm. Both pass checks that trust neither: no ball centre is closer than R to the mesh, every ball not resting on the floor touches it, and no mesh vertex lies inside any tool.
- **OCL's V cutter (`ConeCutter`) gouges; ours does not.** On the filleted part OCL's tip is up to 0.108 mm too low at 4,209 of 252,554 points (over 10 micrometres), on the bracket up to 0.0066 mm. A brute-force lower bound (every triangle under the tool sampled on a fine grid) proves it: at the worst points the bound converges to the TypeScript height (to 5e-5 mm at 2,500 steps) and lies 0.108 mm above OCL's.
- **The TypeScript cutter is 2.5 to 6.9 times faster than our single-threaded OCL build** for the same points: 2.2 to 6.7 s against 14.9 to 28.1 s on the 99,200-triangle part (Node 26, medians of 3 after one first run). OCL's kd-tree search copies every candidate triangle into a new `std::list` per point; natively it hides that behind OpenMP threads, which a single-threaded `.wasm` does not have.
- **Memory**: neither leaks. Over 12 repeated runs the OCL heap top stays flat after the first (dropping, adaptive dropping and waterline, every embind object deleted), and so does the JS heap for the TypeScript cutter. But OCL needs a large heap: 131 MiB of wasm memory for dropping on the 99,200-triangle part (153 MiB for a waterline), against 15.6 MiB of JS heap in total for the TypeScript cutter and its index.
- **AdaptivePathDropCutter and Waterline work and are sane.** Adaptive dropping puts no point below the mesh (checked against the TypeScript cutter) and cuts the point count 3.6 to 6.4 times. Waterline and AdaptiveWaterline give closed loops exactly at the requested level, hugging the part (ball: centre distance equal to R within 8e-4 mm; flat: a tool 0.01 mm smaller clears, one 0.01 mm larger collides), in 0.35 to 1.0 s per level on the large part (adaptive: 1.1 to 3.3 s).
- **License**: the repository says LGPL-2.1 (`COPYING`), every C++ source that goes into the `.wasm` says "LGPL 2.1 or any later version", except the embind bindings file, which has no header, was written by the author of the npm package, and that package declares `LGPL-3.0`. The stricter reading makes the OCL module LGPL-3.0, which ADR 0006 does not allow without an amendment.

Recommendation: **T5.5a uses our TypeScript drop-cutter for parallel finishing, and OCL is not adopted, so ADR 0006 needs no amendment.** The TypeScript cutter matches OCL to 1e-11 mm where OCL is right, is right where OCL's V cutter gouges, is several times faster in the browser's single thread, and uses an eighth of the memory. **Waterline is out of scope for M5**: z-level roughing (plane sections cleared by the pocket operation) and parallel finishing cover the plywood sign and a filleted block; waterline finishing is a follow-up, built in TypeScript on the same cutter geometry, or a reason to revisit OCL with the amendment drafted below. Details under [Recommendations](#recommendations).

## Building OCL

`build-ocl.sh` fetches emsdk (at a pinned commit), cmake and ninja (pinned versions from PyPI into a venv), the Boost headers and OCL at the pinned commit into a work directory, copies the checkout with `git archive`, replaces one file, and runs `emcmake cmake` with `BUILD_EMSCRIPTEN_LIB=ON`, `USE_OPENMP=OFF` and `CMAKE_BUILD_TYPE=Release`. What it took:

1. **Configure from the repository root, not `src/`.** `src/CMakeLists.txt` has no `cmake_minimum_required`, and CMake 4.4 refuses it (`CMP0069 is not set` from `check_ipo_supported`). The root `CMakeLists.txt` sets 3.15...3.25 and includes `src`.
2. **Compile the bindings as C++17.** OCL sets `CMAKE_CXX_STANDARD 14`; current embind's `bind.h` uses `std::optional` and `std::conjunction` and fails with 20 errors. Setting `CXX_STANDARD 17` on the `ocl` target is enough; the library sources compile unchanged.
3. **Replace the link flags.** Upstream's `emscriptenlib.cmake` links with `SINGLE_FILE=1` (the `.wasm` inlined as base64), `ENVIRONMENT=web`, `--closure 1`, `ASSERTIONS=1` and `FORCE_FILESYSTEM`. Our [`emscriptenlib.cmake`](../../spikes/opencamlib/build/emscriptenlib.cmake) keeps the same sources and the same upstream `emscriptenlib.cpp`, and links with:

   ```
   -O3 -lembind -sMODULARIZE=1 -sEXPORT_ES6=1 -sEXPORT_NAME=ocl -sENVIRONMENT=web,worker,node
   -sALLOW_MEMORY_GROWTH=1 -sINITIAL_MEMORY=33554432 -sSTACK_SIZE=1048576 -sASSERTIONS=0
   -sEXPORTED_FUNCTIONS=['_malloc','_free','_sbrk'] -sEXPORTED_RUNTIME_METHODS=['HEAPF64','HEAPU8']
   ```

   (compiled with `-O3`, and CMake's IPO turns on `-flto`). `_sbrk` is exported only for the memory probe.

The compiler printed no warnings. Output: `ocl.mjs` 103,248 bytes (27.6 KB gzipped), `ocl.wasm` 329,046 bytes (119 KB gzipped), SHA-256 `0c6bc7b289c389e5f4a5a76a54c1bf03eaf63249823936f320a5851d6ecaf514` in all four builds. The script also copies OCL's `COPYING`, Boost's `LICENSE_1_0.txt` and Emscripten's `LICENSE` next to the output, as the notices would need.

**Loading**: in Node the module reads `ocl.wasm` next to itself; in a Node worker thread the same (10.6 ms to instantiate); in a browser module worker it fetches `ocl.wasm` as a separate request (`/out/ocl.mjs`, then `/out/ocl.wasm`, 9.3 ms), and a ball drop over the bracket raster takes 668 ms there against 622 ms in Node, with the same points as the TypeScript cutter (max difference 5.4e-14 mm).

**API rough edges** found on the way, for whoever revisits OCL:

- Triangles go in one embind call at a time (`new Point` x 3, `new Triangle`, `addTriangle`, five deletes): 196 to 355 ms for the 99,200-triangle part (355 ms on its first build). Results come out one embind `CLPoint` copy at a time: 142 to 160 ms for 252,554 points. Both are small next to `run()`, but a production binding would pass typed arrays.
- `PathDropCutter.getCLPoints()` is bound on the `Operation` base class, whose implementation returns a copy of a freshly `new`ed empty vector: it always returns nothing and leaks the vector. `getPoints()` is the right call.
- An operation object keeps appending: running a `BatchDropCutter` twice doubles its points. The spike makes a fresh operation per run.
- `ConeCutter`'s angle is the half angle in radians; the tool length must exceed the part's height or the shaft is ignored.

- **Flat and ball agree to rounding.** The differences (1e-14 to 2e-12 mm) are floating-point order of operations, and they go both ways.
- **The V-bit differences are all one way: OCL lower.** 64 bracket points and 9,649 part points differ by more than a micrometre, 4,209 by more than 10 micrometres. For the three worst points per mesh the probe computes a brute-force lower bound (the cutter dropped onto every triangle under it, sampled on a 400-step barycentric grid, as if each sample were a vertex: that bound can only be at or below the true height). It is above OCL's height every time, by 0.106 to 0.108 mm on the part and 0.005 to 0.007 mm on the bracket, so OCL gouges; and it is below the TypeScript height by 0.0002 to 0.0026 mm, the grid's own error on the part's 30 mm tall wall triangles. Refining the grid at the worst point of each mesh (400, 1,000, 2,500 steps) closes that gap on the part to 0.0014, 0.00009 and 0.00006 mm, while the bound stays 0.107 to 0.108 mm above OCL; on the bracket the bound equals the TypeScript height to 1e-8 mm at every step count. The bound converges to the TypeScript answer. These figures are in `results/convergence.json`, written by `src/convergence.test.ts` (about 40 s, no OCL build needed: it reads the worst points from `results/compare.json`). The worst points sit 2.9 mm outside the block's side wall, under the rounded top edge, where the cone's side meets the fillet's facets and edges.
- **Independent sanity of both cutters** (`cases.ts`, sharing no code with either): for ball tools, no centre is closer to the mesh than R (worst 7.5e-14 mm for OCL, 3.3e-14 mm for TS) and every ball above the floor touches the mesh within 1e-6 mm; for every tool, no mesh vertex under the tool is inside it (worst 7e-15 mm). The vertex check cannot see OCL's V-bit gouge, because it happens on edges and facets; that is what the brute-force bound is for.
- **Why OCL is slower here**: `BatchDropCutter::dropCutter5` asks the kd-tree for the triangles under the tool, and the tree returns a newly allocated `std::list<Triangle>` (copies, about 200 bytes each) per point; the 1/4" tool overlaps about 400 triangles per point on the part. Natively OCL spreads the points over OpenMP threads, which this build cannot use (a threaded `.wasm` needs `SharedArrayBuffer`, cross-origin isolation and pthreads, which ADR 0002 avoided for the kernel too). The TypeScript cutter walks a uniform grid in place, with a stamp array instead of a set, and touches only flat typed arrays.

### The TypeScript drop-cutter

[`src/dropcutter.ts`](../../spikes/opencamlib/src/dropcutter.ts), 330 lines including comments, no dependencies. A cutter is described by its profile height above the tip, f(r), for r up to R: 0 for flat, R - sqrt(R^2 - r^2) for ball, r / tan(half angle) for a V-bit (a cone up to the full diameter). Each triangle bounds the tip three ways and the highest bound wins:

- **vertex**: v.z - f(r) for each corner within R of the axis;
- **facet**: the tool touches a plane at a point fixed by the plane's normal (ball: the centre minus R times the normal; flat: the rim on the uphill side; V-bit: the tip, or the rim when the plane is steeper than the cone); if that point is inside the triangle it gives the bound;
- **edge**: in the vertical plane through the edge, at distance d from the axis, the tool's section is f(sqrt(d^2 + s^2)) and the edge is a line z0 + m s. Their difference is concave in s for all three profiles, so its maximum over the part of the edge under the tool is the free maximum (closed form per profile: the far end for flat, s = m w / sqrt(1 + m^2) for ball, s = d q / sqrt(1 - q^2) with q = m tan(half angle) for the V-bit) clamped to that interval. No iteration, no tolerance.

The index is a uniform XY grid (cell size R, at least 0.5 mm) in a compressed layout: one prefix-sum array and one item array. It builds in 0.2 to 14.4 ms and the whole cutter for the 99,200-triangle part holds about 14 MB.

`dropcutter.test.ts` checks it against closed-form answers (a flat square, an inclined plane for each tool and both V-bit regimes, a ridge edge, a spike vertex, a horizontal edge and corner), against the brute-force bound on random meshes for flat, ball and 90 and 60 degree V-bits (never below it; above it only by the bound's sampling error at 240 steps: under 0.001 mm for the ball, under 0.04 mm for flat and V, whose rim and cone-edge contacts fall between samples on steep random triangles), and checks that the grid gives bit-identical answers at any cell size.

What it does not do yet, all straightforward: bull-nose cutters (the same scheme, with the torus handled like OCL does or by a numeric edge step), adaptive sampling, and skipping triangles that lie wholly below the current height (OCL's `below()` test), which would make it faster still.

## Waterline

`Waterline` and `AdaptiveWaterline` (sampling 0.5 mm, adaptive minimum 0.05 mm) with the 1/4" ball and flat tools, at four levels on the bracket and five on the part (through the base, the wall, the fillets and the boss).

- **Every loop is closed and at its level**: z equals the level exactly; the step from a loop's last point back to its first is never longer than its longest step (0.07 to 0.66 mm with 0.5 mm sampling), so the loops come back without the first point repeated, and a consumer must close them.
- **Every loop hugs the part without gouging.** Ball: the centre's distance to the mesh is R to within 8.5e-13 mm inside and 7.9e-4 mm outside (the worst on the part's lowest level, where the loop runs along the bottom fillet). Flat: a tool 0.01 mm smaller than the cutter clears the part at every loop point and one 0.01 mm larger collides.
- **Loops found**: one per level except the bracket's lowest (3 loops: the outline and the two counterbores).
- **Time per level**: bracket 4.5 to 31 ms (adaptive 11 to 136 ms); part 347 to 1,042 ms (adaptive 1.1 to 3.3 s). A waterline finish of a 30 mm part at 0.5 mm steps would be 60 levels, 20 to 60 s single-threaded on this mesh (estimate).

## Memory

`ocl.test.ts`, the filleted part, 12 runs in one module, each run building the `STLSurf`, the cutter and the operation and deleting all of them (a coarser raster, stepover 2 mm and sampling 0.5 mm, so a run takes about 1.5 s):

| Operation              | Heap top after each run (MiB)                 | Growth from run 1 to 12 | Wasm memory at the end |
| ---------------------- | --------------------------------------------- | ----------------------- | ---------------------- |
| PathDropCutter         | 118.2, then 131.2 for runs 2 to 12            | 13 MiB, all at run 2    | 138 MiB                |
| AdaptivePathDropCutter | 131.2 for all 12                              | 0                       | 138 MiB                |
| Waterline (z 20)       | 152.8 for all 12                              | 0                       | 166 MiB                |
| TypeScript cutter      | JS heap used 15.63 down to 15.54 after `gc()` | -91 KiB                 | (no wasm)              |

The heap top (`sbrk(0)`) only moves when the allocator cannot reuse freed memory, so a flat line means deleting every embind object frees everything. The step at run 2 is the allocator settling (fragmentation), not a leak: it never moves again. The memory itself is the problem: OCL keeps each triangle as a `Triangle` object in a `std::list` (three `Point`s, a normal, a bounding box, list links) plus the kd-tree: about 1.2 KiB of heap per triangle in all, so the 99,200-triangle part takes 118 MiB on the first run, and a wasm heap never shrinks back. The TypeScript cutter stores about 140 bytes per triangle in typed arrays (coordinates, plane, XY box, grid entries).

## Recommendations

1. **T5.5a builds parallel finishing on the TypeScript drop-cutter**, moved from `spikes/opencamlib/src/dropcutter.ts` into `packages/cam` (pure TypeScript, as decision 1 of the plan wants) with its tests, the brute-force bound and the closed-form cases. Add bull-nose cutters there if the tool library has them, adaptive sampling (bisect where neighbouring segments turn more than a limit), and the "triangle wholly below the current height" skip. The CAM worker runs it; a 252,554-point finish of the 99,200-triangle part takes 2.2 to 6.7 s, so the worker must report progress and be cancellable between raster lines.
2. **No ADR 0006 amendment for M5.** The TypeScript cutter has no dependencies; nothing new ships. The drafted wording above stays here for whoever revisits OCL.
3. **Waterline is out of scope for M5.** T5.5a should drop "optionally waterline": the plywood sign needs none, z-level roughing comes from plane sections and the pocket operation (T5.1e, T5.2c), and a parallel finish covers a filleted block. OCL's waterline works well and is the strongest reason to take OCL later; a TypeScript waterline (push-cutter intervals along X and Y fibres plus a loop weave, as OCL does, reusing this cutter's profiles) is the alternative and is the bigger job.
