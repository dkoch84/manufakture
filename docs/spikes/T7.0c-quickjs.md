## Summary

- **QuickJS is small and starts fast.** The synchronous release `.wasm` is 503,134 bytes raw and 199,016 brotli (QuickJS-ng 528,551 and 212,245); the asyncified builds are about twice the raw size (1,027,523 and 1,075,905) and 43 % more brotli (284,509 and 301,428). The host JavaScript (core, glue, FFI) is 14,247 bytes brotli. In a module worker the first scripted feature (fetch and streaming compile, instantiate, first run) costs 15 to 27 ms in Chromium, Firefox and WebKit, against 582 to 1,278 ms for the kernel in the same worker.
- **A host call costs 0.8 to 2.3 µs** with the sync build (two numbers in, one out), 3.6 to 6.9 µs with a `[x, y, z]` array each way (2.4 to 4.6 through a JSON string). In the asyncified build a promise-returning host call costs 3.8 to 22.6 µs already resolved and 16 to 38 µs when it waits one macrotask, as a `KernelService` batch does.
- **The kernel dominates a script's time, but the synchronous session is never slower.** A script cutting 24 holes (98 host calls) takes 69 to 81 ms through the synchronous kernel and 72 to 92 ms through the asyncified build awaiting one `KernelService.run` per call; 300 cheap queries take 104 to 156 ms against 118 to 193 ms. All paths give bit-identical results in every browser.
- **Chosen kernel access path: the synchronous kernel session** with the sync release build of Bellard's QuickJS (reasons under [Recommendations](#recommendations)).
- **The interrupt handler stops script loops within 2 ms of the deadline (5 ms in one WebKit case, whose timer steps by 1 ms), but not loops of builtins.** QuickJS polls the handler on a counter of bytecode steps, not on time: a loop calling `a.slice().sort()` on 20,000 numbers ran 8.4 to 11.9 s past a 100 ms deadline, and a loop of `JSON.parse(JSON.stringify(...))` 1.7 to 3.2 s, in every browser and both builds.
- **`setMemoryLimit` is not a byte limit in these builds.** QuickJS reports `malloc_usable_size unavailable`; with a 64 MiB limit one script grew the instance to the 2 GiB maximum before failing, another to 429 MiB. A `WebAssembly.Memory` with a `maximum` of 16 + 64 MiB stops every allocation bomb at 79.9 MiB in 36 to 263 ms. One kind of bomb (many small objects) then throws `null`, and the instance is unusable afterwards in Node and all three browsers; in an earlier run of this spike, touching that runtime again crashed the Chromium page.
- **The stack limit must stay below the host's stack.** Deep recursion overflows the browser's own stack first, as a host exception through `evalCode`, at a QuickJS limit of 192 KiB (QuickJS-ng) or 256 KiB (QuickJS) in Chromium. At 128 KiB QuickJS's own check fires first everywhere (680 frames of a three-argument function).
- **One more instance from a compiled module costs 0.5 to 2 ms and 16 MiB of linear memory** (the minimum the `.wasm` declares), so ADR 0010 decision 4's per-document instance is cheap in time; its memory is the real cost.
- **The Asyncify exception is about suspension, not values**: all runtimes and contexts in one asyncified module share one suspension. Two contexts of one module awaiting host calls at once fail with `QuickJSAsyncifyError: Already suspended`; in separate modules they work; a host function that re-enters and suspends again fails the same way. Disposing an async runtime that ever had a host function also throws in 0.32.0.
- **QuickJS is 30 to 45 times slower than V8** on an arithmetic loop (1,000,000 iterations: 84 ms against 2.5 ms in Chromium); on 10,000 iterations 0.8 to 1.0 ms against 0.025 (Chromium) and 0.1 (Firefox, WebKit).
- **Determinism holds.** Of 18,143 values (Math functions over 431 inputs, `Math.pow`, formatting, sort), QuickJS and QuickJS-ng gave the same bits in Node, Chromium, Firefox and WebKit: zero differences in every pair. The host engines differ from each other in 646 to 1,234 values, and Node 26 and Chromium 153 (both V8) in 632. The build has no SIMD, no relaxed SIMD, no threads and no shared memory.
- **TypeScript erasure: sucrase 3.35.1**, 38,384 bytes brotli against 734,865 for ts-blank-space 0.9.0 (which bundles the TypeScript compiler). Both keep lines and columns of erasable code. Sucrase silently drops `namespace` blocks and `import x = require()`, which T7.2b must reject itself.

| -------------------------------------------- | -------------- | -------------- | ------------- | -------------- |

| **sort 20,000 numbers, default order, loop** | 9,612 / 11,205 | 9,951 / 11,942 | 8,678 / 8,669 | 8,424 / 10,208 |
| **JSON round trip of 500 objects, loop**     | 2,120 / 2,874  | 2,122 / 2,922  | 2,060 / 3,198 | 1,733 / 2,653  |

The two bold rows are the finding. A single `sort()` of 20,000 numbers takes about 6 ms, and the loop around it executes only a few bytecode steps per iteration; the handler, which QuickJS calls when a counter of bytecode branches and calls runs out, was called 6 times in the first 3 ms and then not again for 9.3 s (traced in Node). So **the time limit is soft against builtin-heavy loops**: a script can overrun its budget by thousands of times the cost of one builtin call. Regex backtracking and comparator sorts are fine, because they poll inside.

## Memory limits

Limit 64 MiB. Two ways to set it, in a fresh instance per case:

- **`setMemoryLimit`**: QuickJS's own limit, the instance free to grow to the variant's 2 GiB maximum;
- **Memory maximum**: the caller's `WebAssembly.Memory` created with `maximum: 256 + 64 * 16` pages (80 MiB: the 16 MiB the `.wasm` needs plus 64), so `malloc` itself fails there.

| Case                    | `setMemoryLimit`: outcome, ms, wasm memory after                            | Memory maximum: outcome, ms, wasm memory after           |
| ----------------------- | --------------------------------------------------------------------------- | -------------------------------------------------------- |
| arrays of doubles       | `InternalError: out of memory`, 898 to 1,196 ms, **2,048 MiB**              | `out of memory`, 36 to 46 ms, 79.9 MiB                   |
| one 1.6 GB Float64Array | `out of memory`, under 1 ms, 16 MiB                                         | the same                                                 |
| string doubling         | `InternalError: string too long`, under 1 ms, 16 MiB                        | the same                                                 |
| many objects in a `Map` | throws `null` (not an Error), 619 to 1,062 ms, **429 MiB**; runtime corrupt | throws `null`, 125 to 263 ms, 79.9 MiB; instance corrupt |

The ranges cover Chromium, Firefox and WebKit and both builds (Node is within them). QuickJS's own memory report says `malloc_usable_size unavailable` in both builds: without it QuickJS cannot count the bytes behind each allocation, so `setMemoryLimit` refuses single allocations larger than the limit but lets many small ones far past it.

After the "arrays" bomb, the same runtime and the same instance run scripts again. After the `Map` bomb they do not: with Memory maximum, a new runtime in the same instance failed in Node and all three browsers, and in Node a new context in the old runtime traps with `RuntimeError: memory access out of bounds`. In an earlier run of the spike, creating a context in that runtime crashed the whole Chromium page (`Target crashed`); the final run no longer touches it. This is the interpreter memory-safety risk ADR 0010 decision 4 anticipates, triggered by nothing more than running out of memory.

"QuickJS error" is a catchable error inside the script (`InternalError: stack overflow`, QuickJS-ng `RangeError: Maximum call stack size exceeded`). QuickJS's limit counts its C stack in linear memory (about 5 MiB, from the initial stack pointer in the `.wasm`); the browser's limit counts the native frames the wasm code uses, which differ per engine, so the safe value is set by the smallest engine stack: Chromium's worker.

## The Asyncify exception to context isolation

The README (0.32.0, section "Interfacing with the interpreter") says each context's actions "won't leak into other contexts or runtimes (with one exception, see Asyncify)". Its Asyncify section explains the exception: "we can suspend an _entire WebAssembly module_ (which could contain multiple runtimes and contexts)", and "_An asyncified WebAssembly module can only suspend to wait for a single asynchronous call at a time_. You may call back into a suspended WebAssembly module eg. to create a QuickJS value to return a result, but the system will crash if this call tries to suspend again." So the exception covers **suspension**: every runtime and context in one asyncified module shares a single suspended stack. It says nothing about JavaScript values leaking, and the isolation claim never covered linear memory (runtimes of one instance share it, as ADR 0010 already notes).

Measured, identically in Node and the three browsers:

| Case                                                                  | Outcome                                                       |
| --------------------------------------------------------------------- | ------------------------------------------------------------- |
| two contexts in two runtimes of one module, each awaiting a host call | `QuickJSAsyncifyError: Already suspended`, thrown to the host |
| the same with each context in its own module instance                 | both correct (20 and 200)                                     |
| an asyncified host function that re-enters and suspends again         | `QuickJSAsyncifyError: Already suspended`                     |

Separately, in 0.32.0, disposing an asyncified runtime that ever held a host function throws `QuickJSRuntime(rt = ...) not found when trying to free HostRef` (plain async runtimes, and sync runtimes with host functions, dispose fine).

## Nondeterminism in the build

Read with wabt 1.0.37 (`wasm2wat` with every feature enabled) on all four `.wasm` files: **no SIMD instruction** (no `v128`, so no relaxed SIMD), **no atomics**, and the memory is imported as `(memory 256 32768)`, **not shared**. So nothing in WebAssembly's list of nondeterminism applies except NaN bit patterns and resource exhaustion. The glue does reach the host clock: its imports call `Date.now()` and `performance.now()`, and the timezone functions behind `Date`. With the `Date` intrinsic removed (the spike's script global has no `Date`) and `Math.random` replaced in a prelude, no script-visible value depended on them in this spike. The global object still has `eval`, `Function` and a `SharedArrayBuffer` constructor (QuickJS's own, with no threads behind it).

TypeScript that is more than annotations (`scripts/erasure.ts`):

| Syntax                                                                 | ts-blank-space                     | sucrase                                                  |
| ---------------------------------------------------------------------- | ---------------------------------- | -------------------------------------------------------- |
| `enum`, `const enum`                                                   | reports unsupported, left in place | compiled to an object                                    |
| `namespace`                                                            | reports unsupported, left in place | **silently removed** (later uses throw `ReferenceError`) |
| parameter property                                                     | reports unsupported, modifier left | compiled to an assignment                                |
| `import x = require()`                                                 | reports unsupported, left in place | **silently removed**                                     |
| `<number>x` assertion                                                  | reports unsupported, left in place | erased                                                   |
| decorators                                                             | passed through                     | passed through                                           |
| `satisfies`, `const` type parameters, `<T,>` arrows, `accessor`, `x!:` | erased                             | erased                                                   |

**Choice: sucrase.** It is a nineteenth of the size, as fast, keeps positions for erasable code, and handles `enum`, which users write. ts-blank-space is the stricter tool but carries the TypeScript compiler, 3.7 times the size of QuickJS itself. T7.2b rejects `namespace`, `module` blocks and `import ... = require()` before erasing (a token check over the source), so nothing disappears silently, and states that constructs which sucrase compiles (`enum`, parameter properties) move columns on their own lines.

## Recommendations

### 1. Kernel access path: the synchronous kernel session

The script engine is the **sync release build of Bellard's QuickJS** (`@jitl/quickjs-wasmfile-release-sync` 0.32.0, pinned), and host functions call the regen worker's synchronous `Kernel` directly. Reasons, all measured:

- it is never slower: equal for heavy operations, 42 to 121 µs cheaper per kernel call in the browsers, and 5 to 23 times cheaper per plain host call;
- 199 KB brotli instead of 285 KB, and a first instance in 1 to 4 ms instead of 1.4 to 12.6 ms;
- no shared-suspension rule (two documents or a re-entrant call cannot fail with "Already suspended"), and no dispose bug;
- QuickJS-ng gives the same bits but is 15 to 30 % slower and 13 KB larger; nothing in the spike needed its extras.

What it costs: a script run holds the worker for its whole duration, so ADR 0007's cancellation by generation cannot stop a script between two kernel calls; only the time limit can. T7.2c needs a session API on `KernelService` that runs a synchronous function in the service's exclusive slot (as `run` does for a batch) with ownership of the shapes it makes, instead of reaching for `service.kernel` from outside a batch as the spike did.

### 2. Starting limits for T7.2b

| Limit               | Starting value                                                                                                                      | Why                                                                                                                                                                                                                                                           |
| ------------------- | ----------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Time                | 2 s per run, checked by the interrupt handler **and** at the start of every host call                                               | Script loops stop within 2 ms (5 ms WebKit); 24 booleans take 70 to 90 ms, so 2 s allows about 500. Builtin loops overshoot by seconds (below), so the handler is not a hard bound.                                                                           |

### 3. Determinism rules confirmed

The same `.wasm` gives the same bits in every browser, so ADR 0010 decision 5 stands as written. The binding must canonicalise NaN both ways (QuickJS produced `7ff8...` here, but NaN signs from wasm float operations are not specified and may differ on other CPUs). The host engines are not deterministic even against themselves (Node 26 against Chromium 153: 632 values), which rules out running scripts on the host engine (the SES and plain-worker alternatives).

## Implications for ADR 0010 and T7.2b

For T7.0d's amendment of ADR 0010:

1. **Decision 1** holds; name the build: the sync release variant of Bellard's QuickJS, `@jitl/quickjs-wasmfile-release-sync` 0.32.0 with `quickjs-emscripten-core` 0.32.0, both pinned exactly; 199,016 bytes brotli.
2. **Decision 2**: replace the open question with the answer: a synchronous kernel session (recommendation 1). The asyncified build is not used, so its suspension exception and dispose bug do not apply; record what the exception covers (above) for anyone revisiting it.
3. **Decision 4, time**: the 2 s budget stays, but say that the interrupt handler bounds script code, not builtins, and that terminating the regen worker is the hard bound. Host functions check the deadline too.
4. **Decision 4, heap**: the heap limit is enforced by the instance's `WebAssembly.Memory` maximum, not by `setMemoryLimit` alone (which does not count bytes in this build). After an out-of-memory the instance is discarded, not just the runtime: an out-of-memory can corrupt the instance, which is decision 4's per-document instance paying off.
5. **Decision 4, stack**: 128 KiB, because the browser's stack is smaller than QuickJS's (Chromium's worker); a host stack overflow escaping the interpreter discards the instance.
6. **Decision 4, instances**: an instance costs 0.5 to 2 ms and 16 MiB; add the idle-time drop of large instances, since their memory never comes back.
7. **Decision 5**: unchanged; the spike's determinism script is the seed of the cross-browser test T7.2e runs.
8. **Decision 7**: sucrase 3.35.1 (MIT), with `namespace`, `module` and `import = require` rejected before erasure.
9. **Consequences**: add the session API T7.2c needs on `KernelService`, and that a running script cannot be cancelled by generation.

For T7.2b specifically: the limits table above; `Date` removed through the context's intrinsics (`Date: false`) rather than deleted afterwards; `SharedArrayBuffer`, and if wanted `eval` and `Function`, removed from the global; the error mapper treats `null` and non-Error throws as limit errors where the context says so; and the tests in its acceptance (infinite loop, deep recursion, allocation bomb) should include the three cases this spike found: a loop of `sort()`, the `Map` bomb, and a stack limit above Chromium's.
