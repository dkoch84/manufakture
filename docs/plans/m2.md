# M2 plan: multi-body parts, derived parts, assemblies, configurations, version history

Milestone 2 of the epic "Can't CAD Can We?". M1 made one part with one body: a printable bracket, modelled, exported, saved and changed ([M1 acceptance](../m1-acceptance.md)). M2 makes that part hold several bodies, lets documents reuse each other's parts at pinned versions, places parts in assemblies with mates, turns parameter tables into variants, and keeps named versions of a document.

This page breaks M2 into agent-sized tasks, each roughly one pull request, grounded in the code as it stands after M1. The epic's five items are split as follows:

| Epic item                                         | Tasks                    |
| ------------------------------------------------- | ------------------------ |
| T2.1 Multi-body part studio; visibility, colours  | T2.1a to T2.1e           |
| T2.2 Derived parts, pinned to a version           | T2.2a to T2.2c           |
| T2.3 Assemblies: instances, mates, interference   | T2.3a to T2.3f, ADR 0008 |
| T2.4 Configurations: parameter tables to variants | T2.4a to T2.4c           |
| T2.5 Version history: named versions, branches    | T2.5a to T2.5c           |
| Acceptance                                        | T2.6                     |

The mate solver decision is [ADR 0008](../adr/0008-assembly-mate-solver.md): our own joint-coordinate solver in TypeScript, in a new `packages/assembly`.

## Where M1 leaves us

What each M2 item has to change, from the code:

- **One body per part, as a compound.** `packages/kernel/src/features.ts` `combine()` puts a `new` solid next to the body in one compound, and `noOverlap()` fails an overlapping `new` with `invalid` ("a new solid must stay clear of it until parts can hold several bodies"). Every feature takes and returns one body id (kernel README, "Deviations": "Multi-body parts are one compound"). Later booleans act on the whole compound.
- **Regen chains one body.** `packages/regen/src/graph.ts` gives every kernel feature a "body edge" to the last active kernel feature; `PartResult` (`src/types.ts`) has one `shape`, `bodyKey`, `mesh` and `topology` per part (regen README, "Meshes per part, not per body id").
- **Material is per part.** `PartSchema.material` in `packages/core/src/schema.ts` ("A part has one body until multi-body parts (M2), so this is the body's material"); `DocumentChange.materialChanged` in `src/changes.ts`.
- **The app works on the first part.** `DEFAULT_PART_ID` is the default in `apps/web/src/features/FeatureDialog.tsx`, `tree/FeatureTree.tsx`, `io/actions.ts`, `sketcher/commit.ts` and `App.tsx`; `measure/MeasurePanel.tsx` reads `document.parts[0]`. The viewport already draws a list of bodies (`model/model.ts` flattens `parts[].body`; `viewport/bodies.ts` `BodyInput.id`), and the selection already carries a `bodyId` (`state/selection.ts` `GeometryRef`).
- **Part ids have no counter.** Features, sketch entities and references have per-part counters (`Part.nextIds`), but the document has none, so a second part studio could not get an id that is never reused (ADR 0004 decision 4).
- **Persistence keeps only two snapshots.** `apps/web/src/persistence/library.ts` deletes snapshots older than the previous commit (README, "Crash safety", step 6) but keeps every log segment and blob. The log holds the applied commands (`{ cause, label, command, at }`), so a revision can be rebuilt by replaying commands forward from a retained snapshot, never backward.
- **Imported files are the model for embedded sources.** An `import` feature keeps its bytes inline with `size` and `sha256`; persistence moves them to content-addressed blobs (`blobs.ts`); regen checks the hash once per source object (`packages/regen/src/imports.ts`). Derived parts reuse all three.
- **Naming is per part and starts with a feature id.** Face names are `<feature id>:...` (`packages/kernel/src/naming.ts`), pattern and mirror copies are prefixed `<id>:i<k>/` and `<id>:image/` with prefixed lineage, and vertices are named by their faces (`vertexName`). So names are unique across all bodies of a part without a body qualifier. Core reads dependencies out of names: `featureIdsInName` (`packages/core/src/features.ts`) collects every `<kind>#<n>:` anywhere in a name, through merges and corners, and `featureDependencies` feeds validation, the regen graph, delete blocking, reorder, the tree and the feature forms.
- **Exchange writes several bodies already.** `exportStep` takes a list of named bodies; `write3mf` writes one object per body but no build transforms or components (io README, "3MF"); `parse3mf` reads transforms.

## Decisions that cut across tasks

1. **A body is named after the feature that made it.** A body's id is the id of its creating feature (`extrude#3`, `import#1`); pattern and mirror copies made as new bodies take their instance prefix (`pattern#2:i3`, `mirror#1:image`); derived bodies are `derived#1:from/<source body id>`. Feature ids are permanent and never reused, so body ids are too, and no new counter is needed.
2. **Merging and splitting.** An `add` whose tool touches several bodies in its scope fuses them into one body, which keeps the id of the body whose creating feature comes first in the part; the others end there and regen reports them as consumed. An `add` whose tool touches no body makes a new body named after the `add` feature, with a `detached` warning (the M1 compound kept such a solid too); it is a body like any other and can have props and appear in scopes. A `cut` that leaves a body in several disjoint pieces keeps one body with several solids (regen reports the count); a feature that splits a body into separate bodies is later work.
3. **Scope.** Features with an operation (extrude, revolve, import, hole, pattern and mirror of bodies, derived) get an optional `scope: string[]` of body ids. Absent means every body at that point, which is exactly what the M1 compound did, so old documents regenerate unchanged. Fillet, chamfer and shell take no scope: they act on the bodies that own their references.
4. **Only user settings are stored per body.** `Part.bodies` holds `{ id, name?, color?, material? }` for bodies the user has named, coloured or given a material. `Part.material` stays and becomes the default for bodies without their own. Everything else about a body (that it exists, its solids, its volume) is derived by regen.
5. **Visibility is view state**, not document state: hiding a body is not an undo step and does not change the file, like the camera. It is kept per document next to the app's view settings (`apps/web/src/state/viewSettings.ts`).
6. **No naming scheme bump, but core's name parsing learns `:from/`.** Body ids are not part of face names; derived names add a prefix form (`<id>:from/`) that no stored reference had before; assembly references pair an instance id with an ordinary name. None changes what an existing stored reference means, so `NAMING_SCHEME` stays 1. What does change is how core reads a name: everything after `derived#1:from/` is a name in the source document, and its feature ids are not features of this part. Today's `featureIdsInName` would read `derived#1:from/extrude#1:cap:end` as depending on `derived#1` and on a local `extrude#1`, so validation would refuse the document when the part has no `extrude#1` (or one after the fillet), and false edges would appear in the regen graph, delete blocking, reorder, the tree and the forms. T2.2a changes the parser (scan each merge and corner member up to its first `<id>:from/`, then skip the source name); T2.2b emits names in the form that parser reads. If review finds a case that changes what a stored reference means, that task bumps `NAMING_SCHEME` with a migration (ADR 0004 decision 3).
7. **One format bump per schema task, landed one at a time.** T2.1a, T2.4a, T2.2a and T2.3b each change the document shape and each takes the next free `FORMAT_VERSION` when it lands, with a migration and a fixture (core README, "To change the file shape"). They all edit `packages/core/src/schema.ts`, `migrations.ts` and `format.test.ts`, so they must not be in flight at the same time; the numbers below (v4 to v7) assume the order T2.1a, T2.4a, T2.2a, T2.3b. No other M2 task changes the shape: the `configuration` field T2.4c reads is added by T2.2a (derived sources) and T2.3b (instance sources).
8. **Versions are storage, not document shape.** Named versions, retained snapshots and branches live in the persistence layer (`apps/web/src/persistence`); the document format does not change for T2.5. A derived part pins a version by `documentId` plus `versionId` and carries the pinned document itself, so a document stays self-contained when exported.

## Tasks

Every task follows the repository's rules: tests with the code, `make lint`, `make typecheck` and `make test` green, the e2e specs it names passing (`pnpm --filter @manufakture/web e2e <spec>`), kernel goldens in the `kernel-goldens` Vitest project where the kernel is involved, the package README updated where its API changes, and user docs in `docs/user/` for anything a user sees.

### T2.1a: Core: bodies in the part (format v4)

**Goal.** The document can say which bodies a feature acts on and what each body is called, coloured and made of, and can hold several part studios with ids that are never reused.

**Scope.**

- `packages/core/src/schema.ts`: `BodyPropsSchema` `{ id, name?, color?, material? }` (colour as `#rrggbb`; material a `MaterialId`), `Part.bodies: BodyProps[]`; optional `scope: string[]` on extrude, revolve, import and hole, and on pattern and mirror, where `body: true` stays and `scope` narrows which bodies it copies; a document-level `nextIds` record (key `part`, later `assembly`) so new part ids are allocated like feature ids. `FORMAT_VERSION` 4.
- `src/migrations.ts`: `migrateV3ToV4` adds `bodies: []` to every part and `nextIds: { part: <highest part number + 1> }` to the document; no feature changes, since an absent `scope` means every body, which is what the v3 compound did. Fixture `src/fixtures/v3-bracket.json` migrates to exactly `v4-bracket.json`, plus a v3 fixture with two `new` solids (the compound case).
- `src/validate.ts`: a `BodyProps.id` and every `scope` entry must name a body a feature of the part can create: its leading feature id exists and is a kind that can make a body (extrude, revolve, import, and pattern or mirror of bodies; derived from T2.2a) with an operation of `new` or `add`. `add` is allowed because an `add` that touches no body makes a detached body under its own id (decision 2, T2.1b); whether a given `add` did is known only after regen, so props on an `add` that merged into another body are reported by regen as `reference-lost`, like a missing instance suffix (`:i3`), which is not checked here either. Duplicate ids refused.
- `src/features.ts`: a `bodyCreator(bodyId)` helper that returns the leading feature id of a body id, and `featureDependencies` makes `scope` and `BodyProps` entries depend on it. Body ids do not go through `featureIdsInName`: a bare `extrude#3` has no trailing `:` and would give nothing, and a derived body id (`derived#1:from/pattern#2:i3`, T2.2a) would give ids from the source document.
- `src/commands.ts`: `setBodyProps` `{ partId, bodyId, props }` (inverse: the old props, or removal); `deleteFeature` refuses (`dependency`, with `blockers`) while a `BodyProps` entry or a `scope` names a body the feature creates, so the app deletes both in one `batch`.
- `src/changes.ts`: `DocumentChange` gains `bodyPropsChanged` (names, colours, materials: no geometry), next to `materialChanged`.
- README: the document shape, body ids (decision 1), merge and split rules (decision 2), `scope` (decision 3), what is stored (decision 4).

**Acceptance.**

- Unit tests: v3 to v4 migration of both fixtures; schema accepts and refuses props, colours and scopes (props on an `add` accepted, on a fillet refused); `bodyCreator` of plain, instance and derived-looking ids; `setBodyProps` apply and undo; delete blocked by props and by a scope; `diffDocuments` reports a props change without `firstAffectedIndex`; `nextIds.part` only increases.
- `format.test.ts` has a fixture for every older version (the existing guard).

**Dependencies.** M1 (`packages/core`). None within M2.

**Footprint.** `packages/core/src/{schema,migrations,validate,features,commands,changes}.ts`, `src/fixtures/v3-*.json`, `v4-*.json`, tests, `packages/core/README.md`.

**Risks.** Validating body ids without regen is necessarily partial; the rest is a regen error (`reference-lost` on `scope`). Keeping `Part.material` as the default (rather than moving it into `bodies`) avoids a lossy migration but leaves two places a material can come from; the README must state the precedence.

### T2.1b: Kernel: features on a set of bodies

**Goal.** `applyFeature` and the `feature` op work on an ordered set of named bodies instead of one compound, and `new` solids may overlap.

**Scope.**

- `packages/kernel/src/features.ts`: `applyFeature(kernel, bodies, input)` where `bodies` is `{ id, shape }[]` (each a named body) and `FeatureInput` gains `scope?: string[]` and the body id a `new` creates. `combine()` becomes per-body: `new` adds a body (and `noOverlap()` goes); `add` fuses the tool with every scoped body it touches, merging them under the first id (decision 2), and a tool that touches none becomes a new body under the `add` feature's id with a `detached` warning (decision 2; T2.1a accepts props and scopes naming it); `subtract` and `intersect` apply to each scoped body the tool reaches. Holes cut every scoped body they reach. Fillet, chamfer and shell resolve their references against the union of names and apply to each body that owns some, failing with `invalid` only if one reference spans two bodies. Body patterns and mirrors copy the scoped bodies; `new` copies become bodies `pattern#k:i<n>` and `mirror#k:image`.
- `FeatureOutcome` becomes per body: the body set after the feature (id, shape, names), `created`, `changed`, `consumed` (merged away) and the solid count of each changed body.
- `src/service.ts`, `src/types.ts`: the `feature` op takes and returns body sets; `resolve`, `pick` and `measure` take a body shape as today.
- `src/naming.ts`: nothing changes in the rules; tests prove names stay unique across overlapping bodies and across merges.
- README: "Part features", the deviation on compounds removed, the new outcome shape.

**Acceptance.**

- `features.test.ts` goldens: two overlapping `new` boxes are two bodies whose volumes are each exact (48,000 mm3 case from the README becomes 24,000 plus 24,000); an `add` touching both merges them to the fused volume under the first id; a cut through two bodies cuts both; a cut splitting one body reports two solids in one body; a fillet on an edge of body 2 leaves body 1's shape id unchanged; a `new` body pattern gives n bodies.
- `survival.test.ts`: the T0.5 scenarios still resolve `exact` with a second body present.
- `leaks.test.ts`: no embind object left behind with body sets.

**Dependencies.** M1 (`packages/kernel`). None within M2: the kernel has no runtime dependency on core, so it can be built against its own input types while T2.1a is in flight.

**Footprint.** `packages/kernel/src/{features,types,service,worker-api}.ts`, `features.test.ts`, `survival.test.ts`, `feature-ops.test.ts`, `leaks.test.ts`, `packages/kernel/README.md`.

**Risks.** Fusing a tool with several bodies at once versus one at a time gives different histories; naming must stay deterministic either way (sort scoped bodies by creator order). OCCT booleans on many bodies cost more; one boolean per touched body with a bounding-box prefilter keeps untouched bodies out of it.

### T2.1c: Regen: a body set per part, per-body results

**Goal.** Regen carries a set of bodies through a part, rebuilds only what an edit touches per body, and reports a mesh per body.

**Scope.**

- `packages/regen/src/graph.ts`: the body edge becomes per body. A feature depends on the last feature that changed each body in its scope (or that owns its references); with no scope it depends on the last feature that changed any body, which is today's chain. A regen tracks which body owns which face name to route fillets.
- `src/translate.ts`: `scope` and the new body id into `FeatureInput`; `reference-lost` on `scope` for a body that does not exist at that point.
- `src/cache.ts`, `src/engine.ts`: the cache key of a kernel feature holds the keys of the bodies it reads, not the whole set, so an edit to body 2 is a cache hit for features on body 1 only. Entries store the per-body outcome.
- `src/types.ts`: `PartResult.bodies: BodyResult[]` (`bodyId`, `shape`, `bodyKey`, `meshChanged`, `mesh`, `topology`, `solids`, the creating feature) replacing the part-level `shape`, `bodyKey`, `mesh`, `topology` and `meshChanged`; `consumed` bodies listed; one name table for the reply as now. `regenTransferables` covers every body's buffers.
- README: "Meshes per part" deviation removed; body graph, cache and result documented.

**Acceptance.**

- `graph.test.ts`: per-body dirty sets (an edit to a sketch of body 2 does not dirty a fillet on body 1 when scopes are explicit; it does when scopes are absent).
- `engine.test.ts`: ops sent per edit with two bodies; consumed bodies; a mesh sent only for changed bodies.
- `integration.test.ts`: real kernel, two-body part, edit one body's variable, exactly the features of that body sent; the M1 bracket (no scopes) regenerates to the same volume and names as before.
- `worker-api.test.ts`: per-body meshes transferred.

**Dependencies.** T2.1a, T2.1b.

**Footprint.** `packages/regen/src/{graph,translate,cache,engine,types,worker-api,transfer}.ts` and their tests, `packages/regen/README.md`.

**Risks.** Finer dirty sets depend on scopes that users rarely set; the default (every body) keeps M1's behaviour and its cost. Face-name ownership routing must follow merges, or a fillet after a merge would look for a body that is gone.

- The M1 specs (`m1-bracket`, `m1-views`) still pass unchanged.

**Dependencies.** T2.1c.

**Footprint.** `apps/web/src/{model,viewport,tree,features,measure,io,state}/`, `App.tsx`, `apps/web/e2e/bodies.spec.ts`, `docs/user/`.

### T2.5a: Persistence: named versions, retained snapshots, revision replay

**Goal.** Any named version, and any revision after the first retained snapshot, can be read back exactly; versions have stable ids other documents can pin.

**Scope.**

- `apps/web/src/persistence/library.ts`: `createVersion(id, { name, description })` commits the current state (saving first if autosave is behind) and records `{ id: <uuid>, name, description, revision, snapshotSha256, createdAt }`; `listVersions(id)`; `renameVersion`; no delete in M2 (a pinned copy lives in the documents that derive from it anyway).
- Layout: `versions-<n>.json` written before the head, and `head.json` gains `versions: n`, so the version list follows the same pointer-commit rule as snapshots ("Crash safety"). Save step 6 keeps snapshots that a version names, and a checkpoint snapshot every `CHECKPOINT_EVERY` revisions (64 as a start), so any revision is at most 63 log segments from a snapshot.
- `readRevision(id, rev)`: the nearest retained snapshot at or below `rev`, then the log segments' commands replayed through core `applyCommand`; the result is checked against the stored SHA-256 wherever a snapshot of that revision exists. Documents saved before this task have history only from their oldest remaining snapshot; `historyStart(id)` says so.

- e2e `persistence.spec.ts` gains: create a version, edit, reload, read the version back.

**Dependencies.** M1 (T1.12 persistence, core `applyCommand`). No core change.

**Footprint.** `apps/web/src/persistence/{library,mfk,autosave}.ts` and tests, `apps/web/src/persistence/README.md`.

**Risks.** Replay depends on `applyCommand` being deterministic across app versions: a later release that changes a command's semantics would replay old logs differently. ### T2.2a: Core: the derived feature (format v6)

**Goal.** A part can contain bodies of a part from another document (or another version of this one), pinned to a version and carried inside the document.

**Scope.**

- `schema.ts`: a `derived` feature kind: `source { documentId, documentName, versionId, versionName, partId, sha256, size, data }` where `data` is the canonical JSON text of the source document at that version with its imports inline (so the pin is self-contained, like an import's bytes); `bodies?: string[]` (source body ids; absent: all); `placement` (translation and rotation as expressions); `operation` (`new`, `add`, `cut`, `intersect`) and `scope` as for imports. `MAX_DERIVED_BYTES`. `FORMAT_VERSION` 6.
- Validation: the envelope only (hash format, `size` matches the UTF-8 length of `data`), not the nested document; regen checks the rest, as for imports.
- `configuration?: string` on the source: a row id of the source document's configuration table (T2.4a). Stored and carried now so T2.4c needs no format bump; nothing writes it before T2.4c, and regen checks it against the source there, not at load.
- Body ids of derived bodies (decision 1) accepted in `BodyProps` and `scope`; `bodyCreator` (T2.1a) gives `derived#1` for `derived#1:from/<anything>`.
- `src/features.ts` name parsing (decision 6): `featureIdsInName` splits a name into members at `+` inside a merge `(A+B)` and at `&` in a corner `A&B&C`, keeping parenthesised groups whole, and scans each member only up to its first `<id>:from/`: that id counts, and the rest of the member (a plain name, or one parenthesised group) is a source name and is skipped. So `derived#1:from/extrude#1:cap:end` gives `derived#1` only, `(derived#1:from/extrude#1:cap:end+extrude#2:side:e5)` gives `derived#1` and `extrude#2`, `derived#1:from/(extrude#1:cap:end+extrude#2:side:e5)` gives `derived#1`, and `pattern#7:i2/derived#1:from/extrude#3:side:e1` gives `pattern#7` and `derived#1`. A source corner has no brackets, so T2.2b prefixes each of its members (below); this task fixes that form with tests so the two sides agree. `featureDependencies` and everything built on it (validate, regen `graph.ts`, `deleteFeature` blocking, `reorderFeature`, the app's `tree.ts` and `forms.ts`) then need no change of their own.
- `apps/web/src/persistence/blobs.ts`: `externalize` and `hydrate` handle `derived` sources like import sources, so storage and `.mfk` keep one blob per pinned version.
- README: "Derived parts", why the pinned document is embedded (the same reasoning as "Imported geometry": input, not cache; undo, save and export just work), and why cycles are impossible (a pin is an immutable snapshot, so a document can derive from an older version of itself; nesting depth is capped at `MAX_DERIVED_DEPTH`).

**Acceptance.**

- Unit tests: schema (with and without `configuration`), envelope checks, migration fixture, blob round trip of a derived source (persistence tests).
- `features.test.ts`: the `featureIdsInName` cases above, plus a corner whose members mix a derived face and local faces (`fillet#3:corner:derived#1:from/extrude#1:cap:end&extrude#1:side:e1` gives `fillet#3`, `derived#1`, `extrude#1`), a prefixed source corner (every member prefixed: `derived#1` only), and nested derivation (`derived#1:from/derived#2:from/extrude#1:cap:end` gives `derived#1`). Every existing case keeps its result.
- A fillet on a derived face (`derived#1:from/extrude#1:cap:end`) in a part with no local `extrude#1`: `validateDocument` accepts it, `featureDependencies` is `derived#1` only. The same fillet in a part whose local `extrude#1` comes after it: valid, deleting and reordering that `extrude#1` is not blocked by the fillet, and the regen graph has no edge from it to the fillet.

**Dependencies.** T2.1a (bodies), T2.5a (version ids to pin), T2.4a (schema order; the row ids `configuration` names).

**Footprint.** `packages/core/src/{schema,migrations,validate,features}.ts`, `features.test.ts`, `commands.test.ts`, fixtures, `apps/web/src/persistence/blobs.ts`, a regen `graph.test.ts` case, tests, READMEs.

**Risks.** Documents grow by a copy of every pinned source; a document deriving several versions of a big source holds each. Blobs are shared by hash, so storage holds each version once per document.

### T2.2b: Regen and kernel: regenerate a pinned source, derive bodies

**Goal.** Regen builds a derived feature from its pinned source, with names that let references into derived bodies survive a version update.

**Scope.**

- `packages/regen/src/derived.ts`: check `sha256` once per source object (as `imports.ts` does), `deserialize` the source (migrating older formats in memory; a newer format than the app is an error on the feature), pick the part, regenerate it in the same worker with its own variables, under a cache namespace keyed by `sha256` and part id, so every derived feature of one source shares the work.
- Kernel `derive` feature input (`packages/kernel/src/features.ts`): copies the chosen bodies with the placement transform and prefixes every face name and its lineage with `<feature id>:from/` (the same machinery as pattern instances in `naming.ts`), in the form T2.2a's parser reads: a merged source name `(A+B)` is one group and is prefixed once, and in a source corner (`fillet#3:corner:A&B&C`, no brackets) each `&` member is prefixed too, so no member of a derived name can be read as a local face; then combines them per `operation` and `scope` (T2.1b).
- Source body properties (name, colour, material) carry over unless the deriving part sets its own.
- Errors and warnings: `source` (hash mismatch, unreadable, newer format, missing part), `reference-lost` on `bodies` for a body that no longer exists in that version, and a `derived-source` warning when source features failed.
- README sections in regen and kernel.

**Acceptance.**

- Kernel goldens: a derived box at a placement has the exact volume and prefixed names; `cut` with a derived body.
- `survival.test.ts`-style test: derive the M1 bracket, fillet an edge of the derived body, update the pin to a version where `#thickness` changed: the fillet resolves `exact` to the same named edge.
- `engine.test.ts`: two derived features of one source regenerate it once; an unrelated edit is a cache hit.

**Dependencies.** T2.2a, T2.1c.

**Footprint.** `packages/regen/src/{derived,engine,translate,graph,cache}.ts`, `packages/kernel/src/{features,naming,types}.ts`, tests, READMEs.

**Risks.** A nested regen in the same kernel instance adds to the heap and may trigger a recycle mid-regen; the engine's stale-shape restart already covers it, but tests should force one. Deep nesting multiplies cost; `MAX_DERIVED_DEPTH` bounds it.

### T2.3a: `packages/assembly`: the mate solver

**Goal.** The solver of [ADR 0008](../adr/0008-assembly-mate-solver.md), usable and measured before the assembly model is fixed.

**Scope.**

- New package `packages/assembly` (GPL-3.0-or-later, pure TypeScript, no runtime dependency): rigid transforms (unit quaternion plus translation; compose, invert, log and exp), mate kinds fastened, revolute, slider and planar as relative transforms of their free coordinates (cylindrical and ball if cheap), the mate graph (fixed instances as roots, a spanning tree, loops), forward kinematics on the tree, Levenberg-Marquardt on loop closures seeded from the last poses, a small one-sided Jacobi SVD, DOF and redundancy from rank, conflicts per loop blaming the newest mate, and drags (a tree drag sets the free coordinates nearest the target; a loop drag adds a soft target like the sketcher's FreeCAD-style drag). Limits clamp drags.
- API: `solve(input)` and `drag(input, instanceId, target)` with plain-data input and a report shaped as ADR 0008 decision 2 says; messages in English.
- A benchmark test: trees of 10, 100 and 500 instances, a four-bar, a slider-crank, 20 loops of 4, and drags on each; numbers written to the test output and to a JSON file the CI job can print (Vitest hides console output of passing tests: run it with `--silent=false --reporter=verbose`).
- README.

**Acceptance.**

- Hand-computed poses for each mate kind; a four-bar has DOF 1 and follows a crank drag; two fastened mates between one pair are redundant; a loop that cannot close is a conflict naming its mates; unconnected instances keep their poses; near-singular cases (a revolute axis parallel to a slider) do not blow up.
- Budgets (targets, to be confirmed by the benchmark): a 200-instance tree solves in under 2 ms; a drag step in a 50-instance assembly with a few loops in under 8 ms.

**Dependencies.** None. Runs in wave 1.

**Footprint.** `packages/assembly/` (new), `pnpm-workspace.yaml` if needed, `vitest.config.ts` project list, `tsconfig.json` references.

**Risks.** Numerical code is easy to get subtly wrong; tests against hand-computed poses and randomised round trips (pose to coordinates and back) are the guard. If the benchmark misses its budgets, ADR 0008 decision 6 applies before T2.3c builds on it.

## Risks across M2

- **Four format bumps in one milestone.** Each is cheap on its own, but they serialise four tasks on one file. If the schedule needs more parallelism, fold T2.4a's and T2.2a's shape changes into one bump landed by whichever comes first, with the other extending the same version before any release.
- **Regen cost.** Several bodies, several part studios, nested derived regens and assemblies all go through one kernel worker and one OCCT instance. The per-feature cache and the heap-threshold recycle carry M1's design further; T2.6's budgets watch it.
- **Command-log replay across app versions** (T2.5a) assumes commands keep their meaning; any change to a command's semantics must keep old logs replaying the same, or version history silently differs from what was saved. The SHA check against retained snapshots catches it where one exists.
- **The mate solver is ours** (ADR 0008). The benchmark in T2.3a decides early whether the joint-coordinate design holds; if not, the fallback is OndselSolver in our own `.wasm`, which is a larger task than T2.3a.
- **Not in M2**: merging branches, per-field configurations, splitting a body into several bodies, mate couplings (gears, screws), limits enforced inside loops, a persistent regen cache, and a derived part that follows another part studio of the same document live (assemblies cover the same-document case).
