## Where M1 and M2 leave us

From the code and the M2 plan:

- **Commands are the unit of change, and they are logged.** `applyCommand` in `packages/core/src/commands.ts` validates a command against `CommandSchema`, applies it without mutation, checks the whole document and returns the inverse. `DocumentStore` reports every `execute`, `undo` and `redo`; `apps/web/src/persistence/autosave.ts` records them and `library.ts` stores them as log segments (`{ format: 'manufakture-log', revision, base, entries }`) of `LogEntry { cause, label, command, at }`, chained by `base`, with imported files as content-addressed blobs. Core is pure TypeScript, so it runs on a server unchanged.
- **Ids are chosen by the client.** `previewIds(part.nextIds, kind)` gives the next ids and the command carries them; core refuses `id-reused`. Two devices editing offline will pick the same ids. Counters live in several scopes: `Part.nextIds` today (one counter per feature kind, and `e`, `k`, `r` for sketch entities, constraints and references, `packages/core/src/ids.ts`), then a document `nextIds` (`part`, `assembly`, `cp`, `cfg`) and one per assembly (`inst`, `mate`, `mc`) from M2, `cam.nextIds` from M5, and `script` from T7.2a. Ids also hide inside face names (`extrude#1:side:e2`, `fillet#3:round:r1`), which `featureIdsInName` (`packages/core/src/features.ts`) only scans for `kind#n:` and cannot rewrite. ADR 0009 decision 5 remaps all of them on rebase.
- **Conflicts are whole-document today.** A stale save gets `RevisionConflict`; the user keeps one version or saves a copy (persistence README, "Several tabs"). M2 adds named versions and checkpoints (T2.5a, #987), a history viewer and `replaceDocument` (T2.5b, #988) and branches (T2.5c, #989), and defers merging to M7.
- **Regen is local and cached by input hash** (ADR 0004 decision 8). Nothing geometric needs to be on a server; a share viewer needs meshes, which the app can produce.
- **The extension point exists but builds nothing.** Core's `extension` feature kind validates dependencies, references and expressions; regen reports "Regen does not build ... features yet" (`packages/regen/src/engine.ts`). Scripted features get their own kind (ADR 0010 decision 8).
- **Hosting is headers-only so far.** `apps/web/vite.config.ts` sends COOP and COEP in dev and preview; `apps/web/src/isolation.ts` logs whether the page is isolated. ADR 0002 decided the kernel is single-threaded and "does not depend on cross-origin isolation", and that production hosting serves the `.wasm` hashed, `immutable` and brotli-compressed, with a precaching service worker as a follow-up. There is no deployment yet; CI (`.github/workflows/ci.yml`) builds and tests only.
- **Serving the app distributes it.** ADR 0006's consequences: whoever hosts a build must offer its corresponding source, including the `.wasm` build recipes.

## Decisions that cut across tasks

1. **Everything stays local-first.** No feature of M7 is required to model, save, export or reopen a document. Sync is opt-in per document; the viewer and the PWA work without the server.
2. **The server never computes geometry.** It runs core (validation and ordering), stores logs, snapshots and blobs, and serves files. No OCCT, no regen, no scripts on the server (ADR 0009 decision 3, ADR 0010 alternatives).
3. **Core is now a wire protocol.** Command semantics must not change under old logs. From T7.1a on, CI replays golden command logs and compares canonical output, and a change that alters a golden is a breaking change needing a new command type, not an edit of the old one.
4. **Scripts are data in the document, run in QuickJS in the regen worker** with no capabilities (ADR 0010).
5. **Share first as static files.** A published model is a self-contained bundle of meshes and metadata that any static host, or the sync server, can serve. A share link is the viewer's URL plus the bundle's URL in the fragment, so the viewer's host never sees which model is opened.
6. **One format bump for scripting**, taken in turn after M2's v4 to v7 and anything M3 to M6 add (the M2 plan's rule: schema tasks are serialised). Sync, share and PWA change no document shape.
7. **Security review before exposure.** Anything reachable from outside the user's machine (the server beyond localhost, share links, scripts from other people's documents, the service worker's cache) is reviewed against the threat model of T7.6a and signed off by a human (T7.6b) before a public deployment or before scripted features are on by default.

**Goal.** The decisions an agent must not make: where M7 runs and under whose name.

**Scope.** Decide and record in `docs/decisions/` (a new product decision, not an ADR):

- whether a hosted sync service is operated at all, or the server is self-host only (ADR 0009 decision 12 recommends self-host, single-user first);

**Dependencies.** None. **Footprint.** `docs/decisions/0001-*.md`. **Risks.** Deferring it holds T7.1c's exposure, T7.3c's live deploy and T7.3d, but not the local work.

### T7.1a: Core: id remap, created ids, sync entries, golden logs

**Goal.** Everything sync needs from core, as pure functions.

**Scope.**

- `createdIds(doc, command)`: the ids a command allocates, per counter scope, from the same `allocate` logic `applyCommand` uses. The scopes are those of ADR 0009 decision 5: each part's `nextIds` (a counter per feature kind, and `e`, `k`, `r`), the document `nextIds` (`part`, `assembly`, `cp`, `cfg`, and `script` from T7.2a), each assembly's `nextIds` (`inst`, `mate`, `mc`) and `cam.nextIds` (`tool`, `setup`, a counter per operation kind, `r`), each as far as it has landed when this task does.
- A face-name parser and printer (`packages/core/src/names.ts`) for the grammar of `packages/kernel/src/naming.ts`: born names `<feature id>:<role>[:<tail>]` whose tail is a sub-id with split suffixes (`e2#a`, `e2#a#b`), a positional piece (`e2#1`) or a nested name; kernel pieces `X#k`; merges `(A+B)`; corners and edge-face lists `A&B&C`; instance prefixes `pattern#7:i2/` and `mirror#8:image/`; `import#9:face:4`; `?face` placeholders; M2's derived prefix `<id>:from/`, after which the source name is opaque. `featureIdsInName` is rebuilt on it with every existing case unchanged. Tests: `print(parse(name)) === name` for every name in the kernel and regen test goldens and for generated names of every form.
- `remapIds(commands, table)`: rewrite ids in a list of commands, with a table keyed by scope and old id. Command fields are walked structurally per schema, each through its own scope: feature ids, `dependsOn`, profile and hole sketches, pattern and mirror sources, sketch entity, constraint and reference ids, body ids in `scope` and body properties, part, assembly, instance, mate and connector ids and the fields that name them, configuration parameters and rows, CAM tools, setups and operations. Names go through the parser: the feature id and sub-id tail of a born name (`extrude#1:side:e7#a` to `extrude#1:side:e9#a`, keeping split and positional suffixes), each member of a merge or corner, the feature id of an instance prefix and the name after it, and of a derived prefix only `<id>`, never the source name. The same function rewrites the inverses on an undo stack, which are commands too. Property test: for random command lists, applying remapped commands to a document gives the same document as applying the originals and then renaming every id, in every scope, including inside names.
- `SyncEntrySchema` (zod): `{ clientId, clientSeq, prevSeq, baseRev, format, cause, label, command, at }` in storage form (ADR 0009 decision 2), and `PROTOCOL_VERSION`. `prevSeq` is optional and documented on the schema as the `clientSeq` of the entry the new one was built on, assigned with `clientSeq` when the entry is sent: the nearest entry before it in the client's queue that is neither refused nor doomed, else the client's latest accepted entry, else absent; never an entry the client knows was refused or doomed.
- Command migrations beside the document migrations: `migrateCommand(command, fromFormat)`, applied to an entry before it is applied, so log entries and persisted pending queues written before a format bump replay after it (ADR 0009 consequences). A format task that changes a shape a command carries adds its step here.
- Golden logs: `packages/core/src/fixtures/logs/*.json`, command logs with their format version and expected canonical documents; a test replays each through the command migrations and compares with `serialize`. The README's "To change the file shape" gains "and commands": a command whose meaning changes is a new command type, and a golden written under an old format stays in the suite.

**Acceptance.** Unit and property tests; name round trips for every naming form above; remap tests with one case per form: a sketch split, a region edge, a merge, a corner of three faces, a pattern and a mirror instance, a derived name whose source mentions the same id as a local feature (only the local one changes), the same feature id in two parts (only the remapped part changes), and CAM operation ids next to feature ids of the same shape; golden logs for every command type, including `batch`, `restoreFeature` and `replaceDocument`.

**Dependencies.** T7.0b; #988 (`replaceDocument`). **Footprint.** `packages/core/src/{sync,remap,names}.ts` and tests, `packages/core/src/{features,migrations}.ts`, `packages/core/src/fixtures/logs/`, core README. **Risks.** Names are the hard part of the remap. Every naming form and counter a later task adds (script operations in T7.2c, and any M3 to M6 form landing after this task) must be added to the parser, the remap and their tests in that same task; a missed one renames a local id and leaves a stale name, which core refuses.

### T7.1b: `packages/sync`: client engine and reference server

**Goal.** The sync algorithm of ADR 0009 as a package with no transport and no storage.

**Scope.** New pure TypeScript package `packages/sync`:

- `SyncClient`: confirmed document and revision, and a pending queue in two parts, in flight and unsent (ADR 0009 decision 4); `submit(entry)`, `receive(entries)`, `refused(clientSeq, error)`. `receive` matches the client's own entries in the push stream to in-flight entries by `clientSeq` before anything else, and a match is the acknowledgement (so a lost ack is recovered from the stream). Rebase by replay with id remap (decisions 4 and 5): only unsent entries and refused ones are remapped, never an in-flight one; an in-flight entry that no longer applies is held with everything after it until the server's verdict; an `id-reused` refusal carries the server's head revision, and the client pulls up to that revision before remapping, so the remap sees every id taken so far and the entry is not refused again for one it had not yet received; the entry is then remapped and kept in its own place in the queue, before the entries sent after it, and resubmitted under a new `clientSeq`; any other `CoreError` refusal drops the entry. Once an in-flight entry is known refused (by its own verdict, or by a follower's `predecessor-refused`), every in-flight entry chained after it through `prevSeq` is doomed: held (not shown locally, not remapped, never named as `prevSeq`), with every unsent entry after it held and not sent, until its own verdict arrives. A `predecessor-refused` entry is never dropped for that reason: once its predecessor is resolved (remapped or dropped) it returns to unsent after the remapped predecessor, is replayed and remapped like any unsent entry (with the predecessor's remap table) and resubmitted under a new `clientSeq`, and only a real `CoreError` in that replay drops it; an undo inverse whose command was dropped is removed with it (decision 8). `clientSeq` and `prevSeq` are assigned when an entry is sent, by decision 2's rule: `prevSeq` is the nearest entry before it in the queue that is neither refused nor doomed, else the latest accepted entry, else absent. For a remapped A' that is A's own predecessor (accepted, since the server judged A by core) or nothing, whichever order the verdicts of A and its followers arrive in. A `predecessor-unknown` answer keeps the entry in flight, unchanged, and the client resubmits its in-flight entries in `clientSeq` order, the predecessor first. The undo and redo stacks are remapped with the same table (decision 8). Held, doomed and known-refused entries are hidden from the shown document and from the visible undo stack until they return to unsent or land (decisions 4 and 8); undo acts on the newest shown command, and waits while a held entry comes after that command in the queue. A `remapped` event with the table (for app state) and a `dropped` event with label and `CoreError` per dropped command; the pre-rebase state for the branch fallback (decision 6); selective undo checks (decision 8).
- A serialisable queue state, `SyncQueueState` with its zod schema and a version field, from `client.save()` and `SyncClient.restore(state)`, so a client can be saved and rebuilt at any step (ADR 0009 decision 4: the pending remap tables and entry states are part of the saved queue). It holds: the confirmed revision; the client id, the next `clientSeq` and the latest accepted `clientSeq`; every pending entry in queue order with its `clientSeq` and `prevSeq` once sent and its state, one of in flight, unsent, held, doomed, or refused and awaiting its predecessor (`predecessor-refused`), plus an `id-reused` entry refused and awaiting the pull to the head revision its refusal carried; the pending remap tables, each keyed by the `clientSeq` of the entry that produced it and waiting for the held entries it still has to be applied to; and the known refusals, `clientSeq` to `CoreError`. The confirmed document itself is not in it: the caller saves the state with the document it belongs to (T7.1d).
- `ReferenceServer`: the ordering and validation of decision 3 in memory, with the de-duplication table of decision 2: `(clientId, clientSeq)` to the accepted revision or the refusal, checked in the order of decision 2: a recorded `(clientId, clientSeq)` gets the recorded outcome, refusals included; a `prevSeq` with no recorded outcome gets the retryable `predecessor-unknown` answer, which is not recorded; an entry whose `prevSeq` names a refused entry is refused as `predecessor-refused` and recorded; anything else goes to core. Used by tests and by T7.1c's storage-independent core.
- Protocol messages and their zod schemas (submit, ack, refuse, which carries the server's head revision on `id-reused`, the retryable `predecessor-unknown`, push, pull, hello with protocol and format versions). A submit carries the client's retention floor, for T7.1c's retention of the de-duplication table: the lowest sequence the client may still reference, which is the minimum over its in-flight entries of both their `clientSeq` and their `prevSeq` (ADR 0009 decision 2), so a refused entry that a doomed follower names stays at or above the floor until that follower has its verdict.
- Fuzz tests from T7.0b's generator, now in the package, with lost acks, lost refusals, duplicated deliveries, lost submits (retried later), reordered submits (a later entry reaching the server before its predecessor) and delayed pushes (a client's push stream running behind the server's head, so a refusal can arrive before the entries that caused it) in the random schedules, and a save and restore of a client's queue state at random steps.

**Acceptance.**

- Convergence and validity under random interleavings, with every fault in the fuzz schedules above; a client saved and restored at a random step behaves exactly like one that was never saved.
- Resubmission after a lost ack applies once, and after a lost refusal gets the same refusal.
- An entry whose ack was lost while a foreign entry arrived first is matched from the push stream and never remapped.
- Two clients that add `extrude#3` concurrently end with two extrudes, the loser's entry remapped and resubmitted under a new `clientSeq`. A later entry of the loser that edits its own `extrude#3` is refused as `predecessor-refused`, never applied to the winner's feature, and lands remapped.
- An `id-reused` refusal that arrives while the client's pushes are delayed behind the server's head: the client pulls up to the head revision the refusal carries before remapping, and A' is not refused again for an id taken at or before that revision.
- After an `id-reused` refusal of A with B and C refused as `predecessor-refused`, the client's resubmitted A', B' and C' all land (A' names A's predecessor or nothing, never A, B or C), and entries the client makes afterwards land too.
- A adds `extrude#3`, B edits it and C comes after B, all in flight, and A's `id-reused` refusal arrives before B's and C's verdicts. A' is sent before those verdicts arrive, stays ahead of B and C in the queue, and names A's predecessor or nothing, never C (or B). B and C are held until their verdicts, then land remapped as B' and C' after A'. A check after every step of the schedule shows B never applied to the other client's `extrude#3` in the client's local document.
- The same case with B's and C's verdicts arriving first gives the same `clientSeq` and `prevSeq` for A', B' and C'.
- The same case with a reload: the client is saved after A's `id-reused` refusal and before B's verdict, and a fresh `SyncClient` is restored from the saved state. B's verdict then arrives, and B lands as B' editing `extrude#4`; it is never applied to the other client's `extrude#3`, in the restored client's local document or on the reference server.
- A head refused with a `CoreError` other than `id-reused` (a feature whose sketch another client deleted) is dropped with its notice. An in-flight follower that does not depend on it, refused as `predecessor-refused`, is replayed and lands under a new `clientSeq`, and a follower that edits the dropped feature is dropped with its own `CoreError`.
- An entry whose predecessor's submit was lost gets `predecessor-unknown`, leaves no row in the de-duplication table, and after the predecessor is resubmitted gets its real verdict, so it never lands on another client's feature with the id its predecessor meant to create.
- An undo inverse of an in-flight command is refused with that command, and removed when the command is dropped.
- A held entry is not on the visible undo stack, undo waits while a held entry follows the newest shown command, and the entry is back on the stack with its remapped inverse once it returns.
- Undo after a remap undoes the renamed feature.
- A newer protocol or format version is refused with a message.
- README with the state diagram and the queue state's fields.

**Dependencies.** T7.1a. **Footprint.** `packages/sync/` (new), root workspace config. **Risks.** Rebase cost with a long pending queue after a long offline session; T7.0b's numbers decide whether rebases are batched.

### T7.1c: `apps/server`: Fastify, SQLite, push, blobs, token auth

**Goal.** A server a user can run on their own machine or a small host.

**Scope.**

- New `apps/server`: Node, Fastify 5 (MIT), `@fastify/websocket` (MIT), `better-sqlite3` (MIT) behind a `SyncStore` interface (documents, branches, entries, snapshots every `CHECKPOINT_EVERY` revisions, blobs by SHA-256, clients, and the de-duplication table of ADR 0009 decision 2 with refusals as well as acceptances, written in the same transaction as the entry or refusal it records). A `predecessor-unknown` answer writes nothing. Retention (ADR 0009 decision 2): per `clientId` the table keeps every outcome from the client's retention floor up, plus its latest accepted entry, which a new entry may name as `prevSeq` once the entries before it are resolved; older rows may be pruned. The floor is sent with each submit and is the minimum over the client's in-flight entries of both `clientSeq` and `prevSeq`; the store keeps the highest floor it has received and never lowers it, so an overtaken submit cannot undo a prune. Every `clientSeq` and `prevSeq` a correct client can still send is then in the table (an in-flight entry's own numbers count toward every floor sent while it is in flight, and a new entry's `prevSeq` names an in-flight entry or the latest accepted one), and a `clientSeq` or `prevSeq` below the floor that is not kept is refused with a 4xx as a protocol error.
- Submit order per ADR 0009 decision 2: recorded outcome, then `predecessor-unknown` (HTTP 409 with a retryable code, not recorded), then `predecessor-refused`, then core.
- Endpoints: `POST /documents`, `GET /documents`, `POST /documents/:id/entries` (submit), `GET /documents/:id/entries?since=` (pull), `GET /documents/:id/snapshot`, `PUT` and `GET /blobs/:sha256` (hash checked on upload), a WebSocket per open document for push.
- Validation through `ReferenceServer` (T7.1b) with core; limits: request and entry size, blob size (`MAX_IMPORT_BYTES`), entries per minute per client, a time budget per validation.
- Auth: one bearer token per instance from configuration (T7.0a decides whether real accounts follow, in T7.1h); CORS for the app's origin only; no cookies.
- `pnpm --filter @manufakture/server start` and a container recipe; the app's origin and the database path from environment variables.

**Acceptance.** Integration tests in Node: two clients over real HTTP and WebSocket converge; a restart loses nothing, and a resubmission after it gets the recorded outcome, a refusal included; an entry submitted over HTTP before its predecessor gets the retryable answer with no row written, and its real verdict once the predecessor has been submitted; pruning below a client's floor keeps its latest accepted entry and never changes an outcome a correct client can still ask for; with A (`clientSeq` 1) and B (2, `prevSeq` 1) sent, B's submit lost and A refused, the floor stays 1 while B is in flight, row 1 survives pruning, and B's resubmission with `prevSeq` 1 gets `predecessor-refused`, not a protocol error; a submit carrying a lower floor that arrives after one with a higher floor does not lower the stored floor; a torn write (killed mid-transaction) leaves the store consistent (SQLite transactions); hostile inputs (oversized, malformed, wrong hash, unknown blob, stale protocol) are refused with 4xx and no state change.

**Dependencies.** T7.1b, T7.0d. **Footprint.** `apps/server/` (new), `.github/workflows/ci.yml` (server tests). **Security review:** yes (auth, limits, input validation, validation cost as denial of service). **Risks.** Core work runs on the server's event loop; a huge `batch` blocks it. Mitigation: the size limits, and moving validation to a worker thread if tests show stalls.

### T7.1d: App: sync a document

**Goal.** A user connects a server and syncs a document between two browsers.

**Scope.**

- Settings: server URL and token (stored in the origin's storage, never in documents or `.mfk` files); a per-document **Sync** switch.
- The pending queue persisted beside the log in the document's directory (`documents/<id>/sync.json`): the server id and T7.1b's `SyncQueueState` in full. That is the confirmed revision, the client id, the next `clientSeq`, the latest accepted `clientSeq`, every pending entry with its state (in flight, unsent, held, doomed, or refused and awaiting its predecessor), the pending remap tables and the known refusals (ADR 0009 decision 4). Entries marked only in flight or unsent would not be enough: a reload after A's `id-reused` refusal and before B's verdict would lose A's remap table and the refusal, and B would be replayed onto the other client's `extrude#3`.
- `sync.json` is saved and restored atomically with the snapshot and log it belongs to, under the same crash rules as saves (persistence README): the new files are written first and one commit makes them current together, so a reload never pairs a queue state with a document from another revision. After a reload the client is rebuilt with `SyncClient.restore`: in-flight entries (doomed ones included) are resubmitted unchanged under their `clientSeq`, held entries stay held until their verdicts and then take their pending remap tables, and entries written by an older app version pass through core's command migrations (T7.1a).
- Autosave keeps saving locally; a sync loop submits pending entries, applies pushes through `SyncClient`, and feeds the `DocumentStore` (a remote entry is a new `ChangeEvent` cause, `remote`, so regen and the tree update like any change and the local undo stack is untouched).
- Notices for dropped commands; the branch fallback of ADR 0009 decision 6 through the T2.5c library API; a status indicator (synced, pending n, offline, refused).
- Two tabs of one browser: the Web Lock owner syncs; the other tab follows through the local library as today.

**Acceptance.** e2e `apps/web/e2e/sync.spec.ts` against a server started by the test: two browser contexts edit one document, both converge; offline edits in one context (Playwright `setOffline`) sync on reconnect; concurrent add of an extrude in both contexts gives two features with distinct ids; a command refused after rebase shows its notice and a branch exists with the lost work; a reload mid-rebase: context 1 adds `extrude#3` (A) and edits it (B) while context 2's `extrude#3` is accepted first, the server holds back B's verdict (a test-only reply delay), and context 1 reloads after A's `id-reused` refusal and before B's verdict; after the reload B's verdict arrives and B lands as B' editing `extrude#4`, and neither context 1's document at any point nor the server's log shows B applied to context 2's `extrude#3`.

**Dependencies.** T7.1c; #987 (T2.5a checkpoints), #989 (T2.5c branches). **Footprint.** `apps/web/src/sync/` (new), `apps/server` (the test-only reply delay), `apps/web/src/persistence/{library,autosave}.ts`, `packages/core/src/store.ts` (the `remote` cause), `docs/user/sync.md`. **Security review:** yes (token storage, what a malicious server can send: entries are validated by core on the client too). **Risks.** Remapping ids under an open dialog or a selection; the dialog and the selection follow `SyncClient`'s `remapped` table and re-read their feature after a rebase.

## Risks across M7

- **Command semantics are now forever.** Sync, version replay and branch merges all replay old commands with new code. The golden logs of T7.1a are the guard; a failing golden is a breaking change, not a test to update.
- **Id remapping touches everything that names an id.** Every counter scope (part, document, assembly, CAM) and every naming form M2 to M6 add (derived `:from/`, instances, CAM operations, script operations) must be known to the remap and to the name parser, including sub-ids inside names and their split suffixes. A missed form would rename a local id but leave a stale name, which core then refuses; tests fail loudly, not silently, but only if the form has a test.
- **Concurrent edits of one sketch lose one side** (ADR 0009 decision 7). Fine for one user across devices; a known limitation for several editors until sketch edits get finer commands.
- **The interpreter may be too slow** for scripts users write. The API must make the kernel do the heavy work; if not enough, ADR 0010's first alternative (SES in a worker with shimmed `Math`) is the fallback, at a determinism cost.
- **Hosting is a commitment.** A hosted server and public share links need an owner for uptime, abuse and privacy. Everything here is built so that "self-host only" (T7.0a) is a complete answer.
- **Not in M7**: peer-to-peer sync without a server, field-level merges of one feature, scripts on the server, a public gallery of shared models, user-level libraries (tools, machines and posts from M5, scripts) synced across documents. The M5 plan's open question about where user-level libraries live once a server exists is a follow-up for after M7.
