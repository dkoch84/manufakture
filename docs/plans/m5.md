# M5 plan: 2.5D CAM for the Shapeoko

- Status: proposed
- Date: 2026-09-26
- Epic: "Can't CAD Can We?", milestone M5
- Builds on: M1 as landed (`packages/kernel`, `packages/core`, `packages/regen`, `packages/io`, `packages/sketch`, `packages/units`, `apps/web`), [product decisions](../decisions/0000-product-decisions.md), ADRs [0004](../adr/0004-document-format.md) (document format), [0005](../adr/0005-units.md) (units), [0006](../adr/0006-licensing.md) (licensing) and [0007](../adr/0007-worker-protocol.md) (worker protocol)

M5 turns a part into G-code for the Shapeoko: a tool library, stock and a work coordinate system, 2.5D operations (facing, profile, pocket, drill, V-carve), a toolpath preview with a material-removal simulation, a GRBL post-processor first, 3D surfacing later in the milestone, and DXF/SVG export for laser and plasma. The milestone is accepted when a plywood sign designed in manufakture is cut on a GRBL machine, and CI proves every G-code file the fixtures produce stays inside its stock and machine.

This document has two parts: research findings with sources, then the task breakdown. Everything marked "checked" was read on 2026-09-26 from the source linked next to it; estimates are marked as estimates.

## Part 1: research findings

### Clipper2 in the browser

Clipper2 is Angus Johnson's polygon clipping and offsetting library, the successor of Clipper1. It works on integer coordinates (int64 in C++ and C#), does booleans (intersection, union, difference, xor), polygon and open-path offsetting with round, miter and square joins, rectangle clipping and Minkowski sums. It has no arcs: everything is a polyline.

- **Upstream**: [AngusJohnson/Clipper2](https://github.com/AngusJohnson/Clipper2), BSL-1.0 (GitHub license metadata), latest release `Clipper2_2.0.1` published 2025-12-19, repository active (last push 2026-04-20). Checked through the GitHub API.
- **BSL-1.0 and our license**: the FSF lists the Boost Software License as "a lax, permissive non-copyleft free software license, compatible with the GNU GPL" ([FSF license list](https://www.gnu.org/licenses/license-list.html)). It is not LGPL, so ADR 0006's separate-module rule does not apply: a Clipper2 port may be bundled into our JavaScript, and a WASM build may be bundled or loaded, as suits us. BSL requires the notice in source copies only, not in object code, but ADR 0006 decision 5 ships every bundled dependency's license text anyway.

What this means for us:

- `clipper2-ts` and `clipper2-wasm` are the two live candidates; the other ports are stale. The spike (T5.0a) decides between them on correctness, speed and ergonomics, not on license.
- Both need a scale from millimetres to integers. At 1e-4 mm per unit (0.1 micrometre), a 2 m machine bed is 2e7 units, far inside `clipper2-ts`'s 2^53 limit, and 1e-4 mm is far below the 0.005 mm arc tolerance GRBL enforces (see below). The spike confirms the scale.
- Offsets come back as polylines. G-code wants arcs (G2/G3) for smooth, compact output, and a polyline of hundreds of tiny segments can starve GRBL's planner buffer. So the offset engine needs either analytic offsets for line/arc loops (an offset of an arc is an arc) or an arc refit of Clipper's output within a tolerance, using Z-callbacks to remember which source arc a vertex came from. The spike measures both.

### OpenCAMLib and WASM

[OpenCAMLib](https://github.com/aewallin/opencamlib) (OCL) is a C++ library for 3D toolpaths: drop-cutter (drop a cutter at given XY points until it touches a triangle mesh, the basis of parallel finishing) and push-cutter (waterline: constant-Z loops around the model), with adaptive variants, for cylindrical, ball, bull-nose and conical cutters.

- **License**: the repository is LGPL-2.1 (GitHub license metadata and the README badge; the README says the project moved to LGPL "from August 2018"). The npm package [`@opencamlib/opencamlib`](https://www.npmjs.com/package/@opencamlib/opencamlib) 2023.1.11 declares `"license": "LGPL-3.0"` in its `package.json` (read from the published tarball; the same field is in `src/npmpackage/package.json` in the repository). The two disagree. Under ADR 0006 decision 6 the stricter reading applies until resolved, and that reading is LGPL-3.0, which ADR 0006 as written does not allow: decision 2 admits LGPL only as 2.0 or 2.1 ("only" or "or later"). LGPL-3.0 is compatible with GPL-3.0-or-later ([FSF license list](https://www.gnu.org/licenses/license-list.html)), so adopting OCL needs an **ADR 0006 amendment** that adds LGPL-3.0 to decision 2's allowlist, under the same condition as the other LGPL modules: a separately loaded, replaceable `.wasm`, never bundled into our JavaScript (decision 4). The TypeScript drop-cutter alternative below needs no amendment.
- **Activity**: last push to the repository 2025-02-12 (typo fixes); the npm package was last published 2023-01-11. Slow but not abandoned.
- **The WASM build exists but is rough**. The README: the JavaScript library "works in Node.js and the browser by leveraging emscripten / WASM" and "is not 100% feature complete and lacking some functionality still". The bindings are `src/emscriptenlib/emscriptenlib.cpp` (built with `BUILD_EMSCRIPTEN_LIB=ON`, `USE_OPENMP=OFF`); the JavaScript wrapper exports `Waterline`, `AdaptiveWaterline`, `PathDropCutter`, `AdaptivePathDropCutter`, `STLSurf`, `STLReader`, `CylCutter`, `BallCutter`, `BullCutter`, `ConeCutter`, `Path`, `Point`, `Line` and `Triangle` (read from `lib/emscripten/index.js` in the tarball).
- **The published browser build cannot be used as is.** `browser.js` in the tarball is one 8.6 MB browserify bundle with the `.wasm` inlined as a base64 data URL (Emscripten `SINGLE_FILE`), and it references `USE_PTHREADS`. Bundling it into our JavaScript would break ADR 0006 decision 4 (LGPL modules stay separate and replaceable). Loading it as its own asset might satisfy the letter of the rule, but it is a CommonJS/UMD bundle wrapped in a promise chain, three years old, built with an unknown Emscripten, and it still ships the wasm inside JavaScript. The realistic path is to build OCL ourselves from a pinned commit as an ES module plus a separate `.wasm`, with the build recipe in this repository (as ADR 0002 already requires for any wasm we build), or not to use it.
- **The alternative is our own drop-cutter.** Drop-cutter for flat, ball and V cutters against triangles is a well described algorithm (vertex, facet and edge tests per triangle, with a spatial index), a few hundred lines of TypeScript, and would stay under our own license. Waterline is harder. The spike (T5.0b) compares OCL built by us against a TypeScript drop-cutter on the same mesh, and T5.5 is planned so that either can back it.

### Kiri:Moto as a reference

[Kiri:Moto](https://grid.space/kiri/) is the browser slicer and CAM of [GridSpace/grid-apps](https://github.com/GridSpace/grid-apps).

- **License: MIT.** [`license.md`](https://github.com/GridSpace/grid-apps/blob/master/license.md) is the MIT license, copyright Stewart Allen 2014-2018; `package.json` (version 4.7.0) says `"license": "MIT"`, and the [FAQ](https://docs.grid.space/kiri-moto/faq/) calls it "one of the most liberal in terms of allowing you to do what you want with the code without restriction". The repository is active (last push 2026-08-30).
- **Reuse limits.** MIT code may be copied into a GPL-3.0-or-later project, provided the copyright and permission notice travel with it (in the file and in the shipped notices, ADR 0006 decision 5). grid-apps also bundles third-party code under other licenses (its dependencies include `manifold-3d`, `@salusoft89/planegcs` (LGPL), `three`, `earcut`, `@gridspace/raster-path` and more), so a file must be checked on its own before anything is copied; the repository license does not cover vendored files. The plan uses Kiri as a reference for behaviour and structure, not as a code source; any copied function carries its notice and a line in the task report.
- **Patterns worth taking.** CAM operations ([ops docs](https://docs.grid.space/kiri-moto/CAM/ops/)): outline, level, rough, contour, register, drill, trace, pocket and a raw G-code op. Machine profiles hold G-code macro sections for header, footer, tool change, dwell and spindle, with variables such as `{tool}`, `{tool_name}`, `{rpm}`, `{feed}` and position ([G-code macros](https://docs.grid.space/kiri-moto/gcode-macros/), [machine setup](https://docs.grid.space/kiri-moto/CAM/machines/)), plus directives such as `;; COMMENT_REWRITE_PARENS` for controllers that want `( )` comments.
- **A pattern not to take.** Kiri's macro braces are evaluated as JavaScript ("text inside braces receives evaluation, providing access to JavaScript methods"). A post-processor definition is data a user may download and share, so ours substitutes named variables only and never evaluates code.

### G-code parsers for CI

The bounds check must not grade our own homework: it parses the emitted text with a parser we did not write, and optionally with the firmware's own parser.

- **[cncjs/gcode-parser](https://github.com/cncjs/gcode-parser)** 2.2.0, MIT (npm metadata and GitHub), ESM and CJS, no dependencies, 46 KB unpacked; repository pushed 2026-05-09. Splits lines into words.
- **[cncjs/gcode-interpreter](https://github.com/cncjs/gcode-interpreter)** 3.0.0 and **[cncjs/gcode-toolpath](https://github.com/cncjs/gcode-toolpath)** 3.0.0, MIT, published 2024-11-17. The toolpath package tracks modal state (units, distance mode, plane) and calls back per line and arc segment with start and end points and the arc centre, which is exactly what a bounds checker needs. A development dependency is outside ADR 0006's shipped-code rules, but these are MIT anyway.
- **[grbl/grbl-sim](https://github.com/grbl/grbl-sim)**, GPL-3.0: builds Grbl's own parser on the host; "Run `gvalidate.exe GCODE_FILE` to validate that grbl will parse your GCODE with no errors". Last push 2022-04-05, so it tracks Grbl 1.1, which is what we target.
- **[grblHAL/Simulator](https://github.com/grblHAL/Simulator)**: host build of grblHAL, with a `grblHAL_validator GCODE_FILE` tool that checks for parsing errors; pushed 2026-09-25; described as experimental. The GitHub license metadata says `NOASSERTION`, so its license is read from its `COPYING` file and sources before it goes into CI (it is not shipped either way).

Plan: `gcode-toolpath` for the required bounds check in the normal test run, and an optional CI job that builds `gvalidate` and `grblHAL_validator` from pinned commits and runs them on every golden G-code file, skipping itself when a build fails, like M1's `interop` job.

### GRBL, grblHAL and Carbide Motion: what the post must respect

Grbl 1.1 (read from [`grbl/gcode.c`](https://github.com/gnea/grbl/blob/master/grbl/gcode.c), `protocol.h`, `config.h` and `defaults.h`, and the [v1.1 command list](https://github.com/gnea/grbl/wiki/Grbl-v1.1-Commands)):

- **Supported**: G0, G1, G2, G3, G38.2 to G38.5, G80; G54 to G59; G17, G18, G19; G90, G91; G91.1; G20, G21; G93, G94; G40; G43.1, G49; G61; non-modal G4, G10 L2/L20, G28, G30, G28.1, G30.1, G53, G92, G92.1; M0, M1 (ignored), M2, M30, M3, M4, M5, M8, M9 (M7 only when compiled in).
- **Not supported**: canned cycles G81 to G89 (the source lists them as unsupported), cutter compensation G41/G42, G43 with H, and **M6**: any M code not in the list fails with `STATUS_GCODE_UNSUPPORTED_COMMAND` (error 20). A `T` word is parsed and ignored. So a Grbl post must never emit M6, and drilling cycles must be expanded to G0/G1 moves.
- **Arcs**: G2/G3 in the selected plane, helical when the third axis moves too. IJK are always incremental (G91.1 "does nothing"; G90.1 is refused). An IJK arc whose end point's radius differs from the start point's by more than 0.005 mm **and** by more than 0.1% of the radius, or by more than 0.5 mm at all, fails with "invalid target" (error 33). The full-circle restriction applies to `R`-format arcs only: an `R` arc whose target equals its start fails with "invalid target" (`gcode.c`, around line 692). In IJK mode Grbl 1.1 accepts a full circle: when the start and end angles coincide, `mc_arc` adds 2 pi to the angular travel (`motion_control.c`, around lines 98 to 102). `R` arcs are also numerically fragile near half circles; the post uses IJK. Whether to write a full circle as one IJK arc or as two half arcs is a post choice (T5.4a), not a firmware requirement.
- **Arc tolerance**: `$12` defaults to 0.002 mm, the chord error Grbl uses when it breaks arcs into segments.
- **Line length**: `LINE_BUFFER_SIZE` is 80 characters by default (`protocol.h`); the serial receive buffer is 128 bytes. The post keeps every line under 80 characters.
- **Units**: G20/G21 set the program's units; the post writes G21 and millimetres by default (the document's internal unit, ADR 0005), with G20 as an option.

grblHAL (the Shapeoko 5 Pro's firmware; [grblHAL/core README](https://github.com/grblHAL/core)):

- adds G5 splines, G33, multi-turn arcs (G2/G3 with P), canned cycles G73, G81, G82, G83, G85, G86, G89 with G98/G99, G43/G43.1/G43.2/G49, G54 to G59.3, and **M6** "in two modes (manual with jogging or ATC)" plus M61, M62 to M68;
- M6 and G43 are driver and configuration dependent: whether M6 works (and in which mode) depends on the board driver and the tool change settings, and a manual M6 needs a sender that handles grblHAL's tool change protocol;
- so a grblHAL post may emit M6 and canned drilling cycles, but M6 is an option of the grblHAL dialect, not a default; the plan also expands cycles by default and makes them an option, so one file runs everywhere.

Carbide Motion (the Shapeoko's own sender):

- Carbide 3D's [supported G-codes](https://guides.carbide3d.com/faq/supported-gcodes/) page lists G0 to G3, G4, G17 to G19, G20, G21, G28, G28.2, G90, G91, M0, M1, M2, M30, M3, M5, **M6** "implemented in Carbide Motion to facilitate the Nomad tool length sensor", and "G40, G43, G49 (Accepted but ignored)", "G54-G59 (Accepted but ignored)" with the note that "Carbide Motion uses work coordinate systems internal and care must be taken when interacting with them". The page reads like the Nomad era; it is taken as a floor, not a complete list.
- On a Shapeoko, "M6 commands are ignored by the controller, but Carbide Motion uses the M6 tool change command to trigger a user prompt" ([Shapeoko CNC A to Z](https://shapeokoenthusiasts.gitbook.io/shapeoko-cnc-a-to-z/cad-cam-tools)). With a BitSetter, Carbide Motion then measures the new tool and re-zeroes Z, so the user sets Z zero once per job ([BitSetter](https://shop.carbide3d.com/products/bitsetter), [BitSetter changes in Carbide Motion](https://carbide3d.com/blog/bitsetter-changes-carbide-motion/)). A community thread reports that `T[#]` and `M6` both trigger its probing ([forum, 2020](https://community.carbide3d.com/t/list-of-supported-g-codes-carbide-motion-and-nomad/22903)).
- On stock machines with a trim router, M3/M5 and `S` change a PWM output but do not start the router or set its speed ([Shapeoko CNC A to Z](https://shapeokoenthusiasts.gitbook.io/shapeoko-cnc-a-to-z/cad-cam-tools)): the user sets the dial. The post writes the intended speed in a comment (and the dial setting, when the machine profile has a dial table) as well as in `S`.
- Comments are parenthesised. The post writes only `( )` comments, ASCII, without nested parentheses, and never `;`.
- Work offsets: Carbide Motion owns the WCS. The post writes no G10 and no G54-G59 changes for Carbide Motion, and assumes the user set X, Y and Z zero at the setup's origin (which the setup sheet states).

Consequences for the plan: one post-processor engine with per-dialect data. The **GRBL** post (first) has no M6: a job with one tool is one file; with several tools it writes one file per tool (the default) or one file with an M0 pause and a comment per change. The **Carbide Motion** post writes `M6 T<n>` and relies on Carbide Motion's prompt and BitSetter. The **grblHAL** post may write M6 (an option, since it depends on the driver, the configuration and the sender) and canned cycles. LinuxCNC and Mach3 posts come last.

## Part 2: design decisions the tasks rely on

These are proposals for the architecture ADR (T5.0c) to confirm or change. The tasks below are written against them.

1. **A new package, `packages/cam`**, pure TypeScript: CAM types, the toolpath intermediate representation (IR), operations, the offset adapter, linking, the simulation, the post-processor engine and posts, and a G-code verifier for tests. It has no dependency on the kernel, regen or the app; it takes plain 2D loops, points and meshes in the setup's coordinates. The one polygon library (the Clipper2 port chosen by T5.0a) is its dependency. It runs in Node for tests like every M1 package.
2. **CAM state lives in the document, at document level**, next to `parts`: `cam: { tools, setups, nextIds }`. A setup names the part it machines (`partId`, later a body once M2 brings multi-body parts), its stock, its WCS, its machine and post, and an ordered list of operations. CAM operations are **not** part features: they do not change the body, must not enter regen's body chain, and must not use the `extension` feature kind (which regen treats as a feature on the part). Nothing derived is stored: no toolpaths, no G-code (ADR 0004 decision 1).
3. **Numbers are `StoredExpression`s**, including feeds and speeds, so `1/4"` is a valid tool diameter in a millimetre document and `#depth + 1mm` works in an operation (ADR 0005 decision 2). `packages/units` gains a time dimension for feed rates (`mm/min`, `in/min`) and spindle speeds (`rpm`) first (T5.1a), as ADR 0005's consequences require.
4. **Ids are permanent**, per ADR 0004 decision 4, from document-level counters in `cam.nextIds`: `tool#n`, `setup#n`, operations `<kind>#n` (`profile#2`, `pocket#1`), references `r<n>`. These are a separate namespace from part feature ids; messages always say which setup an operation belongs to. One name overlaps: `profile` is both the CAM operation kind (`profile#2`, a contour cut) and the field of a part feature that names its sketch region (`profile: { sketch, entities? }`, reused by decision 5 for a CAM geometry source). The two never share a scope, but code and messages should say "profile operation" and "sketch profile" (or "region") so they are not confused; T5.0c may rename one if that proves clearer.
5. **Geometry is referenced by name.** An operation's geometry is a list of sources: a planar face (`FaceRef` in a core `Reference` wrapper), a sketch region (`{ sketch, entities? }`, the same shape as a feature `profile`), a hole feature (its points and diameter), and later edges and whole-part silhouettes. They resolve against the part's **final** body, with regen's vocabulary (`exact`, `descendant`, `ancestor`, `ends`, `ordinal`, `fragile`, `lost`, `ambiguous`) and the same re-pick UI.
6. **CAM references never block modelling.** Core's rule "a feature comes after everything it depends on" does not extend to CAM: deleting or reordering a feature that an operation names is allowed, and the operation reports `reference-lost` when toolpaths are next generated. Blocking a model edit because of a toolpath would invert the order users think in (model first, then machine).
7. **Geometry extraction runs in the regen worker; toolpaths run in a CAM worker.** Extracting a face's loops needs the kernel and the final body, which live in the regen worker (ADR 0007, regen README). Toolpaths, the simulation and OpenCAMLib run in a new CAM worker, so a slow pocket or a 3D finish never delays a regen or a sketch drag. This adds a fourth context to ADR 0007's three; T5.0c records it. Between them only plain data travels: loops, points, depths, meshes (transferred).
8. **CAM is lazy.** A regen never generates toolpaths. The CAM workspace asks for toolpaths of the setup on screen, and export generates what is stale. After a model edit, operations whose inputs changed are marked stale and regenerate when shown.
9. **Toolpaths are cached like features** (ADR 0004 decision 8): the key hashes the evaluated operation, tool, setup (stock, WCS), the extracted geometry (which chains regen's `PartResult.bodyKey`), the CAM implementation version and the polygon library build. The first cache is in memory in the CAM worker; OPFS persistence follows the regen cache's `FeatureCache` shape.
10. **The post-processor is data plus one engine.** A dialect is a record of what the controller accepts (codes, tool change style, canned cycles, comment style, line length, number formats, header and footer templates with named variables); the engine turns the IR into lines, tracks modal state and refuses anything the dialect does not allow. User posts are data only; nothing is evaluated.

The document shape, as a first cut for T5.1b (fields grow per operation kind):

```ts
interface ManufaktureDocument {
  // ...as today (format, version, namingScheme, id, name, units, variables, parts)
  cam: CamData; // added by the M5 format version, with a migration that adds an empty one
}

interface CamData {
  tools: CamTool[]; // the tools this document uses, copied from a library
  setups: CamSetup[];
  nextIds: Record<string, number>; // 'tool', 'setup', 'profile', 'pocket', ..., 'r'; only ever increase
}

interface CamTool {
  id: string; // 'tool#1'
  name: string;
  kind: 'flat' | 'ball' | 'bull' | 'vbit' | 'drill' | 'engraver';
  number?: number; // the tool number written with M6 (a vendor catalogue number such as 201)
  diameter: StoredExpression;
  fluteLength: StoredExpression;
  flutes: number;
  cornerRadius?: StoredExpression; // bull
  angle?: StoredExpression; // V-bit included angle, drill point angle
  tipDiameter?: StoredExpression; // V-bit flat tip
  presets: FeedPreset[]; // per material category: rpm, feed, plunge, stepdown, stepover
  source?: { library: string; id: string }; // where it was copied from
}

interface CamSetup {
  id: string; // 'setup#1'
  name: string;
  partId: string;
  machine: string; // machine profile id ('shapeoko-4-xxl', 'shapeoko-5-pro-4x4', ...)
  post: string; // post id ('grbl', 'carbide-motion', 'grblhal', ...)
  stock: CamStock; // box: from the part's bounding box plus margins, or explicit size and offset; material
  wcs: CamWcs; // up direction (model axis or planar FaceRef), origin (stock corner or centre; top or bottom)
  heights: { clearance: StoredExpression; retract: StoredExpression };
  operations: CamOperation[]; // cut order
}

interface CamOperation {
  id: string; // 'profile#1'
  kind: 'facing' | 'profile' | 'pocket' | 'drill' | 'vcarve' | 'surface3d';
  name: string;
  suppressed: boolean;
  tool: string; // a CamTool id
  geometry: CamGeometrySource[];
  // kind-specific fields: depths, stepdown, stepover, side, tabs, lead-in, ramp, ...
}
```

## Part 3: tasks

Conventions: "Deps" lists tasks that must land first; "M1" names the landed packages a task builds on. "Footprint" is where the code goes. Every task adds tests next to its code and updates the README of each package it touches, like M1. Every new runtime dependency gets its license checked from the installed package (ADR 0006 decision 6) and a line in the task report.

### T5.1e Kernel: planar face loops and plane sections

- **Goal**: the kernel gives CAM the outline of a planar face (and the section of a body at a plane) as exact lines and arcs, by name.
- **Scope**: a `faceLoops` op and `Kernel.faceLoops(shape, target, frame, deflection)`: target by face name on a named body (as `measure` does) or by index; returns the outer loop and hole loops in the frame's 2D coordinates, each segment a line or arc (from `BRepAdaptor_Curve` types `line` and `circle`) or a polyline flattened within the deflection (`GCPnts_TangentialDeflection`) for anything else, with each segment tagged by the edge's name (the naming layer's edge name) so toolpaths can say which edge they follow; the plane's height along the frame normal; orientation (outer counter-clockwise, holes clockwise). A `section` op: the loops of a body cut by a plane (`BRepAlgoAPI_Section`), for silhouettes and "profile the part at this height". Wire order from `BRepTools.OuterWire` and `BRepTools_WireExplorer` (declared in libcascade 3.0.2's `types.d.ts`; each must be proven bound and working, as the STEP work did for XCAF). Memory rules as the rest of the kernel (scopes, `Nullify`, the embind tracker test), with libcascade 3.x's destructor problem in mind: for about 2,100 of its classes `delete()` frees nothing (the registered destructor is empty), including every `BRepAlgoAPI_*` class, `BRepAlgoAPI_Section` among them, `TopoDS_Shape` and its subtypes, `TopExp_Explorer` and `BRep_Builder`. So `section` and `faceLoops` release what they can explicitly: `Nullify()` on every shape they hold, `Clear()` on locations and on the section algorithm (with empty arguments and tools set) before `delete()`, which is what `releaseOwned` in `packages/kernel/src/occt.ts` already does for `TopoDS_*`, `TopLoc_Location` and `BRepAlgoAPI_*`; any new class these ops hold that `releaseOwned` does not cover gets a rule there.
- **Acceptance**: golden tests: a box top face (4 lines), a face with a through hole (outer plus one circle), the M1 bracket's foot top with its counterbores (the counterbore floors are separate faces; the foot top has two circular holes), a filleted edge's neighbour face (a line meeting an arc), a face with a B-spline edge (flattened within deflection, checked by distance); section of the bracket at a height; nothing left undeleted (`track()`); the ops through the service like `feature-ops.test.ts`.
- **Deps**: none. M1: `packages/kernel` (naming, measure's target resolution, `sketchFrame` / `frameOnPlane`).
- **Footprint**: `packages/kernel` (`src/loops.ts` or similar, ops, README).
- **Risks**: libcascade bindings present in the `.d.ts` may still be empty or broken at run time (ADR 0002); the tracker test proves `delete()` was called, not that memory was freed, so a leak from the empty destructors shows only in a heap measurement over repeated calls (add one for `section`); seam edges on planar faces do not occur, but degenerated edges might; face orientation (reversed faces) flips loop direction.

### T5.1f Regen worker: CAM geometry stage

- **Goal**: turn a setup's operations into plain geometry in machine coordinates, resolving references like regen does.
- **Scope**: a `camGeometry(document, setupId, { generation })` call on the regen worker API (`createRegenWorkerApi`), after regen has built the part: resolve each geometry source against the part's final body (`resolve` op for face references, then `faceLoops`), sketch regions from the solved sketches regen already holds (`detectRegions` on the cached solve, placed by the sketch's placement), hole features' points and diameters and extents (from the translated hole input), the part's tight bounding box (for stock) and its mesh at a CAM tolerance (for 3D and simulation); transform all into the setup's WCS; evaluate CAM expressions with the document's variables (the same evaluation and dimension check as `values.ts`); report per operation `ok`, `error` (`reference-lost`, `reference-ambiguous`, `expression`, `unsupported`) or warnings, with the reference resolutions in regen's vocabulary; cache the result by a key chaining the part's `bodyKey`, the evaluated setup and sources.
- **Acceptance**: integration tests with the real kernel and solver (like `integration.test.ts`): the M1 bracket with a setup whose operations reference the foot top face, a sketch region and the hole feature give the expected loops, depths and drill points; editing `#thickness` moves the depths and keeps the references `exact`; deleting the referenced sketch gives `reference-lost` on that operation only; a CAM-only edit sends no feature ops.
- **Deps**: T5.1b, T5.1c, T5.1e. M1: `packages/regen` (engine, cache, translate, values, worker API, client).
- **Footprint**: `packages/regen` (a `cam.ts` stage, worker API, client), README.
- **Risks**: regen currently reports the solved sketch only through its cache; the stage must read it without widening `RegenResult`. Generations are one sequence per client (regen README): the CAM call must be sent at `latestGeneration`, never a new one, or it cancels the regen in flight.

### T5.2g Linking and job assembly: order, retracts, rapids, tool grouping

- **Goal**: turn a setup's operations into one safe, reasonably short program per tool.
- **Scope**: operation order as the user set it, with an option to group by tool; rapids at clearance height between operations and at retract height within one where safe (the move stays inside already-cleared area or above the stock top); nearest-neighbour ordering of independent loops and holes; tool changes as IR `toolChange`; spindle on with a dwell after changes; start and end at clearance height; the job's statistics.
- **Acceptance**: tests: no rapid below the stock top outside cleared regions (checked against the stock and a raster of cleared area), every tool change preceded by a retract, total rapid length reduced against the naive order on a fixture, and the IR validator passes on the whole job.
- **Deps**: T5.2b (and the other ops as they land).
- **Footprint**: `packages/cam/src/job.ts`.
- **Risks**: safe-link checks against cleared material are easy to get subtly wrong; default to clearance height when unsure.

### T5.3a CAM workspace UI: setups, stock, WCS, tools, operation dialogs

- **Goal**: a user sets up a job in the app.
- **Scope**: a "Manufacture" workspace switch next to modelling; a setup panel (part, machine, post, stock from bounding box with margins or explicit, material defaulting to the part's `material`, WCS up axis and origin with a gizmo); the tool library dialog (T5.1d) and tools in the document; an operations list modelled on the feature tree (order, suppress, rename, per-operation status, errors and re-pick for lost references, stale marks); operation dialogs built from `ExpressionField` with the new kinds, geometry picking of planar faces (the `pick` op) and sketch regions; generate on demand through the CAM worker. User documentation in `docs/user/cam.md`.
- **Acceptance**: component tests for each dialog (fields, validation, commands produced); an e2e test creating a setup and a profile operation on the M1 bracket and seeing it `ok`, which in this task means "geometry resolved" (the T5.1f stage returned `ok` for its references and expressions); generating the toolpath is checked once T5.2b lands; undo and redo of every CAM command; reload keeps the setup (persistence).
- **Deps**: T5.1b, T5.1d, T5.1f, T5.1g. M1: `apps/web` (`features/`, `tree/`, `components/ExpressionField`, `viewport/picking`, `state/`).
- **Footprint**: `apps/web/src/cam/`, `docs/user/`.
- **Risks**: the workspace switch touches the app's layout; keep the modelling UI unchanged when CAM is closed.

### T5.3b Toolpath preview and playback

- **Goal**: see what will be cut before cutting it.
- **Scope**: three.js rendering of the IR (cuts coloured per operation, plunges and ramps distinct, rapids dashed), stock as a translucent box, WCS gizmo, per-operation visibility, a playback scrubber with a tool marker, statistics per operation and job (length, estimated time).
- **Acceptance**: unit tests for IR to line geometry (arcs tessellated within a tolerance, buffer sizes); a viewport screenshot test of a fixture job like `m1-views.spec.ts`; scrubbing to a move index shows the tool at that move's end.
- **Deps**: T5.1c, T5.3a. M1: `apps/web/src/viewport`.
- **Footprint**: `apps/web/src/cam/preview/`.

### T5.3c Heightmap material-removal simulation and gouge check

- **Goal**: see the stock being cut, and catch gouges and leftovers automatically.
- **Scope**: in the CAM worker: a heightfield over the stock (cell size from the smallest tool, capped for memory), tool stamps for flat, ball, bull and V profiles swept along lines and arcs (including helices), incremental updates for playback; a comparison against the part's own heightmap (rastered from the part mesh in the setup's WCS): cells cut below the part surface by more than a tolerance are gouges, cells left above it are leftover stock; rapids that pass through uncut stock are collisions. Rendering as a displaced grid mesh on the main thread, with gouges highlighted.
- **Acceptance**: tests: a single straight cut leaves a slot of the tool's width and depth; a ball tool leaves a round-bottom groove of the right radius; a profile around the M1 bracket's outline with tabs (generated by T5.2b) leaves tabs of the right height; a deliberately wrong offset is reported as a gouge; a rapid through stock is reported; performance recorded for a fixture job (the profile-with-tabs job plus a pocket, at a stated stock size and cell size), as an estimate with the machine named. The sign job does not exist until T5.7a.
- **Deps**: T5.1g, T5.3b, T5.2b (the bracket profile with tabs).
- **Footprint**: `packages/cam/src/sim/`, `apps/web/src/cam/sim/`.
- **Risks**: a heightfield cannot represent undercuts (fine for 3-axis); memory for large stock at fine cells.

### T5.4a G-code engine: modal writer, arcs, formatting, dialect data

- **Goal**: one engine that writes correct G-code for any dialect described as data.
- **Scope**: `packages/cam/src/post/`: a dialect record (allowed G and M codes, tool change style `none` / `m0-pause` / `m6`, split files per tool, canned cycles allowed, comment style, maximum line length, decimals per unit, header and footer templates with named variables such as `{tool}`, `{toolName}`, `{rpm}`, `{feed}`, `{job}`, `{date}` and nothing evaluated); the writer: modal state tracking (omit repeated G and F words), G17 arcs with IJK incremental, helical arcs, full circles split in two by default (a deliberate choice for senders and previewers that mishandle a full-circle arc, and for the dialects that need it; Grbl 1.1 itself accepts an IJK full circle, so single-arc output is a dialect option), arcs below a minimum radius written as lines, GRBL's arc rule checked on the rounded numbers (start and end radius within 0.005 mm and 0.1%), unit conversion for G20 output, number formatting without exponents, comment sanitising (ASCII, no nested parentheses), line length enforcement; a refusal (error value) whenever the IR needs something the dialect lacks.
- **Acceptance**: unit tests for every rule above with exact expected text; a property test writing random arcs and checking each against Grbl's arc rule after rounding; round trip: parse the output with `gcode-toolpath` and compare positions with the IR within the rounding.
- **Deps**: T5.1c.
- **Footprint**: `packages/cam/src/post/`.
- **Risks**: template substitution creeping towards a language; keep it to named variables.

### T5.4b GRBL post-processor

- **Goal**: the first post: G-code that Grbl 1.1 accepts, for the Shapeoko.
- **Scope**: the `grbl` dialect: header `G21 G90 G17 G94` (or G20), a comment block with job, setup, tools and the WCS origin to zero at, `M3 S<rpm>` with the rpm and router dial setting in a comment, no M6 (split files per tool by default, `m0-pause` as an option), `M5` and `M30` at the end, lines under 80 characters, parenthesised comments; file naming through `@manufakture/io`'s `fileName`.
- **Acceptance**: golden G-code files for fixture jobs built as hand-written IR in the test (a profile with tabs, a pocket, drilling, a two-tool job in both multi-tool modes), so this task does not wait for the operations, stable byte for byte; no word outside the dialect's list (checked by the T5.4d checker when it lands, by a word whitelist before that).
- **Deps**: T5.4a.
- **Footprint**: `packages/cam/src/post/grbl.ts`, golden files under `packages/cam/test/`.
- **Risks**: users of Carbide Motion would expect M6 prompts; the export UI (T5.4e) steers them to the Carbide Motion post.

### T5.4c Carbide Motion, grblHAL, LinuxCNC and Mach3 posts

- **Goal**: the dialects the Shapeoko family and common controllers need.
- **Scope**: `carbide-motion` (`M6 T<n>` at every tool change so Carbide Motion prompts and the BitSetter measures; no G10 or WCS changes; comment conventions as researched), `grblhal` (tool changes as in the `grbl` dialect by default, with M6 and the tool number as an option for machines whose driver and configuration support it and whose sender handles a manual M6; optional canned cycles G81/G83 for drilling; G43 not used unless configured; both caveats kept as footnotes in the cam README's dialect table), `linuxcnc` (M6 T, G43 H, G64 P with the path tolerance, `%` wrappers as LinuxCNC expects) and `mach3`; each as dialect data with golden files.
- **Acceptance**: golden files per dialect for the same fixture jobs; the dialect differences are visible in a single table in the cam README; each post's output passes the T5.4d checker for its dialect.
- **Deps**: T5.4b, T5.4d (its acceptance runs the T5.4d checker).
- **Footprint**: `packages/cam/src/post/`.
- **Risks**: Carbide Motion's accepted set is documented only partly; confirm on a machine in T5.7b and record any surprise.

### T5.4d CI G-code verification: bounds checker and firmware validators

- **Goal**: every G-code file the fixtures produce is proven inside its stock and machine, by a parser we did not write.
- **Scope**: `verifyGcode(text, { dialect, stock, machine, tools })` in `packages/cam` test utilities, built on `gcode-toolpath` (development dependency, MIT): parse, then check every move (arcs by their true extremes) against the machine travel from the WCS origin, cutting moves within the stock outline grown by the tool radius and the lead-in allowance, the lowest Z at most the stock bottom minus the through-cut allowance, no cutting move with the spindle off, feeds positive, every tool change in the dialect's style, words within the dialect's list, line length; returns a report with extents. A vitest project that runs it on every golden file. An optional CI job `gcode-validate` that builds `gvalidate` (grbl-sim) and `grblHAL_validator` (grblHAL Simulator) from pinned commits and runs them on the golden files, skipping itself when a build fails, never blocking a merge (like `interop`); the grblHAL Simulator's license is read from its files first.
- **Acceptance**: the checker catches seeded faults (a move past the machine travel, a cut below the spoilboard allowance, an M6 in a Grbl file, an 81-character line, an arc failing the radius rule); every golden file passes; the CI job runs green on the goldens.
- **Deps**: T5.4b. M1: CI patterns in `.github/workflows/ci.yml` (`kernel-goldens`, `interop`).
- **Footprint**: `packages/cam/test/`, `.github/workflows/ci.yml`, `vitest.config.ts`.
- **Risks**: grbl-sim is old and may not build on current compilers; it is optional for that reason.

### T5.7a M5 acceptance: the plywood sign, end to end, with checks

- **Goal**: prove M5 through the UI the way M1 proved the bracket.
- **Scope**: an e2e spec `apps/web/e2e/m5-sign.spec.ts` and `docs/m5-acceptance.md`: model a sign in plywood (for example 300 by 150 mm, `#thickness` set to the measured sheet, rounded corners, two mounting holes as hole features, a recessed border, and lettering or artwork from T5.8, or sketch artwork if T5.8 is not in); a setup on a Shapeoko profile with the stock from the part and origin at the top front left corner; operations: V-carve the lettering (90 degree bit), pocket the border (1/8" flat), drill or bore the holes, profile outside with tabs (1/4" flat); simulate with no gouge and no collision; export with the GRBL post (two files, one per tool, or the chosen mode) and with the Carbide Motion post; `verifyGcode` on every file; the files uploaded as CI artifacts for the optional `gcode-validate` job; screenshots for the doc; performance numbers labelled as estimates.

### T5.7b Cut the plywood sign on a GRBL machine (human-only)

- **Goal**: the milestone's physical acceptance.
- **Human-only**: yes. It needs a person at a Shapeoko with stock, tools, a spoilboard and hearing protection. An agent can prepare the files and the checklist and write up the results the person reports; it cannot run the machine.
- **Scope**: cut T5.7a's files on a Grbl-family Shapeoko through Carbide Motion (the Carbide Motion post), and if available the GRBL post through another sender, and on the Shapeoko 5 Pro (grblHAL) if one is available; record machine, firmware and sender versions, stock actual thickness, tools, what happened at each tool change (prompt, BitSetter), any controller error, the cut time against the estimate, measured outer dimensions and hole positions against the model, tab and pocket depths, and photos.
- **Acceptance**: a cut sign whose outer dimensions and hole positions match the model within 0.3 mm (a target to confirm against the machine's own accuracy, not a spec), no controller errors, and a results section added to `docs/m5-acceptance.md`; any post change it forces is a follow-up task.
- **Deps**: T5.7a.
- **Footprint**: `docs/m5-acceptance.md`, photos under `docs/m5-acceptance/`.
- **Risks**: material and machine variation; the first cut should be an air cut above the stock (Z offset) to check motion.

### T5.8 Sign artwork: SVG import to sketch geometry (text if in scope)

- **Goal**: lettering and artwork for the sign, as sketch geometry the CAM operations can use.
- **Scope**: import an SVG file's paths into a sketch as lines and arcs (Bezier curves approximated by arcs within a tolerance, since sketches have lines, arcs and circles only), with a scale and placement, as a new sketch or into the open one, fixed so the solver keeps it where it was placed: either held by constraints (a fix constraint per point) or stored as construction-free fixed geometry that the solver treats as constants and never moves, whichever the solver's performance allows (see risks); optionally text to sketch geometry through a font library and a bundled font, if the text feature is not planned in another milestone.
- **Acceptance**: an SVG with letters imports as closed regions that `detectRegions` finds, with arcs within the tolerance; the regions work as V-carve and pocket sources, which this task checks through `detectRegions` (the regions those operations consume) until T5.2c and T5.2f land, and then by generating a pocket and a V-carve on them.
- **Deps**: none within M5. M1: `packages/sketch`, `packages/core`, `apps/web/src/sketcher`.
- **Footprint**: `packages/io` (SVG path parsing), `apps/web/src/sketcher/`.
- **Risks**: **coordinate with the owners of other milestone plans before creating this task**: text in sketches may already be planned elsewhere. A bundled font brings a font license (typically the SIL Open Font License) that ADR 0006's allowlist does not name yet; adding it needs an ADR 0006 amendment. Importing hundreds of fixed entities may be slow in the solver; they may need to be stored as fixed construction-free geometry without per-point constraints.

## Open questions

- Where do user-level libraries (tools, machines, posts) live once M7 brings a server? M5 keeps them in OPFS with JSON import and export.
